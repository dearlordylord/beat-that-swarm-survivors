# GGPO / GGRS: подходит ли rollback для Area и projectile боя?

Проверено 25 октября 2026 по исходникам и официальной документации: GGPO `master` (версия релиза здесь не предположена), GGRS `0.13.0`, `bevy_ggrs` upstream `main` и release-матрице. Это обзор интерфейсов и ограничений; код, зависимости и игровые проверки не менялись.

## Короткий ответ

GGPO и GGRS дают работающий каркас **rollback по кадрам ввода**: локально предсказать недостающий ввод партнёра, сохранить state, принять настоящий ввод, восстановить прошлый state и проиграть кадры заново. Они подходят, если оба клиента симулируют один и тот же детерминированный мир. GGPO описывает в state также врагов, все пули, здоровье и очки; вне state можно оставить только то, что не влияет на исход боя. Это прямо включает снаряды и цели, от которых зависит их попадание. [GGPO Developer Guide: state and inputs](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#game-state-and-inputs), [GGRS: how it works](https://docs.rs/ggrs/0.13.0/ggrs/).

Для текущего примера это **архитектурная альтернатива, не подключаемый фикс**. Survivors сейчас исполняет общий чистый Bend gameplay на host, guest отправляет команды через Iroh и получает authoritative observations; `bevy_ggrs` сохраняет и восстанавливает зарегистрированные Bevy-компоненты/ресурсы, а GGRS ожидает состояние и симуляцию, которыми управляет Rust-клиент. GGPO/GGRS в штатной модели синхронизируют полные копии игры через ввод игроков, а не добавляют server-authoritative reconciliation поверх существующего протокола. [Текущий контракт co-op](../examples/survivors/COOP.md), [GGPO synchronization model](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#using-state-and-inputs-for-synchronization), [bevy_ggrs](https://github.com/gschup/bevy_ggrs).

Если отсутствующий host input поздно меняет выстрел, rollback может исправить получателя так: загрузить state до выстрела и повторить весь кадр с настоящим вводом host. До прихода ввода прогноз может всё ещё выбрать неверную цель. Библиотека не знает будущий выстрел заранее и не превращает предсказанный контакт в подтверждённое попадание.

## Контракт, который нужно встроить

**Каждый simulation frame должен получать ввод всех игроков для того же frame index.** В GGPO приложение вызывает `ggpo_add_local_input`, затем на каждом шаге использует именно результат `ggpo_synchronize_inputs`, в том числе при повторном проходе; текущий ввод устройства не заменяет исторический. В GGRS приложение вызывает `add_local_input` для локальных handle и `advance_frame()`, затем выполняет выданные `GgrsRequest` в их порядке. `AdvanceFrame` содержит ввод каждого игрока и статус `Confirmed`, `Predicted` или `Disconnected`. Командный FIFO ACK или число миллисекунд между сообщениями сами по себе не назначают игровой кадр. [GGPO input synchronization](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#synchronizing-local-and-remote-inputs), [GGRS main loop](https://github.com/gschup/ggrs/blob/main/docs/main-loop.md), [GgrsRequest](https://docs.rs/ggrs/0.13.0/ggrs/enum.GgrsRequest.html), [InputStatus](https://docs.rs/ggrs/0.13.0/ggrs/enum.InputStatus.html).

На уровне игры нужно иметь чистую операцию вида `advance(state, inputs_for_frame) -> state`. Её результат должен зависеть только от сохранённого состояния и назначенных вводов кадра. Сохранять/загружать нужно **всё gameplay-состояние**, включая tick, состояние RNG, порядок принятия решений и рождение/удаление сущностей. GGRS оставляет приложению реализацию `Config::{Input, State, Address}` и обработку сохранения, загрузки и одного simulation step; передаются игровые вводы, а не полное состояние мира. [GGRS setup](https://github.com/gschup/ggrs/blob/main/docs/setup.md), [GgrsRequest API](https://docs.rs/ggrs/0.13.0/ggrs/enum.GgrsRequest.html).

Для Area/projectile сценария rollback closure — не только Transform снаряда. В неё входят все позиции и жизни потенциальных целей, игроки и их кадрированные вводы, auto-fire cooldown/оружие, projectile birth/velocity/lifetime/team/owner, pierce и visited targets, AoE/status/damage state, slot или generation identity и RNG. Если исключить состояние, способное изменить hit recipient, повтор кадра не воспроизведёт тот же конфликт. GGPO отдельно приводит для shooter enemies, bullets, HP и score как части state; `bevy_ggrs` восстанавливает сущности и только зарегистрированные компоненты/ресурсы. [GGPO state and inputs](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#game-state-and-inputs), [bevy_ggrs snapshot architecture](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#snapshot-storage).

### Три разных «лага»

| Настройка | Что она означает | Практический эффект |
| --- | --- | --- |
| **Input delay `D`** | Ввод, снятый на frame `F`, применяется на `F + D`. | Постоянно добавляет задержку управления, но даёт пакету время дойти и уменьшает число rollback. В GGRS default — `0`; документация обычно приводит `2–4` кадра как tuning range. |
| **Max prediction window `P`** | Максимум кадров, на которые сессия может уйти вперёд без подтверждённого remote input. | Ограничивает глубину спекуляции и потенциального повторного прохода; при исчерпании сессия ждёт/пропускает advancement. Default GGRS — `8`. `P=0` включает lockstep без rollback и может останавливать игру до прихода ввода. |
| **Observation/display delay** | Отложенное отображение полученного снимка или буфер интерполяции. | Сдвигает то, что видит игрок; само по себе не назначает ввод на другой simulation tick и не является input delay. |

Это разные оси: при 60 Hz `D=2` — около 33 ms преднамеренной задержки локального ввода, а `P=8` — предел в восемь кадров предсказания, не восемь кадров постоянной input latency. Текущий `COOP_PROJECTILE_DELAY_MS=800` — тест задержки наблюдения; он не равен GGRS `with_input_delay`. [GGRS SessionBuilder](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_input_delay), [prediction window и lockstep](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_max_prediction_window), [локальный тест-контракт](../examples/survivors/COOP.md#guest-input-response).

### Replay-safe presentation и детерминизм

Не публиковать звук, экранный flash, rewards, achievements или I/O непосредственно внутри повторно исполняемого simulation step. GGPO советует отделять game state от render state и откладывать эффекты/звук до конца rollback. GGRS помечает входы кадра как speculative/confirmed; в Bevy `Events<T>` не snapshot-ятся, поэтому библиотека советует держать gameplay-события в rollback component/resource и создавать внешние события за пределами `GgrsSchedule`. Для одноразовой presentation использовать стабильный event key (например, frame + logical shot generation + target life + contact ordinal) и выпускать/дедуплицировать только подтверждённые результаты. [GGPO render/effect guidance](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#separate-updating-game-state-from-rendering-in-your-game-loop), [GGRS InputStatus](https://docs.rs/ggrs/0.13.0/ggrs/enum.InputStatus.html), [bevy_ggrs event pitfall](https://github.com/gschup/bevy_ggrs/blob/main/docs/pitfalls.md#events).

Rollback требует одинаковый результат на всех платформах и сборках. GGRS отдельно предупреждает о различиях floating-point между x86/ARM и Debug/Release, о нестабильной итерации map/set и RNG из системной энтропии; рекомендует fixed-point/integer для чувствительной игровой математики, детерминированный порядок и RNG, состояние которого входит в rollback. Это существенно для нашего Bend `F32` и native/browser execution: нормализация float после JS boundary не доказывает одинаковый результат всей симуляции. [GGRS determinism requirements](https://github.com/gschup/ggrs/blob/main/docs/setup.md#determinism), [GGPO RNG/wall-clock guidance](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#make-sure-your-game-state-advances-deterministically), [наши текущие ограничения проверки](../examples/survivors/COOP.md#checks).

## Цена и пределы с сотнями сущностей

В обычном режиме каждый кадр GGRS запрашивает сохранение state; rollback восстанавливает его и повторно исполняет до текущего кадра. По умолчанию GGRS хранит кольцевой буфер из `max_prediction_window + 1` state slots. У `bevy_ggrs` snapshot хранит значения зарегистрированных типов для rollback entities; `Clone` может аллоцировать на каждый кадр, `Reflect` документация называет самым медленным вариантом. Sparse saving сокращает количество save requests, но может увеличить длину replay. Значит, стоимость определяется и байтами/типами в snapshot, и ценой одного полного simulation tick, и длиной/частотой rollback. [GGRS saved-state ring](https://github.com/gschup/ggrs/blob/v0.13.0/src/sync_layer.rs), [GGRS sparse saving](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_sparse_saving_mode), [bevy_ggrs snapshot strategies](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#snapshot-strategies).

Сотни сущностей сами по себе не являются обещанием производительности или запретом. Если каждый повторный tick делает `projectiles × targets` проверок Area/contact, rollback повторит и эту работу. В нашем локальном профиле есть отдельный сценарий 100 снарядов × 400 целей = около 40 000 пар на один tick; это измерение текущего Bend combat forecast, **не** замер GGRS и не предсказание времени rollback. Нужен benchmark реального состава state с ожидаемым числом активных врагов/снарядов и correction window; никаких универсальных entity capacity или сравнимых GGRS цифр в просмотренных upstream источниках нет. [текущий профиль контактов](coop-combat-replay-cost.md).

## Подходит ли к нашему проекту

- **GGPO:** хороший эталон минимального callback-контракта (`advance_frame`, save/load, `ggpo_synchronize_inputs`) и presentation separation. Потребуется state serializer, идентичная fixed-step Bend симуляция и интеграция C API; GGPO не подключает сам себя к Iroh или JS game worker.
- **GGRS:** более близкий Rust вариант. Его `NonBlockingSocket` позволяет написать транспортный адаптер, а `wasm-bindgen` feature поддерживает WASM. Но это приложение должно реализовать адресуемый обмен дискретными GGRS `Message`; текущий Iroh adapter передаёт надёжные сообщения потоками и не реализует этот интерфейс. Для браузеров upstream прямо описывает Matchbox как готовый WebRTC socket/signalling вариант. Адаптация Iroh возможна только после отдельной проверки packet boundaries, ordering, buffering, pacing и поведения при потере/задержке. [GGRS custom socket](https://docs.rs/ggrs/0.13.0/ggrs/trait.NonBlockingSocket.html), [GGRS browser setup](https://github.com/gschup/ggrs/blob/main/docs/setup.md#feature-flags), [наша Iroh transport boundary](../tools/iroh-transport/README.md).
- **bevy_ggrs:** самый готовый Bevy путь: plugin, `ReadInputs`, `GgrsSchedule`, регистрация `Rollback` entities и каждого rollback component/resource. Это полезный образец восстановления ECS identity и детерминированного time. Он не интегрирует текущий Bend world; совместимые версии следует pin-ить комплектом (на просмотренной матрице release `bevy_ggrs 0.22` соответствует Bevy `0.19` + GGRS `0.13.0`; upstream `main` показывал другую пару). [quickstart и версия матрицы](https://github.com/gschup/bevy_ggrs#bevy-ggrs), [rollback loop](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#the-rollback-loop).

## Безопасная оценка без переноса игрового backend

1. Сначала повторить выбранный pure Bend combat scenario из общей canonical anchor и inputs, включая поздний host shot, Area, recycled shot/target slot и hit recipient. Текущий код уже отделяет forecast от authoritative damage/rewards; результаты временных прогонов и их ограничения записаны в [исследовании попаданий](coop-projectile-visibility.md). JS-наборы тестов удалены параллельным изменением репозитория; host остаётся источником результата.
2. Если нужна проверка самой rollback-модели, сделать маленький GGRS prototype только после выбора runtime/bridge для Bend state: `Config`, canonical save/load и `advance(state, inputs)`. Прогнать GGRS `SyncTestSession` с `with_check_distance(...)`; он намеренно повторно проигрывает предыдущие кадры и сравнивает checksum. Затем прогнать задержки/потерю на P2P session и только после этого снимать профили полного набора combat entities. Не начинать с `bevy_ggrs`, пока simulation действительно не живёт в Bevy ECS. [GGRS SyncTest/debug guide](https://github.com/gschup/bevy_ggrs/blob/main/docs/debugging-desyncs.md#synctest-session), [GGRS `ex_game_p2p` loop](https://github.com/gschup/ggrs/blob/main/docs/main-loop.md#working-example).

Никакого rollback перехода не требуется только для того, чтобы улучшить текущую синхронизацию. Сохранять host authority и проверять полный, согласованный projectile/target forecast — отдельный путь с меньшими изменениями, чем перенос всей игры на симметричный P2P rollback.
