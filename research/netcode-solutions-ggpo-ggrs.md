# GGPO / GGRS: is rollback suitable for Area and projectile combat?

Verified on October 25, 2026 using sources and official documentation: GGPO `master` (the release version is not assumed here), GGRS `0.13.0`, `bevy_ggrs` upstream `main` and the release matrix. This is an overview of interfaces and limitations; code, dependencies and game checks have not changed.

## Short answer

GGPO and GGRS provide a working framework **rollback on input frames**: locally predict the missing partner input, save the state, accept the real input, restore the previous state and play the frames again. They are suitable if both clients are simulating the same deterministic world. GGPO also describes enemies, all bullets, health and points in state; You can only leave outside the state what does not affect the outcome of the battle. This directly includes the projectiles and the targets they depend on to hit. [GGPO Developer Guide: state and inputs](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#game-state-and-inputs), [GGRS: how it works](https://docs.rs/ggrs/0.13.0/ggrs/).

For the current example, this is an **architectural alternative, not a drop-in fix**. Survivors is now performing general clean Bend gameplay on the host, the guest sends commands through Iroh and receives authoritative observations; `bevy_ggrs` saves and restores registered Bevy components/resources, and GGRS waits for the state and simulation managed by the Rust client. GGPO/GGRS in the standard model synchronizes full copies of the game through player input, rather than adding server-authoritative reconciliation on top of the existing protocol. [Current contract co-op](../examples/survivors/COOP.md), [GGPO synchronization model](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#using-state-and-inputs-for-synchronization), [bevy_ggrs](https://github.com/gschup/bevy_ggrs).

If a missing host input changes the shot late, rollback can correct the receiver by loading the state before the shot and repeating the entire frame with the real host input. Before the input arrives, the forecast may still select the wrong target. The library does not know the future shot in advance and does not turn a predicted contact into a confirmed hit.

## Contract to be embedded

**Each simulation frame must receive input from all players for the same frame index.** In GGPO, the application calls `ggpo_add_local_input`, then at each step it uses exactly the result of `ggpo_synchronize_inputs`, including the second pass; The current device input does not replace the historical input. In GGRS, the application calls `add_local_input` for local handle and `advance_frame()`, then executes the issued `GgrsRequest` in their order. `AdvanceFrame` contains each player's input and the status of `Confirmed`, `Predicted` or `Disconnected`. The command FIFO ACK or the number of milliseconds between messages does not, by itself, assign a game frame. [GGPO input synchronization](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#synchronizing-local-and-remote-inputs), [GGRS main loop](https://github.com/gschup/ggrs/blob/main/docs/main-loop.md), [GgrsRequest](https://docs.rs/ggrs/0.13.0/ggrs/enum.GgrsRequest.html), [InputStatus](https://docs.rs/ggrs/0.13.0/ggrs/enum.InputStatus.html).

At the game level, you need to have a pure operation of the form `advance(state, inputs_for_frame) -> state`. Its result should depend only on the saved state and the assigned block inputs. Save/load must cover **all gameplay state**, including tick, RNG state, decision order and entity spawning/removal. GGRS leaves the implementation of `Config::{Input, State, Address}` and handling of saving, loading and one simulation step to the application; Game inputs are transmitted, not the full state of the world. [GGRS setup](https://github.com/gschup/ggrs/blob/main/docs/setup.md), [GgrsRequest API](https://docs.rs/ggrs/0.13.0/ggrs/enum.GgrsRequest.html).

For the Area/projectile scenario, rollback closure is not only the Transform of the projectile. This includes all positions and lives of potential targets, players and their framed inputs, auto-fire cooldown/weapon, projectile birth/velocity/lifetime/team/owner, pierce and visited targets, AoE/status/damage state, slot or generation identity and RNG. If you exclude a condition that could change the hit recipient, replaying the frame will not reproduce the same conflict. GGPO separately lists shooter enemies, bullets, HP and score as part of state; `bevy_ggrs` restores entities and only registered components/resources. [GGPO state and inputs](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#game-state-and-inputs), [bevy_ggrs snapshot architecture](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#snapshot-storage).

### Three different "lags"

| Settings | What does it mean | Practical effect |
| --- | --- | --- |
| **Input delay `D`** | The input captured on frame `F` is applied to `F + D`. | Constantly adds control delay, but gives the packet time to arrive and reduces the rollback number. In GGRS default - `0`; documentation usually lists `2–4` frame as the tuning range. |
| **Max prediction window `P`** | The maximum frames by which a session can advance without a confirmed remote input. | Limits the depth of speculation and potential replay; when exhausted, the session waits/skips advancement. Default GGRS — `8`. `P=0` enables lockstep without rollback and can stop the game before input arrives. |
| **Observation/display delay** | Delayed display of the resulting image or interpolation buffer. | Shifts what the player sees; itself does not assign input to another simulation tick and is not an input delay. |

These are different axes: at 60 Hz `D=2` - about 33 ms of deliberate local input delay, and `P=8` - a limit of eight prediction frames, not eight frames of constant input latency. Current `COOP_PROJECTILE_DELAY_MS=800` - observation delay test; it is not equal to GGRS `with_input_delay`. [GGRS SessionBuilder](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_input_delay), [prediction window and lockstep](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_max_prediction_window), [local test contract](../examples/survivors/COOP.md#guest-input-response).

### Replay-safe presentation and determinism

Do not publish sound, screen flash, rewards, achievements or I/O directly inside a re-executed simulation step. GGPO advises separating game state from render state and deferring effects/sound until the end of rollback. GGRS marks frame inputs as speculative/confirmed; Bevy `Events<T>` does not have snapshots, so the library advises keeping gameplay events in a rollback component/resource and creating external events outside of `GgrsSchedule`. For a one-time presentation, use a stable event key (for example, frame + logical shot generation + target life + contact ordinal) and release/deduplicate only confirmed results. [GGPO render/effect guidance](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#separate-updating-game-state-from-rendering-in-your-game-loop), [GGRS InputStatus](https://docs.rs/ggrs/0.13.0/ggrs/enum.InputStatus.html), [bevy_ggrs event pitfall](https://github.com/gschup/bevy_ggrs/blob/main/docs/pitfalls.md#events).

Rollback requires the same result on all platforms and builds. GGRS specifically warns about floating-point differences between x86/ARM and Debug/Release, about unstable map/set iteration and RNG from system entropy; Recommends fixed-point/integer for sensitive game math, deterministic order, and RNG whose state is included in rollback. This is essential for our Bend `F32` and native/browser execution: float normalization after the JS boundary does not prove the same result for the entire simulation. [GGRS determinism requirements](https://github.com/gschup/ggrs/blob/main/docs/setup.md#determinism), [GGPO RNG/wall-clock guidance](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md#make-sure-your-game-state-advances-deterministically), [our current verification restrictions](../examples/survivors/COOP.md#checks).

## Price and limits with hundreds of entities

In normal mode, each GGRS frame requests state storage; rollback restores it and re-executes it to the current frame. By default, GGRS stores a ring buffer from `max_prediction_window + 1` state slots. `bevy_ggrs` snapshot stores values of registered types for rollback entities; `Clone` can allocate to each frame; the documentation calls `Reflect` the slowest option. Sparse saving reduces the number of save requests, but can increase the replay length. This means that the cost is determined by the bytes/types in the snapshot, the price of one full simulation tick, and the length/frequency of the rollback. [GGRS saved-state ring](https://github.com/gschup/ggrs/blob/v0.13.0/src/sync_layer.rs), [GGRS sparse saving](https://docs.rs/ggrs/0.13.0/ggrs/struct.SessionBuilder.html#method.with_sparse_saving_mode), [bevy_ggrs snapshot strategies](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#snapshot-strategies).

Hundreds of entities in and of themselves are not a promise of performance or a prohibition. If each repeated tick does `projectiles × targets` Area/contact checks, rollback will repeat this work. In our local profile there is a separate scenario of 100 projectiles × 400 targets = about 40,000 pairs per tick; This is a measurement of the current Bend combat forecast, **not** a GGRS measurement and not a rollback time prediction. We need a benchmark of the real state composition with the expected number of active enemies/projectiles and a correction window; There are no universal entity capacity or comparable GGRS figures in the upstream sources reviewed. [current contact profile](coop-combat-replay-cost.md).

## Is it suitable for our project?

- **GGPO:** good standard for minimal callback contract (`advance_frame`, save/load, `ggpo_synchronize_inputs`) and presentation separation. You will need a state serializer, identical fixed-step Bend simulation and C API integration; GGPO does not connect itself to Iroh or JS game worker.
- **GGRS:** A closer Rust option. Its `NonBlockingSocket` allows you to write a transport adapter, and the `wasm-bindgen` feature supports WASM. But this application must implement addressable exchange of discrete GGRS `Message`; The current Iroh adapter streams reliable messages and does not implement this interface. For browsers, upstream directly describes Matchbox as a ready-made WebRTC socket/signalling option. Adaptation of Iroh is possible only after a separate check of packet boundaries, ordering, buffering, pacing and loss/delay behavior. [GGRS custom socket](https://docs.rs/ggrs/0.13.0/ggrs/trait.NonBlockingSocket.html), [GGRS browser setup](https://github.com/gschup/ggrs/blob/main/docs/setup.md#feature-flags), [our Iroh transport boundary](../tools/iroh-transport/README.md).
- **bevy_ggrs:** the most ready Bevy way: plugin, `ReadInputs`, `GgrsSchedule`, registration of `Rollback` entities and each rollback component/resource. This is a useful example of recovering ECS identity and deterministic time. It does not integrate the current Bend world; compatible versions should be pinned as a set (on the reviewed matrix, release `bevy_ggrs 0.22` corresponds to Bevy `0.19` + GGRS `0.13.0`; upstream `main` showed another pair). [quickstart and matrix version](https://github.com/gschup/bevy_ggrs#bevy-ggrs), [rollback loop](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md#the-rollback-loop).

## Safe evaluation without transferring the game backend

1. First, repeat the selected pure Bend combat scenario from the general canonical anchor and inputs, including late host shot, Area, recycled shot/target slot and hit recipient. The current code already separates forecast from authoritative damage/rewards; The results of the time runs and their limitations are recorded in [hit study ](coop-projectile-visibility.md). JS test suites were removed by a parallel repository change; host remains the source of the result.
2. If you need to check the rollback model itself, make a small GGRS prototype only after selecting runtime/bridge for Bend state: `Config`, canonical save/load and `advance(state, inputs)`. Run GGRS `SyncTestSession` from `with_check_distance(...)`; it deliberately replays previous frames and compares the checksum. Then eliminate delays/losses in the P2P session and only after that remove the profiles of the full set of combat entities. Don't start with `bevy_ggrs` until the simulation actually lives in Bevy ECS. [GGRS SyncTest/debug guide](https://github.com/gschup/bevy_ggrs/blob/main/docs/debugging-desyncs.md#synctest-session), [GGRS `ex_game_p2p` loop](https://github.com/gschup/ggrs/blob/main/docs/main-loop.md#working-example).

No rollback transition is required just to improve the current synchronization. Maintaining the host authority and checking the full, consistent projectile/target forecast is a separate path with fewer changes than moving the entire game to a symmetric P2P rollback.
