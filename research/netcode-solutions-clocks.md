# Game clock, tick lead and interpolation in netcode

Reviewed **October 25, 2026** based on documentation and project sources. This is a help for browser co-op parallel fix; it is not a condition for continuing the main correction. The code, dependencies and game rules have not changed.

## Short conclusion

A useful model is to keep four values separate: **tick of the authoritative world**, **number of the executed command**, **local forecast cursor** and **playback time for the picture**. `seq` is responsible for command order and ACK; it doesn't prove how many world ticks the host has performed. The forecast should continue from the fresh world-tick anchor through inputs that have not yet been executed, and snapshots for the picture should be played on a separate timeline.

Unity Netcode for Entities shows tick lead with feedback from the server and smooth adjustment of client speed; Photon Fusion separates the input buffer, resimulation constraint, and interpolation buffer; FishNet separately documents the synchronized tick, which can go backwards, and the monotonic `LocalTick`; Valve stores the state and selects it for a delayed presentation time. These are different parts of the solution; no library specifies our entire protocol.

## Formulas and guards for transfer

Let `T = 1000 / tickRate` milliseconds per tick. The initial stock of client lead can be estimated as

```text
leadTicks = clamp(minLead, maxLead,
                  ceil((oneWayDelayQuantile + hostScheduleMargin) / T))
```

To offset to the network timeline, use a pair of fresh server anchor and local monotonic receive time: `estimatedServerTick = snapshot.worldTick + (nowMono - receivedAtMono + oneWayDelayEstimate) / T`. If only RTT is measured, `oneWayDelayEstimate ≈ RTT / 2` is a starting estimate assuming a roughly symmetrical path, not a guarantee. The required quantile in the lead formula is taken from the actually measured delay of the command/packet with jitter. It is better to additionally take into account the feedback from host: `arrivalMargin = intendedWorldTick - hostWorldTickAtReceive`. This is closer to NFE/Fusion than constantly recalculating the lead from one `Setup` RTT. Set limit `maxLead` and maximum predicted/replay ticks per frame; after reaching the limit, choose input delay or an explicit late input policy, rather than endlessly increasing the history. This calculation goes to world ticks; do not subtract browser `performance.now()` number directly from server timestamp with different origin.

For each session, store at least `{epoch, observationSeq, worldTick, lastExecutedSeq}`. Inside the epoch, the accepted authoritative `worldTick` and cumulative `lastExecutedSeq` do not decrease. ACK must identify the **executed** prefix and include the world tick at which the host executed it; transport FIFO, the received-message number and `lastSeq` do not by themselves define world time. Discard or separately process a snapshot delivered late with a smaller world tick. If the tick is the same, revision/ordering is needed for changes at this step.

When accepting a new anchor, restore the canonical state to `worldTick = A` and replay exactly the ticks of `A+1 … predictedCursor`, removing from the ledger only commands confirmed by `lastExecutedSeq`. Do not shift cursor by ACK amount or reapply timing of pending commands. For cooldown, store end tick/effect time on world timeline; for the visual age of the projectile, use its `birthTick` and presentation timeline. If a new anchor requires too long a replay, limit the work and explicitly resync, rather than submit the old world to cooldown as a fresh one.

The authoritative host remains the owner of the monotonous `worldTick`; RTT does not adjust the host clock. The client's time estimate can be brought to the anchor by small slew: limit `scaledDt = realDt * clamp(1 + k * error, 1 - ε, 1 + ε)`. A large reset is acceptable with a new `epoch` or after a registered resync. This is an engineering pattern, not an exact Unity/Fusion formula.

## Browser clock, suspend and server load

`performance.now()` — monotonic scale relative to the time origin of this global object; When using `Date.now()`, you can get a shift from the calendar correction. Window and Worker receive time origins at different times. The relative timestamps transferred between them must be normalized via `performance.timeOrigin` to a common scale or not compared directly. [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/#sec-time-origin) describes origins and monotony.

In one Window rAF callback receives the timestamp of the frame, and not the moment the handler is executed. It may be older than the `performance.now()` already read by the message handler. This means that even the timestamps of one origin cannot be assigned to a common `lastTime` in the order of callbacks without protection from rewind. Take delta from one watch owner; if you still mix sources in the same context - clamp `sample = max(sample, lastSample)`. [HTML animation-frame algorithm](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks) passes one frame timestamp to all callbacks of this update.

On resume after the hidden tab, do not give the minute `delta` to the accumulator. The standard allows throttling and complete stopping of timers in the background; The co-op's server browser host can actually stop the shared world. We need an explicit policy for visibility/resume: the host pauses the game/session on resync, and the client waits for a fresh anchor. Do not catch up with the background all the time without a limit. [HR Time](https://www.w3.org/TR/hr-time-3/#time-origin) says that throttling does not ruin the monotony of the clock, but it does not promise timely execution of callbacks.

60 Hz is a world ticks schedule, not a render-FPS promise. The client can show 30 FPS and take several fixed steps per frame if the execution budget allows. If the authoritative simulation does not keep up with the `T = 16.67 ms` on average, the wall-clock backlog will grow; tickrate by itself does not fix the problem. Limit catch-up per frame, measure the cost of a host tick and separately decide whether to slow down/pause the host or reduce the load. Don't throw away host ticks silently: this changes the game's cooldown and damage over time timings. FishNet explicitly separates tick rate from frame rate and documents dropping as protecting the client from the increasing number of simulations per frame.

## Reading and checking

Recommended reading order: (1) NFE 1.9.3 [time synchronization](https://docs.unity3d.com/Packages/com.unity.netcode@1.9/manual/time-synchronization.html) — prediction tick, interpolation tick and `TargetCommandSlack`; (2) Fusion [time synchronization](https://doc.photonengine.com/fusion/v2/manual/advanced/time-synchronization) — jitter quantiles, redundancy and input-delay budget; (3) FishNet [TimeManager](https://fish-networking.gitbook.io/docs/fishnet-building-blocks/components/managers/time-manager) — actual tick events, overload controls and the distinction between `Tick`/`LocalTick`; (4) Valve [interpolation source](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/interpolatedvar.h); (5) W3C specifications on browser clock origins and rAF timestamps.

For our case, we need easy scripts for time behavior, not a new SDK:

- A package of several FIFO commands: ACK confirms the executed prefix, and host worldTick is incremented independently; no replay one input tick twice.
- A Snapshot delivered **800 ms later** than a more recent one has the old `worldTick`: it does not move the authoritative anchor back and does not run a cooldown on the old world.
- ACK/RTT jumps and then a new anchor arrives: `predictedCursor` remains limited and monotonous; replay does not add the pending tick again; projectile animation age does not jump to receipt-time.
- Submit a packet jitter/loss burst with a fixed p95/p99 or target delay and check the resim limit and the selected input-delay policy. Separately check RTT above `maxLead`.
- Run render 30/60/120 FPS, host simulation around and below 60 ticks/s, then hide the tab and resume after a few seconds. Check bounded catch-up, cooldown by world tick and consistent pause/resync behavior.
- Reproduce the order of `rAF(timestamp_old) → message(performance.now_new) → rAF(timestamp_old)` in one Window; separately exchange Window/Worker timestamps with different origins.
- In fake transport, set the delay with a deferred delivery queue, rather than blocking sleep/expensive serialization within the simulation. Record separately command sent, transport delivered, host admitted/executed, ACK and snapshot delivered; otherwise the test driver load will look like an input lag.

This is a reading of documents and suggested checks, not the result of running tests. RTT/2 is inaccurate for asymmetric networks; jitter-percentile requires sampling and a tail-risk policy. Increasing lead increases replay-cost and/or input delay; no library eliminates the CPU shortage of the host. Specific Unity/Fusion/FishNet APIs cannot be inserted directly into Bend/Iroh without moving to another runtime - their temporary contracts and checks are portable.
