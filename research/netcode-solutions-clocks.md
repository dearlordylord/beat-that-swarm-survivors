# Игровые часы, tick lead и интерполяция в netcode

Проверено **25 октября 2026** по документации и исходникам проектов. Это справка для параллельного исправления browser co-op; она не является условием для продолжения основного исправления. Код, зависимости и игровые правила не менялись.

## Короткий вывод

Полезная модель — держать раздельно четыре значения: **тик авторитетного мира**, **номер исполненной команды**, **курсор локального прогноза** и **время воспроизведения для картинки**. `seq` отвечает за порядок команд и ACK; он не доказывает, сколько world ticks host выполнил. Прогноз должен продолжаться от свежего world-tick anchor по ещё не исполненным входам, а снимки для картинки должны проигрываться на отдельном timeline.

Unity Netcode for Entities показывает tick lead с feedback от сервера и плавной коррекцией клиентской скорости; Photon Fusion разделяет входной буфер, ограничение повторной симуляции и буфер интерполяции; FishNet отдельно документирует синхронизированный tick, который может идти назад, и монотонный `LocalTick`; Valve хранит состояние и выбирает его на отложенное presentation time. Это разные части решения, ни одна библиотека не задаёт наш protocol целиком.

## Формулы и guards для переноса

Пусть `T = 1000 / tickRate` миллисекунд на тик. Начальный запас client lead можно оценить как

```text
leadTicks = clamp(minLead, maxLead,
                  ceil((oneWayDelayQuantile + hostScheduleMargin) / T))
```

Для offset к сетевому timeline использовать пару свежего server anchor и локального monotonic receive time: `estimatedServerTick = snapshot.worldTick + (nowMono - receivedAtMono + oneWayDelayEstimate) / T`. Если измерен только RTT, `oneWayDelayEstimate ≈ RTT / 2` — стартовая оценка при условии примерно симметричного пути, а не гарантия. Нужный quantile в формуле lead берётся из реально измеренной задержки команды/пакета с jitter. Лучше дополнительно учитывать обратную связь host: `arrivalMargin = intendedWorldTick - hostWorldTickAtReceive`. Это ближе к NFE/Fusion, чем постоянно пересчитывать lead от одного `Setup` RTT. Установить предел `maxLead` и максимум предсказанных/replay ticks на кадр; после достижения предела выбрать input delay или явную политику late input, а не бесконечно увеличивать историю. Это вычисление идёт в world ticks; не вычитать число browser `performance.now()` напрямую из server timestamp с другим origin.

Для каждой сессии хранить, как минимум, `{epoch, observationSeq, worldTick, lastExecutedSeq}`. Внутри epoch принятый authoritative `worldTick` и cumulative `lastExecutedSeq` не уменьшаются. ACK обязан означать **исполненный** префикс и сопровождаться world tick, на котором host его исполнил; транспортный FIFO, номер принятого сообщения и `lastSeq` сами по себе не задают мир-время. Отбрасывать или отдельно обрабатывать snapshot, доставленный поздно с меньшим world tick. При одинаковом tick нужна revision/ordering для изменений на этом шаге.

При принятии нового anchor восстановить canonical state на `worldTick = A` и переиграть ровно ticks `A+1 … predictedCursor`, удалив из ledger только команды, подтверждённые `lastExecutedSeq`. Не сдвигать cursor на величину ACK или повторно применять время pending-команд. Для cooldown хранить end tick/время эффекта на world timeline; для визуального возраста снаряда использовать его `birthTick` и presentation timeline. Если новый anchor требует слишком длинный replay, ограничить работу и явно resync, а не подать старый мир на cooldown как свежий.

Авторитетный host остаётся владельцем монотонного `worldTick`; RTT не корректирует host clock. Клиентскую оценку времени можно подводить к anchor малым slew: ограничивать `scaledDt = realDt * clamp(1 + k * error, 1 - ε, 1 + ε)`. Большой reset допустим при новом `epoch` или после зарегистрированного resync. Это инженерный шаблон, не точная формула Unity/Fusion.

## Browser часы, suspend и серверная нагрузка

`performance.now()` — монотонная шкала относительно time origin данного global object; при использовании `Date.now()` можно получить сдвиг от календарной коррекции. Window и Worker получают time origins в разное время. Переданные между ними относительные timestamps нужно нормализовать через `performance.timeOrigin` к общей шкале или не сравнивать напрямую. [W3C High Resolution Time](https://www.w3.org/TR/hr-time-3/#sec-time-origin) описывает origins и монотонность.

В одном Window rAF callback получает timestamp кадра, а не момент выполнения обработчика. Он может быть старее `performance.now()`, уже прочитанного обработчиком сообщения. Значит, даже timestamps одного origin нельзя присваивать общему `lastTime` в порядке callback-ов без защиты от rewind. Брать delta из одного хозяина часов; если всё же смешивать источники в том же контексте — clamp `sample = max(sample, lastSample)`. [HTML animation-frame algorithm](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks) передаёт один frame timestamp всем callbacks этого обновления.

На resume после скрытой вкладки не отдавать минутный `delta` в accumulator. Стандарт допускает throttling и полную остановку таймеров в фоне; серверный browser host кооператива может фактически остановить общий мир. Нужна явная политика для visibility/resume: host ставит игру на паузу/сессию на resync, а клиент ждёт свежий anchor. Не догонять всё время фона без лимита. [HR Time](https://www.w3.org/TR/hr-time-3/#time-origin) говорит, что throttling не портит монотонность часов, но она не обещает своевременное выполнение callback-ов.

60 Hz — расписание world ticks, а не render-FPS обещание. Клиент может показывать 30 FPS и сделать несколько фиксированных шагов в кадре, если бюджет исполнения позволяет. Если авторитетная симуляция в среднем не успевает за `T = 16.67 ms`, wall-clock backlog будет расти; tickrate сам по себе проблему не исправляет. Ограничить catch-up за кадр, измерять стоимость host tick и отдельно решить, следует ли замедлить/поставить host на паузу или снижать нагрузку. Не выбрасывать host ticks молча: это меняет игровое время cooldown и периодического урона. FishNet прямо отделяет tick rate от частоты кадра и документирует dropping как защиту клиента от растущего числа симуляций за frame.

## Чтение и проверки

Рекомендуемый порядок чтения: (1) NFE 1.9.3 [time synchronization](https://docs.unity3d.com/Packages/com.unity.netcode@1.9/manual/time-synchronization.html) — prediction tick, interpolation tick и `TargetCommandSlack`; (2) Fusion [time synchronization](https://doc.photonengine.com/fusion/v2/manual/advanced/time-synchronization) — jitter-квантили, redundancy и input-delay budget; (3) FishNet [TimeManager](https://fish-networking.gitbook.io/docs/fishnet-building-blocks/components/managers/time-manager) — actual tick events, overload knobs и различие `Tick`/`LocalTick`; (4) Valve [interpolation source](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/interpolatedvar.h); (5) спецификации W3C про browser clock origin и rAF timestamp.

Для нашего случая нужны лёгкие сценарии по поведению времени, не новый SDK:

- Пакет из нескольких FIFO-команд: ACK подтверждает исполненный префикс, а host worldTick увеличивается независимо; нет replay одного input tick дважды.
- Snapshot, доставленный на **800 ms позже** более свежего, имеет старый `worldTick`: он не передвигает authoritative anchor назад и не запускает cooldown по старому миру.
- ACK/RTT скачет, а затем приходит новый anchor: `predictedCursor` остаётся ограниченным и монотонным; replay не прибавляет pending tick повторно; projectile animation age не прыгает к receipt-time.
- Подать packet jitter/loss burst с фиксированным p95/p99 или целевой задержкой и проверить предел resim и выбранную input-delay политику. Отдельно проверить RTT выше `maxLead`.
- Запустить render 30/60/120 FPS, host simulation около и ниже 60 ticks/s, затем скрыть вкладку и возобновить через несколько секунд. Проверить bounded catch-up, cooldown по world tick и согласованное pause/resync поведение.
- Воспроизвести порядок `rAF(timestamp_old) → message(performance.now_new) → rAF(timestamp_old)` в одном Window; отдельно обменять timestamps Window/Worker с разными origins.
- В fake transport задавать задержку очередью отложенной доставки, а не блокирующим sleep/дорогой сериализацией внутри симуляции. Записывать отдельно command sent, transport delivered, host admitted/executed, ACK и snapshot delivered; иначе нагрузка test driver будет выглядеть как входной лаг.

Это чтение документов и предлагаемые проверки, не результат исполнения тестов. RTT/2 неточен для асимметричных сетей; jitter-percentile требует выборки и политики tail-risk. Увеличение lead повышает replay-cost и/или input delay; ни одна библиотека не убирает нехватку CPU у host. Конкретные Unity/Fusion/FishNet API нельзя вставить напрямую в Bend/Iroh без перехода на другой runtime — переносимы их временные контракты и проверки.
