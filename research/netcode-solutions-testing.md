# Ready-made network time, replay and hit checks

Retrieved October 25, 2026 from official guides, APIs and sources. This is a review of reused test recipes for browser-host/Iroh, not a proposal to change the stack, nor a fix blocker. The current example uses the browser-based Iroh relay; details of the local link are recorded in [transport README](../tools/iroh-transport/README.md) and [COOP.md](../examples/survivors/COOP.md).

## Short answer

One network simulator is not enough. It delays or loses **packets**; it does not prove that the command was applied on the specified `worldTick`, the cooldown passed through every missed simulation, the bullet projectile retained its logical identity, or the client showed exactly the AoE hit that the host confirmed. The robust set consists of Bend transition checks, repeatable delivery schedule simulations, and a small browser run of real vehicles.

## What off-the-shelf tools really test

| --- | --- | --- |
| [Unity Multiplayer Tools 2.1.0: Network Simulator](https://docs-multiplayer.unity3d.com/tools/2.1.0/tools-network-simulator/) + [Unity Transport 2.0.0: SimulatorPipelineStage](https://docs-multiplayer.unity3d.com/transport/2.0.0/pipelines/) | Simulates delay, jitter, loss and send/receive direction; The script SDK can enable lag spikes/disconnect. | The parameters are sent via UTP. Tools documentation is marked archived; The simulator does not control the application `targetWorldTick`. This is a sample script, not a ready driver for Iroh. |
| [Unreal Engine 5.8: Network Emulation](https://dev.epicgames.com/documentation/unreal-engine/using-network-emulation-in-unreal-engine) and [NetcodeUnitTest](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetcodeUnitTest) | For a separate server/client path, incoming/outgoing lag and loss, packet reorder/duplicate are configured; commandlet runs netcode unit tests with a lightweight client. | Checks Unreal NetDriver and the game code around it. Does not cover browser event loop, Bend adapter or Iroh. [Network Prediction API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction) describes rollback services, not proof of the entire game simulation. |
| [GGRS 0.13.0 `SyncTestSession`](https://docs.rs/ggrs/0.13.0/ggrs/struct.SyncTestSession.html) | Each player provides a local input; the session saves the state, takes a step, rolls back to `check_distance`, plays back the frames and compares the checksum. Tests the determinism of re-execution. | The API itself says directly: there is no network, all players are local. Does not check for delays, delivery misses, browser clock, host/client transport or incomplete snapshots. |
| [Lightyear 0.31.0 `ClientServerStepper`](https://github.com/cBournhonesque/lightyear/blob/8a926d6fece6a0cf04c2747de90c01258524fe0d/crates/tests/src/stepper.rs), [prediction rollback tests](https://github.com/cBournhonesque/lightyear/blob/8a926d6fece6a0cf04c2747de90c01258524fe0d/crates/tests/src/client_server/prediction/rollback.rs), [pre-spawn tests](https://github.com/cBournhonesque/lightyear/blob/8a926d6fece6a0cf04c2747de90c01258524fe0d/crates/tests/src/client_server/prediction/prespawn.rs) | In the initial test harness there are separate Bevy Apps client/server, controlled by frame/tick steps, and IO options Crossbeam, UDP, WebTransport. There are specific checks for restoring state during rollback and distinguishing between pre-spawn entities. [LinkConditionerConfig](https://github.com/cBournhonesque/lightyear/blob/8a926d6fece6a0cf04c2747de90c01258524fe0d/crates/io/link/src/conditioner.rs) adds inbound latency/jitter/loss. | This is test code inside Lightyear, not an independent library for Bend. Random conditioner is useful for degradation, but does not replace the seed record + exact delivery scenario: the implementation selects `rand::rng()` without the seed parameter. Stepper and a separate event queue can be transferred as a template. |
| [Linux `tc-netem`](https://man7.org/linux/man-pages/man8/tc-netem.8.html) | Emulates delay/jitter, loss, duplicate, corruption, reorder and rate on the selected network interface; Suitable for checking the real network path without changing the transport. | These are IP packets of a specific interface, not game tick or processing time. For our browser/Iroh case, qdisc on the browser interface affects packets to the remote relay. It does not affect `keydown`, Worker/`postMessage`, Bend step or watch release delay. Two tabs of one host share the interface, CPU and test driver; these are not two independent networks. Separate paths require separate machines or isolated network namespaces/veth with directions configured. |

For browser harness [Playwright BrowserContext](https://playwright.dev/docs/browser-contexts) gives isolated sessions within one browser process and is suitable for host + guest. This is isolation of cookies/storage, not physical interfaces. Contextual [route API](https://playwright.dev/docs/api/class-browsercontext) manages browser requests; use it as an application driver, and set Iroh network conditions at the transport/OS level. The conclusion about contexts and the general machine follows from the described Playwright model; it should not be passed off as a WAN test.

## Check Matrix

First, drive cheap repeatable strings; then - real browser tabs and, if necessary, `netem`. In each recording, save a seed and an abbreviated reproducible trace.

| Contract/auditable trace | Minimal script and strong oracle | Suitable layer |
| --- | --- | --- |
| **Monotonic hours and samples order** | Give `performance.now()` sample, then deliver the previously taken rAF timestamp; check that the cursor/accumulator has not retreated and the world tick has not been executed twice. In trace, save the sample source, `timeOrigin`, collection time and delivery time. `performance.now()` is monotonous in its time origin; frame timestamp is a frame sample, not the callback execution time ([W3C HR Time 2026 WD](https://www.w3.org/TR/2026/WD-hr-time-3-20260225/), [HTML animation-frame callbacks](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks)). | Pure clock/queue laws + browser schedule test; Window/Worker relative clocks are normalized only with an explicit time origin. |
| **Fixed world tick, gaps and late input** | For commands `seq=10@tick=40`, `seq=11@41`, delay the second one, advance the host to 42, deliver it after 43. Oracle: tick 41 executed neutrally, late 41 clearly rejected; it cannot be used discreetly in 43. Rearrange/duplicate messages and leave input `targetWorldTick` unchanged. FIFO preserves the order of delivery, but does not itself preserve game time. | Bend law and property trace; additional in-memory queue on `deliverAt` for reproducible reorder/drop. `netem`/SDK simulator - late integration layer. |
| **Rewind/replay and canonical convergence** | After the new authoritative anchor, recalculate the entire suffix: every world tick, including neutral hole, cooldown, spawn and all known events. For one anchor + one tick-indexed input/event trace, repeated execution should give the same canonical state/hash and the same ordered event stream. GGRS `SyncTest` is a useful example of checksum after rewind/replay, but it excludes the network. | Law for Bend fold/transition + deterministic replay runner. Separately compare the authoritative host snapshot after the actual delivery. |
| **Projectile birth and reuse slot** | Multiple births on one physical slot, then reuse after despawn; check the logical key `{owner,birthTick,weapon,volleySlot}` and visual age/generation separately. The old contact/correction cannot be attributed to the new projectile; new birth has age 0. | Pure identity law/property trace and runtime renderer assertion on the same key. |
| **Predicted AoE/impact vs. confirmed hit** | For a fixture with a full set of causal inputs, check not “each witness is valid in itself,” but the full host event tuple on one tick: `{worldTick,shotId,targetId,impactOrder}` (for AoE - recipient set; for pierce - ordered hits). Compare with a run from the same canonical anchor. An unknown future remote input should be marked unknown and verified after host confirmation/correction, rather than requiring its prediction in advance. | Differential replay Bend vs host trace + browser-visible confirmed-hit assertion. The fact that all the calculated witnesses are valid does not prove that among them there is a target that the host actually hit. |
| **Piercing and remote-weapon dependencies** | In the pending horizon, the remote player has a known weapon state/aim/input and the next shot has not yet been born in the old anchor. Enable this known shot during replay: check the target's life/HP, contact order, visited set and the rest of the pierce against the host trace. This case catches "future known host shot missed, dead target remained alive, next projectile received a different pierce." Mark the unknown future remote input as unknown, do not pretend that it is recoverable. | Scenario replay and exact event diff; proof is possible only for a given complete dependence of inputs, not for hidden input. |
| **Two real browser peers and driver latency** | Host + guest in two Playwright contexts via real relay. For one command id, collect locally: sampled → assigned target tick → send requested → host receive → applied tick → ACK received; separately measure the drawn/captured observation. Compare capture off/on and regular/loaded harness. Buffer small numeric records, unload after run. | End-to-end browser smoke; next to it is OS `netem` or a second physical client. RTT is measured in hours of one client tab; host processing duration — host clock, do not subtract unsynchronized clocks. |
| **Deterministic replay, fuzz and mutation** | Generate limited traces `input/drop/delay/duplicate/reorder/snapshot/pause/slot reuse`, save seed and minimized failure. Mutate pass neutral tick, "late → current tick", skip future known bullet, slot as ShotId, pierce/order and oracle only `witness exists`; every semantic error should break a specific test. | [fast-check](https://fast-check.dev/docs/introduction/what-is-property-based-testing/) generates and shrinks inputs; [model-based tests](https://fast-check.dev/docs/advanced/model-based-testing/) save replay seed/path. [Stryker](https://stryker-mutator.io/docs/) verifies that tests detect changed logic. This is a search for counterexamples/test quality, not a universal proof. |

A practical measurement trap: **800 ms of observation delay is not 800 ms of input latency**. The timestamp refers to a specific stage (input sample, Iroh send, host receive, applied tick, snapshot receive, observer dump). A heavy probe, serializing each frame, waiting for a test driver, or a busy main thread can increase the distance between these stages and look like a network. First measure zero-network-delay and capture-off baseline; Don't attribute the entire elapsed interval to the Iroh path.

## What can be proven in Bend, and what remains runtime

If the functions and prerequisites are included in the Bend model being tested, it is possible to prove for all its inputs: the order and ACK of exactly the executed tick; neutral holes and refusal to use late input; replay from anchor every tick; unique shot identity upon reuse; order of contacts, recipients and pierce for a given geometry/set of events. Property/fuzz tests are useful for finding short inconsistent traces and testing borderline combinations. Mutation tests confirm that the selected oracle responds to known incorrect variants.

This **does not prove the entire network client**. Browser issuance/delivery of clock samples, Worker scheduling, Playwright driver, Iroh/QUIC/relay, batch processing and a specific adapter to the host world require runtime checks. Even a proven prediction cannot know another player's future unsubmitted input. Therefore, the confirmed host event must be compared with the trace on the common canonical timeline, and unknown dependencies must be shown explicitly.
