# Готовые проверки сетевого времени, replay и попаданий

Проверено 25 октября 2026 по официальным руководствам, API и исходникам. Это обзор переиспользуемых тестовых рецептов для browser-host / Iroh, не предложение менять стек и не блокер исправления. Текущий пример использует браузерный Iroh relay; детали локальной связки записаны в [транспортном README](../tools/iroh-transport/README.md) и [COOP.md](../examples/survivors/COOP.md).

## Короткий ответ

Одного сетевого симулятора недостаточно. Он задерживает или теряет **пакеты**; он не доказывает, что команда применена на указанном `worldTick`, cooldown прошёл через каждую пропущенную симуляцию, пул-снаряд сохранил логическую личность, или клиент показал именно тот AoE hit, который подтвердил хост. Надёжный набор состоит из проверок Bend-переходов, повторяемого моделирования расписания доставки и небольшого браузерного прогона настоящего транспорта.

## Что действительно проверяют готовые инструменты

| --- | --- | --- |

Проверяет детерминизм повторного исполнения. | Сам API прямо говорит: сети нет, все игроки локальны. Не проверяет задержки, пропуски доставки, browser clock, host/client transport или неполные snapshots. |

Stepper и отдельная очередь событий можно перенести как шаблон. |
| [Linux `tc-netem`](https://man7.org/linux/man-pages/man8/tc-netem.8.html) | На выбранном сетевом интерфейсе эмулирует delay/jitter, loss, duplicate, corruption, reorder и rate; годится для проверки настоящего сетевого пути без замены транспорта. | Это IP-пакеты конкретного интерфейса, не игровой тик и не время обработки. Для нашего browser/Iroh случая qdisc на интерфейсе браузера воздействует на пакеты к удалённому relay. Он не воздействует на `keydown`, Worker/`postMessage`, Bend step или задержку снятия наблюдения. Две вкладки одного хоста делят интерфейс, CPU и test driver; это не две независимые сети. Для браузерного harness [Playwright BrowserContext](https://playwright.dev/docs/browser-contexts) даёт изолированные сессии внутри одного browser process и подходит для host + guest. Это изоляция cookies/storage, не физических интерфейсов. Контекстный [route API](https://playwright.dev/docs/api/class-browsercontext) управляет запросами браузера; используйте его как драйвер приложения, а сетевые условия Iroh задавайте на транспортном/ОС-уровне. Вывод о контекстах и общей машине следует из описанной модели Playwright; его не следует выдавать за WAN-тест.

## Матрица проверок

Сначала гонять дешёвые повторяемые строки; затем — реальные браузерные вкладки и, по необходимости, `netem`. В каждой записи сохранять seed и сокращённый воспроизводимый trace.

| Контракт / проверяемый trace | Минимальный сценарий и сильный oracle | Подходящий слой |
| --- | --- | --- |
| **Монотонные часы и порядок samples** | Дать `performance.now()` sample, затем доставить ранее снятый rAF timestamp; проверить, что cursor/accumulator не отступил и мировой тик не исполнился дважды. В trace сохранять источник sample, `timeOrigin`, время съёма и время доставки. `performance.now()` монотонен в своём time origin; timestamp кадра — sample кадра, а не время выполнения callback ([W3C HR Time 2026 WD](https://www.w3.org/TR/2026/WD-hr-time-3-20260225/), [HTML animation-frame callbacks](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks)). | Pure clock/queue laws + browser schedule test; Window/Worker относительные часы нормализовать только с явным time origin. |
| **Фиксированный world tick, дыры, опоздавший ввод** | Для команд `seq=10@tick=40`, `seq=11@41`, задержать вторую, продвинуть хост до 42, доставить её после 43. Oracle: tick 41 исполнен нейтрально, поздний 41 явно отклонён; его нельзя незаметно применить в 43. Переставить/дублировать сообщения и оставить input `targetWorldTick` неизменным. FIFO сохраняет порядок доставки, но сам по себе не сохраняет игровое время. | Закон Bend и property trace; дополнительная in-memory очередь по `deliverAt` для воспроизводимого reorder/drop. `netem`/SDK симулятор — поздний интеграционный слой. |
| **Rewind/replay и canonical convergence** | После новой authoritative anchor пересчитать весь suffix: каждый мировой тик, включая neutral hole, cooldown, spawn и все известные события. Для одного anchor + одного tick-indexed input/event trace повторное исполнение должно дать одинаковый canonical state/hash и такой же ordered event stream. GGRS `SyncTest` — полезный образец checksum после rewind/replay, но сеть он исключает. | Закон для Bend fold/transition + deterministic replay runner. Отдельно сравнить авторитетный host snapshot после фактической доставки. |
| **Рождение снаряда и reuse slot** | Несколько birth на одном физическом slot, затем reuse после despawn; сверить логический ключ `{owner,birthTick,weapon,volleySlot}` и отдельно visual age/generation. Старый contact/correction не может быть приписан новому снаряду; новая birth имеет возраст 0. | Pure identity law/property trace и runtime renderer assertion на том же ключе. |
| **Предсказанный AoE/impact против подтверждённого попадания** | Для fixture с полным набором причинных входов сверять не «каждый witness сам по себе допустим», а полный host event tuple на одном tick: `{worldTick,shotId,targetId,impactOrder}` (для AoE — recipient set; для pierce — ordered hits). Сравнить с прогоном от той же canonical anchor. Неизвестный будущий remote input помечать unknown и сверять после host confirmation/correction, а не требовать его предсказания заранее. | Differential replay Bend vs host trace + browser-visible confirmed-hit assertion. Факт, что все вычисленные witnesses валидны, не доказывает, что среди них есть цель, которую действительно задел хост. |
| **Pierce и зависимости удалённого оружия** | В pending horizon удалённый игрок имеет известное состояние оружия/aim/input и следующий выстрел ещё не родился в старой anchor. Включить этот известный shot при replay: проверить жизнь/HP цели, порядок контактов, visited set и остаток pierce против host trace. Этот случай ловит «будущий известный host shot пропущен, мёртвая цель осталась живой, следующий снаряд получил другой pierce». Неизвестный будущий remote input помечать неизвестным, не притворяться, что он восстановим. | Сценарный replay и exact event diff; доказательство возможно только для заданной полной зависимости входов, не для скрытого ввода. |
| **Два реальных browser peers и задержка драйвера** | Host + guest в двух Playwright contexts через настоящий relay. Для одного command id собирать локально: sampled → assigned target tick → send requested → host receive → applied tick → ACK received; отдельно измерять отрисованный/снятый observation. Сравнить capture off/on и обычный/нагруженный harness. Буферизовать малые числовые записи, выгружать после прогона. | End-to-end браузерный smoke; рядом с ним OS `netem` или второй физический клиент. RTT измерять часами одной клиентской вкладки; host processing duration — часами хоста, не вычитать unsynchronized clocks. |
| **Deterministic replay, fuzz и mutation** | Генерировать ограниченные traces `input/drop/delay/duplicate/reorder/snapshot/pause/slot reuse`, сохранять seed и minimised failure. Мутировать пропуск neutral tick, «late → current tick», пропуск будущей известной пули, slot как ShotId, pierce/order и oracle только `witness exists`; каждая смысловая ошибка должна ломать конкретный тест. | [fast-check](https://fast-check.dev/docs/introduction/what-is-property-based-testing/) генерирует и shrink-ит входы; [model-based tests](https://fast-check.dev/docs/advanced/model-based-testing/) сохраняют replay seed/path. [Stryker](https://stryker-mutator.io/docs/) проверяет, что тесты обнаруживают изменённую логику. Это поиск контрпримеров/качество тестов, не универсальное доказательство. |

Практический измерительный капкан: **800 ms задержки наблюдения — это не 800 ms input latency**. Временная метка относится к конкретному этапу (input sample, Iroh send, host receive, applied tick, snapshot receive, observer dump). Тяжёлый probe, сериализация каждого frame, ожидание test driver или занятая main thread могут увеличить расстояние между этими этапами и выглядеть как сеть. Сначала замерить zero-network-delay и capture-off baseline; не приписывать весь elapsed interval пути Iroh.

## Что можно доказать в Bend, а что остаётся runtime

Если функции и предпосылки входят в проверяемую Bend-модель, можно доказать для всех её входов: очередность и ACK именно исполненного tick; neutral holes и отказ от применения late input; replay от anchor через каждый tick; уникальность shot identity при reuse; порядок контактов, recipients и pierce для заданной геометрии/набора событий. Property/fuzz tests полезны для поиска коротких противоречивых traces и проверки пограничных комбинаций. Mutation tests подтверждают, что выбранный oracle реагирует на известные неправильные варианты.

Это **не доказывает весь сетевой клиент**. Браузерная выдача/доставка clock samples, Worker scheduling, Playwright driver, Iroh/QUIC/relay, пакетная обработка и конкретный adapter к host world требуют runtime-проверок. Даже доказанный прогноз не может знать будущий неотправленный ввод другого игрока. Поэтому подтверждённый host event надо сравнивать с trace на общей canonical timeline, а неизвестные зависимости показывать явно.

## Первые ссылки для чтения

1. [GGRS SyncTest 0.13.0](https://docs.rs/ggrs/0.13.0/ggrs/struct.SyncTestSession.html) — простая точная модель «сохранить → шаг → rollback → checksum».
2. [Lightyear 0.31.0 stepper и rollback/prespawn tests](https://github.com/cBournhonesque/lightyear/tree/8a926d6fece6a0cf04c2747de90c01258524fe0d/crates/tests/src) — примеры контролируемого headless-порядка клиент/сервер и entity matching.
3. [tc-netem manual](https://man7.org/linux/man-pages/man8/tc-netem.8.html) — какие packet impairments реально задаются и ограничения порядка.
4. [High Resolution Time](https://www.w3.org/TR/hr-time-3/) и [HTML rAF](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#run-the-animation-frame-callbacks) — clock origin и смысл frame callback timestamp.
5. [Unity UTP Simulator](https://docs-multiplayer.unity3d.com/transport/2.0.0/pipelines/) / [Unreal Network Emulation](https://dev.epicgames.com/documentation/unreal-engine/using-network-emulation-in-unreal-engine) — настройки packet-level деградации в других движках.
