# Shots, contacts and rollback in SS14, Veloren and OpenRA

Checked **2026-10-25** from sources on recorded revisions: [Space Station 14 `0d9b3de`](https://github.com/space-wizards/space-station-14/commit/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b), its [RobustToolbox submodule `de49cf7`](https://github.com/space-wizards/RobustToolbox/commit/de49cf724f8d8f3afa5c8bb3aaa5331a4cfac3b4), [Veloren `c639f81`](https://github.com/veloren/veloren/commit/c639f81778d0df0eac6dfd463ffc3689e06b8df3) and [OpenRA `dbe6747`](https://github.com/OpenRA/OpenRA/commit/dbe674733305cd1ebe7bd03feed347b5c0da3c08). This is a code read, not a game launch or network test.

## What the sources confirm

### Space Station 14 + RobustToolbox: local response, server shot

The client `RequestShootEvent` carries the weapon, coordinates/target and continuous fire flag, but not the game tick ([event type ](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Weapons/Ranged/Events/RequestShootEvent.cs#L6-L31)). RobustToolbox stores the current `GameTick`; `RaisePredictiveEvent` sends a message to the server and re-raises it locally when replaying the predicted tick ([interface](https://github.com/space-wizards/RobustToolbox/blob/de49cf724f8d8f3afa5c8bb3aaa5331a4cfac3b4/Robust.Shared/GameObjects/IEntityManager.cs#L17-L22), [contract predictive event](https://github.com/space-wizards/RobustToolbox/blob/de49cf724f8d8f3afa5c8bb3aaa5331a4cfac3b4/Robust.Shared/GameObjects/IEntityManager.cs#L273-L276)). The client shooting system triggers the request only on the first tick simulation, and the predicted `Shoot` gives muzzle flash, sound and recoil; it does not fire the projectile on collisions ([client input](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Client/Weapons/Ranged/Systems/GunSystem.cs#L167-L224), [local response](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Client/Weapons/Ranged/Systems/GunSystem.cs#L227-L285)).

The server accepts the request, checks the attached player and weapon ownership, then applies a cooldown from its `Timing.CurTime` ([handler and cadence](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Weapons/Ranged/Systems/SharedGunSystem.cs#L143-L160), [cooldown](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Weapons/Ranged/Systems/SharedGunSystem.cs#L252-L307)). Only the server `GunSystem` creates spread bullets, sets their speed and arrow ([birth and volley](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Server/Weapons/Ranged/Systems/GunSystem.cs#L103-L198), [launch of projectile component ](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Weapons/Ranged/Systems/SharedGunSystem.cs#L444-L464)). The server-side `StartCollide` changes damage/health, penetration state and projectile removal; this is not client outcome prediction ([hit handling](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Server/Projectiles/ProjectileSystem.cs#L26-L100)).

Impact presentation is a separate network event: the client creates a short visual entity from lifetime to prototype or 0.5 seconds ([server event and client handler](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Server/Projectiles/ProjectileSystem.cs#L93-L99), [temporary impact visual](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Client/Projectiles/ProjectileSystem.cs#L14-L56)). The viewed event path does not contain shot/event ID and client dedupe set. And Robust rollback restores dirty **NetSync** components to the latest server state and removes some predicted spawn/component additions; this is not a magical rollback of an arbitrary local contact cache ([replay inputs/messages](https://github.com/space-wizards/RobustToolbox/blob/de49cf724f8d8f3afa5c8bb3aaa5331a4cfac3b4/Robust.Client/GameStates/ClientGameStateManager.cs#L553-L585), [rollback/reset components](https://github.com/space-wizards/RobustToolbox/blob/de49cf724f8d8f3afa5c8bb3aaa5331a4cfac3b4/Robust.Client/GameStates/ClientGameStateManager.cs#L610-L707)).

For portability, a limitation is important: SS14 `PenetrationThreshold` accumulates damage-required of destroyed entities; `ProjectileComponent` does not store a list of already affected target IDs ([penetration-model](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Projectiles/ProjectileComponent.cs#L90-L112)). Projectiles are normally removed after collision; the extracted embed can become dynamic again, and the code resets shooter/weapon/spent, but does not reset `PenetrationAmount` ([detach](https://github.com/space-wizards/space-station-14/blob/0d9b3de35f49ebecafc17af7de7bbec5775d8c0b/Content.Shared/Projectiles/SharedProjectileSystem.cs#L153-L175)). This penetration should not be considered a recipe for a finite number of hits on different targets.

### Veloren: explicit contact identity and separate beam semantics

The server creates each bullet as a new synced entity with projectile state ([`handle_shoot`](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/events/entity_creation.rs#L420-L457), [entity builder](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/state_ext.rs#L400-L426)). Projectile stores owner, lifetime, `pierce_entities` and `hit_entities: Vec<Uid>`; the new projectile constructor starts with an empty list ([component](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/src/comp/projectile.rs#L41-L73), [init](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/src/comp/projectile.rs#L365-L392)). On contact, the system discards a repeat of the same target for that projectile, writes the target to effects, and optionally denies other projectiles of the same owner from hitting for one second ([checks and writes hit identity](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/projectile.rs#L173-L239), [reset owner-history after a second](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/projectile.rs#L532-L537)). When timer is already zero, the system deletes the entity and performs timeout effects, then subtracts `dt` with saturation to zero; so the deletion occurs on the next pass after reaching zero ([check/delete/timeout](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/projectile.rs#L399-L405), [decrement](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/projectile.rs#L526-L529)). There is no projectile pool in the studied path: new entity/state, then delete or timeout.

Beam specifies another contract: at the boundary `tick_dur` clears the current `hit_entities`, saving the number of past intervals for target; inside the interval, the second hit of the same target is skipped ([reset and duration](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/beam.rs#L94-L103), [check and write](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/beam.rs#L173-L177), [adding successful contact](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/beam.rs#L347-L353)). This means that for Bend you need to choose the semantics explicitly: once per projectile, once per pulse/tick, or cooldown per target. `hit_entities` for bullet and contact memory beam are not interchangeable.

AoE works differently: `ExplosionEvent` bypasses living entities with Health, checks the radius/falloff and LOS in the world state when processing the event, then applies attack ([server resolver](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/events/entity_manipulation.rs#L1903-L1958), [applying effect](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/events/entity_manipulation.rs#L2033-L2045)). Recipient set is not built into `Explosion` - there are only effects, radius, reagent and falloff ([type](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/src/explosion.rs#L10-L26)). Under rollback, the set of goals can therefore become different: it must be recalculated according to the restored state, and not saved as a universal result of the old future.

Veloren runs common systems in both client and server, but `Projectile` is written among the server-local components ([common schedule](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/lib.rs#L24-L44), [component](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/state/src/state.rs#L361-L378)). Before network sending, the client sets its `Controller.inputs` and makes a local state tick, but projectile birth creates a server; the client then discards local `Outcome`, server outcomes are sent to subscribed clients ([input + send](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/client/src/lib.rs#L2272-L2300), [local outcomes discarded](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/client/src/lib.rs#L2369-L2375), [outcome sync](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/sys/entity_sync.rs#L478-L500)). This shows local input/character simulation, but not predicted remote bullet birth or authoritative client damage. `Outcome::ProjectileHit` carries source and target, but there is no separate projectile/event ID in the payload ([result type ](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/src/outcome.rs#L23-L51)).

Several remote controllers converge on one server step: the server increments `Tick`, accepts network inputs (handler updates `Controller.inputs`), then executes one `LocalState::tick` ([tick and order](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/lib.rs#L790-L794), [update controller](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/sys/msg/in_game.rs#L114-L119), [network before state step](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/server/src/lib.rs#L853-L883)). This gives the authoritative world a common tick for accepted inputs, but the input does not carry the historical `intendedTick`: these paths do not rollback to the sender's tick.

There is one more practical nuance: the contact loop iterates `physics.touch_entities`; this container is `HashMap<Uid, Vec3<f32>>` ([contact type](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/src/comp/phys.rs#L193-L211), [loop](https://github.com/veloren/veloren/blob/c639f81778d0df0eac6dfd463ffc3689e06b8df3/common/systems/src/projectile.rs#L117-L124)). There is no explicit tie-break for the order of concurrent targets. Bend should not borrow this order for finite pierce: maintain its sweep time and stable sorting by target/shot identity.

### OpenRA: tick agreement via lockstep

This is a useful architectural contrast, not ready-made real-time netcode. OpenRA processes orders from each client for the expected `NetFrameNumber`, checks the frame number and waits for a packet from all clients; after the frame sends sync hash ([frame orders and sync](https://github.com/OpenRA/OpenRA/blob/dbe674733305cd1ebe7bd03feed347b5c0da3c08/OpenRA.Game/Network/OrderManager.cs#L234-L284), [waiting for all peers](https://github.com/OpenRA/OpenRA/blob/dbe674733305cd1ebe7bd03feed347b5c0da3c08/OpenRA.Game/Network/OrderManager.cs#L300-L332)). Projectile moves to the game tick and launches weapon/warhead upon impact; `SpreadDamageWarhead` builds a radial list from the current world, checks validity and HitShape, then deals damage with falloff ([bullet tick/impact](https://github.com/OpenRA/OpenRA/blob/dbe674733305cd1ebe7bd03feed347b5c0da3c08/OpenRA.Mods.Common/Projectiles/Bullet.cs#L247-L260), [AoE recipient resolution](https://github.com/OpenRA/OpenRA/blob/dbe674733305cd1ebe7bd03feed347b5c0da3c08/OpenRA.Mods.Common/Warheads/SpreadDamageWarhead.cs#L56-L125)). All players converge through an agreed frame, not through a replay of the client world; the lagging peer delays the overall step.

## Recipe for Bend/browser host/Iroh - conclusions from these sources

```text
receive(cmd): log(commandSeq, intendedTick, receivedTick)
hostStep(T): validate commands[T]; apply cooldown/births; step world; resolve ordered contacts
guestPredict(T): predict own input; predict remote fire only when that fire for T is known
rollback(T): restore world + shots + target lives + cooldown/pierce/contact history; replay T..now
```

- `commandSeq` - delivery order/ACK, `intendedTick` and `appliedTick` - game meaning. The server callback or FIFO position by themselves does not set the tick of the shot. For SS14 it is significant that payload fire does not contain a tick, and the server cooldown uses its time; for Veloren, the client sends the current state of the Controller, whereas OpenRA explicitly numbers the frame.
- If the guest does not know the host's shot for tick `T`, the guest's hit/pierce is provisional only. A future host fire exception may leave the target mistakenly alive, changing the actual target of the next contact, and assigning the pierce to the wrong person. Do not turn such a forecast into canonical health.
- Separate `ShotId = (ownerLifeId, intendedTick, fireOrdinal)`, `HitId = (ShotId, targetLifeId, hitOrdinal-or-tick)` and `AreaPulseId = (ShotId, pulseOrdinal-or-tick)`. For AoE recipient set, calculate by world replay tick; The effect's dedupe key should not capture the old list of targets. For beam/pierce, restore per-target contact state along with snapshot.
- For immediate response, show muzzle/flash and ghost projectile to the owner; host confirms birth, trajectory and damage. Make a visual event idempotent by effect ID, do not hold its result in the gameplay state. When pool reuse, include generation in projectile ID and clear owner, cooldown, visited targets and effect keys.
- Local events that are executed repeatedly during rollback must be separated from the one-time presentation. In RobustToolbox, repeating predictive events is directly provided; SS14 limits some client effects to first prediction. Veloren, instead of trying to dedupe, now discards locally generated `Outcome`.

## Regressions for the current defect

1. Send a command earlier/later ACK with the same `intendedTick`: host cooldown and projectile birth must remain on the same world tick; change `intendedTick` with the same FIFO order - cooldown should change as expected.
2. Two shooters cross one target in one tick: change the delivery delay, saving the received ticks; check stable pin order, HP, death, target selection and pierce remainder.
3. Replay with a missing future host fire, which with host replay kills the target before the guest shot: the prediction may change, but the host state is ultimately the same; guest does not receive a permanent invalid target/pierce and does not show two confirmed impacts.
4. AoE at the border of the radius/LOS during rollback: move or kill the target in the replay state, reconfirm the recipient set and damage; visual explosion event show exactly once.
5. One high-pierce projectile crosses the same target a few ticks, then a new one; check the specified repeat-hit policy. Separately check the beam with hit-once-per-pulse and legal repetition in the next pulse.
6. An expired projectile slot is re-issued: the new generation does not inherit the visited target, owner cooldown, pierce or old dedupe key.
7. Drive the 800 ms observation delay separately from the command delay: record `clientCaptureTick`, `intendedTick`, `hostReceiveTick`, `hostAppliedTick`, `serverSnapshotTick`, `guestObservedTick`. This is an observational delay, not evidence of a command delay before it was applied.

**Transfer restrictions:** SS14 and Veloren in the considered battle paths are server-authoritative; SS14 penetration - damage/destruction, not hit counter on targets; Veloren does not demonstrate the rollback of the entire combat world and its outcome payload is not an idempotency protocol. OpenRA lockstep provides a clear tick agreement model, but waits for all peers and therefore can increase input latency. Portable ownership boundaries, tick ledger, per-shot/per-target identity and separate contact/area event semantics are not libraries and do not assume that the browser client knows the future of the host.
