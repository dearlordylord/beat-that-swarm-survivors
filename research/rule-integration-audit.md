# How laws connect to executable logic

## Conclusion

The project has several independent verification layers, but no single universal proof that every law of an isolated module is respected throughout the entire gameplay path. The kernel gate checks proofs of declared laws; the mutation gate checks that selected implementation changes break a named law; ECS types check system read/write permissions; integration checks exercise some real game functions and ECS paths. Together these layers provide useful confidence, but each answers a different question.

The main gap appears in reused-entity lifecycles: proving `newborn_payload_and_status` does not prove that the production caller passed a clean `Motion`. The caller currently passes `empty_motion()` explicitly, and a runtime regression exercises that route through game functions. Documentation accurately limits the formal guarantee to a small policy module and separately states that it does not cover every callsite or the complete ECS interpreter.

## What the gates actually check

[`scripts/check-bend-laws.py`](../scripts/check-bend-laws.py#L21) finds proof modules and, in its ordinary no-argument invocation, checks that each `*LAWS.bend` has a corresponding adjacent `*PROOF.bend` importing that exact laws file ([lines 26–39](../scripts/check-bend-laws.py#L26)). It then runs `bend ... --verdict` for each proof and accepts only a successful kernel verdict ([lines 60–77](../scripts/check-bend-laws.py#L60)). This ensures declared Bend laws have proofs accepted by the proof toolchain in use. The gate itself does not analyze the `game.bend` import graph or prove that the gameplay entry point calls the policy imported by a proof module.

[`scripts/check-bend-mutants.py`](../scripts/check-bend-mutants.py#L30) takes specific entries from `scripts/law-mutants/*.json`, copies sources into an isolated directory, applies the exact specified replacement, first requires the mutant to compile, then runs the proof and accepts only failure of the named law ([lines 35–70](../scripts/check-bend-mutants.py#L35)). This guards against some laws accidentally becoming ineffective or ceasing to detect a known bug. But if a proof imports a policy helper directly, a passing mutant test demonstrates law sensitivity to that helper, not the helper's connection to the production callsite. An exception is mutation of a compositional/public model that production itself calls, with the check additionally executing that production path.

[`capability-controls.test.py`](../examples/survivors/capability-controls.test.py#L31) checks positive/negative control pairs against actual game accessor functions: permitted reads compile, while writes through `Read` or access to another family must fail with a specific permission error ([lines 33–44](../examples/survivors/capability-controls.test.py#L33), [82–99](../examples/survivors/capability-controls.test.py#L82)). This is a real component-access boundary guarantee. It does not prove computed coordinates, health or lifecycle transitions correct, or guarantee that a policy was called.

## Example: spawning in a reused slot

The production path can be traced directly:

1. `game.bend` imports `spawn-policy.bend` as `S` and `spawn-lifecycle.bend` as `SL` ([imports](../examples/survivors/game.bend#L1)). `candidate_enemy` uses `S.admission` and retains the previous body on `Reject` ([lines 453–460](../examples/survivors/game.bend#L453)). The co-op check additionally accounts for all players and the predicted camera position ([lines 1557–1603](../examples/survivors/game.bend#L1557)).
2. In the ECS enemy query, the system reads `Body`, `Vitals`, `Status`, calls `party_update`, then passes the result through `team_spawn_gate` ([lines 1624–1648](../examples/survivors/game.bend#L1624)). `team_enemy_updated` computes a transition from previous/new `kind/age`, then calls `SL.route` ([line 1614](../examples/survivors/game.bend#L1614)).
3. A fresh result takes a separate branch: `SL.Fresh` bypasses contacts/effects from the previous lifetime, and `SL.newborn` receives `empty_motion()` ([lines 1608–1611](../examples/survivors/game.bend#L1608)). Then `write_row` writes new `Vitals` and `Status` into ECS ([lines 835–838](../examples/survivors/game.bend#L835)). The overall game sequence invokes the ECS plan through `team_execute`/`execute`, then `advance_raw_with`; native execution uses `G.advance_live_quiet` ([game loop](../examples/survivors/game.bend#L1725), [game loop](../examples/survivors/game.bend#L1743), [native caller](../examples/survivors/native.bend#L680)). The browser calls `advance_live` from emitted `game.mjs` ([browser caller](../examples/survivors/browser.mts#L386)).

Laws do verify part of this logic. In [`spawn-policy/LAWS.bend`](../examples/survivors/spawn-policy/LAWS.bend#L6), `admission_matches_geometry` relates the result of `admission` to predicate `admissible`, while `accepted_newborn_is_outside` proves an accepted point remains outside viewport exclusion after passing through `newborn` ([lines 92–103](../examples/survivors/spawn-policy/LAWS.bend#L92)). The proof uses the exact gate decomposition and the logical consequence of bounds ∧ outside ([proof](../examples/survivors/spawn-policy/PROOF.bend#L7)). However, `newborn_payload_and_status` only states that the generic helper returns the supplied `payload` and `cleanMotion` unchanged ([law](../examples/survivors/spawn-policy/LAWS.bend#L27), [proof](../examples/survivors/spawn-policy/PROOF.bend#L26)). It does not state that `cleanMotion` equals `empty_motion()`. This precisely illustrates the boundary between a helper proof and a wiring guarantee.

Executable checks cover some wiring. `coop-hit-source-check.mts` calls `Game.team_enemy_updated` with a previous dormant body, a fresh row and contaminated status; it expects preserved HP and zero `Motion`, then checks that an existing lifetime still receives the old contact ([test](../examples/survivors/coop-hit-source-check.mts#L224)). This exercises the actual gameplay lifecycle-call path, including selection of `SL.Fresh`, not just the generic helper. `check-coop-reliability.sh` recompiles `game.bend` and invokes this test against the freshly built game ([lines 21–24](../examples/survivors/check-coop-reliability.sh#L21), [37–39](../examples/survivors/check-coop-reliability.sh#L37)). The validation receipt additionally reports 148 stale-status/tower/boss/age-wrap scenarios, including actual ECS writes, and 5,590 live spawn transitions ([VALIDATION.md](../examples/survivors/VALIDATION.md#L242)). This is finite integration evidence, not a universal proof of all ECS transitions.

The spawn-policy laws are substantive about local geometry, but their names/formulas do not independently express an external game specification. For example, `admission_matches_geometry` compares two functions in one module; if `admissible` and the expected specification change together, the law remains provable. Viewport/raster geometry analysis and runtime fixtures provide a stronger external oracle here. Current mutation manifests also contain mutants for `prediction-spawn` and party spawn budget, but I found no entries directly mutating `spawn-policy.bend` or `spawn-lifecycle.bend`; the README describes historical rejected mutants with receipts stored outside the repository ([mutation gate scope](../scripts/check-bend-mutants.py#L30), [README](../examples/survivors/spawn-policy/README.md#L3)). The ordinary mutation gate therefore does not reproduce sensitivity checks of these lifecycle laws from current tracked manifests.

## Stronger composition example: co-op client delivery

Some policy modules have a more explicit compositional path. `coop-client-delivery.bend` imports `coop-input-flow.bend` and builds its public `enqueue` on `I.enqueue` ([import and call](../examples/survivors/coop-client-delivery.bend#L1), [lines 16–25](../examples/survivors/coop-client-delivery.bend#L16)). Its laws check public entry points as well as child functions: for example, rejection after failed transport, readiness of the combined ACK/input path and exact composition preparation. The mutation manifest changes these public-entry decisions and requires failure of the named law ([mutants](../scripts/law-mutants/client-delivery.json#L1)). The browser guest path calls exactly the compiled `ClientDelivery.enqueue`, `prepare`, `encode`, plus `complete/fail` after the I/O result ([browser wiring](../examples/survivors/coop-browser.mts#L343)). The freshly emitted module passes runtime checks for queues, batch bounds, codec and backpressure ([check](../examples/survivors/check-coop-reliability.sh#L22), [client delivery check](../examples/survivors/coop-client-delivery-check.mts#L17)). This is stronger than proving a helper without a public caller, although the runtime harness still tests finite scenarios rather than proving execution of every browser call or real-network quality.

## Suggestions for strengthening verification

- Express the business rule in a separate specification predicate, rather than merely calling the production predicate again. For spawning, the geometric integration oracle already partly does this; retain an independent level for viewport inclusion and boundary cases.
- Make clean spawning difficult to bypass through the API. For example, production-specific `fresh_enemy` could construct the initial `Body/Motion` pair itself, rather than having callers supply a value promised to be “clean.” The current generic `SL.newborn(payload, cleanMotion)` leaves that responsibility with the caller.
- Add a law/small kernel-friendly module for the specific production transition: `old Body + Status + updated Row -> Fresh/Existing result`, requiring zero status and bypass of old hits on Fresh. Then prove the ECS system calls precisely that transition, or enforce the call with a small source/wiring control. Proving the entire imported game previously exceeded the kernel CPU budget, so isolate a narrow orchestration function instead of importing all of `game.bend` into a proof.
- Add wiring mutants for important policy modules: mutate the game callsite to bypass a policy or pass a wrong argument, then require a narrow integration check to fail. Mutants inside a helper expose defects in a rule; wiring mutants address the separate question of integration.
- Preserve paired checks: a universal policy law, at least one runtime/integration fixture through the real production caller, and a mutation demonstrating that the fixture or law detects the expected regression class. Keep positive/negative capability controls separately for ECS authority; do not treat them as business-semantics checks.

This audit is based on source tracing and tracked validation records. Full gates and gameplay suites were not run as part of this audit.
