# AoE and projectile queries: ready-made patterns for the current Bend/Iroh example

Reviewed **October 25, 2026** using Box2D 3.2.0 sources (release October 19, commit `178495b`), Rapier 0.36.1 (October 4), versioned API Unity Physics 1.1 and Unity NetCode 1.0.12 plus package changelog available on the date of review. This is a study of algorithms and temporary contracts; the engine was not ported, performance measurements were not run.

## Short conclusion

We need two different indexings for one consistent simulation tick:

1. **Spatial:** for each projectile/AoE request, find a small conservative set of targets via BVH / dynamic AABB tree; then leave the current precise F32 narrow phase in authority.
2. **By recipient:** collect the found hit plans into a bucket by target ID, preserving the original ordinal of each plan. This removes `each enemy × all hit plans` without depending on the order in which the spatial query returned the candidates.

Scope note following the example: production [advance → recipient path](../examples/survivors/coop-combat-prediction.bend#L294) passes through `existing_enemies_cached` → `moved_enemy_recipients` → `recipient_hits_at`. For AoE, `recipient_hits_at` does one ordered scan of the plan list for each post-move enemy and calls the exact `G.hit_recipient` for its current body; the list preserves order and multiplicity. Therefore, the area path still linearly checks all plans for each enemy, but rejected plans are not included in the further hit/effect gather. Generic `recipient_hits()` with all plans returned is not this production path. For non-area plans, the ID map is used. In [broadphase candidate](../examples/survivors/coop-combat-broadphase.bend) AABBs are tested linearly; This is an unqualified candidate option, with no conclusion about latency or scaling benefits.

### Spatial query as next index

To remove the current `area plans × enemies` exact scan, build a spatial index over cached post-move bodies containing **the same coordinates, radii, filters and logical IDs** used by the existing `G.hit_recipient`. Then go through `HitPlan` in the same order: area plan requests geometric candidates; for each candidate the exact `G.hit_recipient` is still called; non-area plan uses the existing ID map based on explicit target IDs. The found pairs are grouped into `targetID → ordered HitPlan[]` or given the equivalent ordered recipient index. This is an algorithm proposal, not a description of the current production path. Geometric lookup eliminates impossible candidates; only narrow phase decides hit.

If query returns K candidate hits, further work depends on the geometric structure, density and number of actual hits; K in a dense AoE can still be `H_area×E` if every enemy needs to cast every pulse. This is an algorithmic scheme, not a productive measurement. Query-hit list cannot simply be mistaken for gameplay result: box/circle AABB overlap gives extra candidates that the current narrow phase should cut off.

It is important to keep F32 operations in their original sequence. In `game.bend` collision effects accumulate damage/knock/pull, select burn source if equal and then calculate new positions; rearranging the addition can change the F32 bits. Do not use traversal order BVH: store the original HitPlan ordinal inside each recipient bucket. For ballistic pierce, the exact function `Contact.sweep` remains oracle, and contacts are sorted by the existing `(time F32 bits, target seed)` comparator before spending pierce/life/visited; a limit on candidates cannot be introduced.

Repeated area pulse is a separate event on tick. Deduplication by `(shot,target)` only will break repeated damage. The event key must distinguish between shot life/generation, simulation tick, pulse ordinal and target life/ID. The spatial index and all recipient buckets should be rebuilt for the tick/world that is actually being checked; old BVH or hit plan cannot be applied to new canonical snapshot positions.

## Network timing and applicability to Bend/Iroh

The Unity pattern is only useful when the product rule says "check hit as the player saw the collision world on tick X". Then the query must explicitly select this tick, show/process the history clamp, and return an authoritative result on the current state. For host-authoritative rules, a simpler query is usually the canonical world/tick at which the host accepted the input. Mixing predicted projectile and remote target from another snapshot/tick does not become correct from the spatial index.

Bend can leave tree/grid, narrow-phase predicate, ordered buckets and differential laws as normal pure game data. The project recorded Bend 2.0.38 (`vendor/bendlib/toolchain.json`); his [pinned guide](https://github.com/bendlang/bend/blob/0a57ca0d21de94a3724d8be21afb0eb89f88b4d8/guide/GUIDE.md) describes fork-join calls to work independently, roughly equally, but explicitly says that the JavaScript target executes them sequentially. Therefore, you cannot promise to speed up browser physics through Bend parallel notation or consider the order of issuing a parallel query to be stable. Iroh remains the transport boundary from [`tools/iroh-transport/README.md`](../tools/iroh-transport/README.md); it does not specify geometry, collision truth, shot identity, or world history. None of the considered engines is a mandatory migration or a ready-made JS physics dependency.

## Regression recipes

1. **Broadphase superset:** on the same scenes brute-force `Contact.sweep` / `G.hit_recipient` and index path; every accurate hit must be among the candidates. An extra candidate is allowed up to the narrow phase, but an omission is not. Cover border touch, zero move, fast opposing movement, grazing, large/unsafe F32, various radii, NaN/Inf and fallback.
2. **Exact parity:** compare ordered contacts/witnesses and all state outputs: shot IDs/lives, hit target order, pierce, visited, hp/status/burn owner/killer, spawn/death/awards. For the deterministic F32 path, compare bit patterns, not just epsilon.
3. **Order perturbation:** change the order of insertion and traversal spatial index; after sorting by the canonical key, the result should be the same. Check for equal contact time, equal seed/duplicate IDs and finite pierce; tie policy should repeat the reference comparator.
4. **Repeat AoE:** one area weapon hits one target on adjacent ticks and several pulses of one tick; Each resolved event is applied exactly once, reuse storage slot does not mix lives.
5. **Stale world / lag compensation:** moving target passes through the beam between ticks; check the current world and the expected historical tick separately. Check history clamp, ring wrap, one-tick offset, distant target and static wall. Record the requested tick and the actual tick returned.
6. **World consistency:** broadphase and narrow-phase predicates must read the same target snapshot; place the target so old/current/predicted positions yield different answers, exposing accidental stale queries or mixed presentation/simulation timelines.
