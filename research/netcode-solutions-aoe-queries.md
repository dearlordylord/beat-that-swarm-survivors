# AoE и projectile queries: готовые паттерны для текущего Bend/Iroh примера

Проверено **25 октября 2026** по исходникам Box2D 3.2.0 (release 19 октября, commit `178495b`), Rapier 0.36.1 (4 октября), versioned API Unity Physics 1.1 и Unity NetCode 1.0.12 плюс changelog пакета, доступный на дату проверки. Это исследование алгоритмов и временных контрактов; движок не переносился, performance-замеры не запускались.

## Короткий вывод

Нужны две разные индексации на один согласованный simulation tick:

1. **Пространственная:** для каждого projectile/AoE запроса найти малый консервативный набор целей через BVH / dynamic AABB tree; затем оставить нынешний точный F32 narrow phase авторитетом.
2. **По получателю:** собрать найденные hit plans в bucket по target ID, сохранив исходный ordinal каждого плана. Это снимает `каждый enemy × все hit plans` без зависимости от порядка, в котором spatial query вернул кандидатов.

Scope note по примеру: production [advance → recipient path](../examples/survivors/coop-combat-prediction.bend#L294) проходит через `existing_enemies_cached` → `moved_enemy_recipients` → `recipient_hits_at`. Для AoE `recipient_hits_at` делает один ordered scan списка планов на каждого post-move enemy и вызывает точный `G.hit_recipient` для его текущего body; список сохраняет порядок и multiplicity. Поэтому area path всё ещё линейно проверяет все планы на каждого enemy, но отвергнутые планы не попадают в дальнейший hit/effect gather. Общий `recipient_hits()` с возвратом всех планов не является этим production path. Для non-area планов используется ID map. В [broadphase candidate](../examples/survivors/coop-combat-broadphase.bend) AABB проверяются линейно; это незаквалифицированный вариант-кандидат, без вывода о выигрыше latency или масштабировании.

### Пространственный query как следующий индекс

Чтобы убрать текущий `area plans × enemies` exact scan, можно строить spatial index по кэшированным post-move bodies, содержащим **те же координаты, радиусы, фильтры и logical IDs**, которые использует существующий `G.hit_recipient`. Затем идти по `HitPlan` в прежнем порядке: area plan запрашивает геометрических кандидатов; для каждого кандидата всё равно вызывается точный `G.hit_recipient`; non-area plan использует существующий ID map по явным target IDs. Найденные пары группируются в `targetID → ordered HitPlan[]` либо выдаются эквивалентным ordered recipient index. Это предложение по алгоритму, а не описание текущего production path. Геометрический lookup отсекает невозможных кандидатов; только narrow phase решает hit.

Если query возвращает K кандидат-попаданий, дальнейшая работа зависит от геометрической структуры, плотности и числа реально точных hits; K в плотном AoE всё ещё может быть `H_area×E`, если каждому врагу надо применить каждый pulse. Это алгоритмическая схема, не производительный замер. Query-hit list нельзя просто принять за gameplay result: box/circle AABB overlap даёт лишних кандидатов, которые должен отсечь текущий narrow phase.

Важно сохранять F32-операции в исходной последовательности. В `game.bend` collision effects накапливают damage/knock/pull, выбирают burn source при равенстве и затем вычисляют новые позиции; перестановка сложения может изменить F32 биты. Не использовать traversal order BVH: сохранять исходный HitPlan ordinal внутри каждого recipient bucket. Для ballistic pierce точная функция `Contact.sweep` остаётся oracle, а contacts сортируются существующим `(time F32 bits, target seed)` comparator до расходования pierce/life/visited; лимита на кандидатов вводить нельзя.

Повторный area pulse — отдельное событие на tick. Дедупликация только по `(shot,target)` сломает повторный урон. Ключ event должен различать shot life/generation, simulation tick, pulse ordinal и target life/ID. Пространственный индекс и все recipient buckets следует строить заново для того tick/world, который реально проверяется; старый BVH или hit plan нельзя применить к новым canonical snapshot positions.

## Время сети и применимость к Bend/Iroh

Unity pattern полезен только когда продуктовое правило говорит «проверить hit так, как игрок видел collision world на tick X». Тогда запрос должен явно выбрать этот tick, показать/обработать clamp истории и вернуть авторитетный результат на текущем состоянии. Для host-authoritative правил обычно проще query тот canonical world/tick, на котором host принял input. Смешение predicted projectile и remote target из другого snapshot/tick не становится корректным от spatial index.

Bend может оставить tree/grid, narrow-phase predicate, ordered buckets и differential laws обычными чистыми игровыми данными. В проекте зафиксирован Bend 2.0.38 (`vendor/bendlib/toolchain.json`); его [pinned guide](https://github.com/bendlang/bend/blob/0a57ca0d21de94a3724d8be21afb0eb89f88b4d8/guide/GUIDE.md) описывает fork-join calls для независимой, примерно равной работы, но явно говорит, что JavaScript target исполняет их последовательно. Поэтому нельзя обещать ускорение browser physics через Bend parallel notation или считать порядок выдачи параллельного query стабильным. Iroh остаётся transport boundary из [`tools/iroh-transport/README.md`](../tools/iroh-transport/README.md); он не задаёт geometry, collision truth, shot identity или историю мира. Ни один из рассмотренных движков не является обязательной миграцией или готовой JS physics зависимостью.

## Регрессионные рецепты

1. **Broadphase superset:** на одинаковых сценах brute-force `Contact.sweep` / `G.hit_recipient` и индексный path; каждый точный hit обязан быть среди кандидатов. Лишний кандидат допустим до narrow phase, пропуск — нет. Покрыть касание по границе, нулевой ход, fast opposing movement, grazing, большие/unsafe F32, различные радиусы, NaN/Inf и fallback.
2. **Точная parity:** сравнивать ordered contacts/witnesses и все state outputs: shot IDs/lives, hit target order, pierce, visited, hp/status/burn owner/killer, spawn/death/awards. Для deterministic F32-пути сравнить bit patterns, а не только epsilon.
3. **Order perturbation:** менять порядок вставки и обхода spatial index; после сортировки по каноническому ключу результат должен совпадать. Проверить равный contact time, одинаковые seed/duplicate IDs и finite pierce; tie policy должна повторять reference comparator.
4. **Повторный AoE:** одна area weapon попадает в одну цель на соседних ticks и несколько pulses одного tick; каждое разрешённое событие применяется ровно один раз, reuse storage slot не смешивает lives.
5. **Stale world / lag compensation:** движущаяся цель проходит через луч между ticks; отдельно проверить current world и ожидаемый historical tick. Проверить history clamp, ring wrap, one-tick offset, удалённую цель и статическую стену. Записывать requested tick и фактически возвращённый tick.
6. **Сверка мира:** предикат broadphase и narrow phase должны читать один снимок цели; поставить цель так, чтобы old/current/predicted позиции давали разные ответы, чтобы выявить случайный stale-query или смешение presentation и simulation timelines.
