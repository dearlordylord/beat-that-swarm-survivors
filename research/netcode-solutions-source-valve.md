# Source 1: Network Time, Projectiles and Burst Damage

Retrieved October 25, 2026. This is a study of the Valve Developer Community and the Valve Source SDK 2013 `master`; The studied files are available in the Valve repository, not in the Bendvy sources. We're talking about Source 1, not Source 2. The code was not transferred.

## Short output for our error

Source separates three things: the user command number/tick, the authoritative server tick, and the delayed display time of remote objects. In each server tick, commands, simulation and game rules are executed; the client smoothes the images by interpolation. For hitscan, Source can briefly restore **other players' history** around command time and then return them to their current state. This is not a rollback of the entire world or rewinding the flight of a projectile. [Source Multiplayer Networking](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking) review, [player history list ](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/player_lagcompensation.cpp#L221-L222), [player backtrack ](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/player_lagcompensation.cpp#L345-L437) and [their recovery ](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/player_lagcompensation.cpp#L768-L795).

In our case, this is a useful distinction: the confirmation/FIFO element number should not replace the world tick on which the host applied it. And the added **800 ms to the snapshot receipt** by itself does not mean that the guest's input arrived at the host with a delay of 800 ms. These are different directions and hours. The current local history of confirmed contacts also shows a separate reason for the incorrect target: the forecast did not include a future salvo from the host, who managed to kill the target and spend his own penetration before the contact of the guest’s shot. [Evidence of contacts](coop-projectile-visibility.md), [description of model co-op](../examples/survivors/COOP.md).

## What exactly does Source do?

**Command and world tick are different fields.** `CUserCmd` stores `command_number` for mapping/debugging and a separate `tick_count` - the tick on which the client created the command. The server itself runs `gpGlobals->tickcount`; The SDK implementation of lag compensation takes the outgoing latency, adds client interpolation, limits the correction to `sv_maxunlag` and checks the calculated tick with `cmd->tick_count`. This means that the number of the delivered/confirmed command is not equal to the world simulation time: a separate authoritative world tick of application is needed. [Fields `CUserCmd`](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/shared/usercmd.h#L136-L140), [command time calculation](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/player_lagcompensation.cpp#L345-L437). Valve stores lag-compensation history in an array of **player** records; this is not history for all entities. [Player history storage](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/player_lagcompensation.cpp#L221-L222).

**Hitscan is not a projectile.** Valve documentation says shot prediction can be combined with server-side lag compensation, but this usually applies to hitscan: a visible rocket or grenade appearing out of thin air to an observer looks wrong. [Valve: Authoring a weapon entity](https://developer.valvesoftware.com/wiki/Authoring_a_weapon_entity). In the original article, Yahn Bernier specifically explains that in Half-Life the projectile object itself was not lag-compensated; the sound of a gunshot can be locally predicted. Lag compensation hitscan - moving players back in time while the command is being processed, after which their positions are restored. [Yahn Bernier, primary article Valve Developer Community](https://developer.valvesoftware.com/w/index.php?title=Latency_Compensating_Methods_in_Client%2FServer_In-game_Protocol_Design_and_Optimization&uselang=en). Therefore, a predicted shot animation/birth should not automatically be considered a confirmed trajectory, hit, or damage.

**Explosion is a world event at the moment of detonation.** Example Source SDK: damage, radius and timer are set for a fragmentation grenade; when the timer expires, `Detonate()` is called. The general grenade code builds `CTakeDamageInfo` and calls `RadiusDamage` from the current position of the grenade with its radius; then the object becomes inert/deleted. [Frag grenade creation and radius](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/hl2/grenade_frag.cpp#L102-L135), [timer and detonation](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/hl2/grenade_frag.cpp#L291-L333), [explosion and radius damage](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/shared/basegrenade_shared.cpp#L112-L186). For RPG, the projectile triggers `Explode` on contact, creates a fixed radius explosion, and is removed; Before creating an explosion, the surface is checked so as not to explode on the skybox. [RPG missile: explosion/contact/removal](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/hl2/weapon_rpg.cpp#L341-L403). Hitscan shotgun, on the other hand, performs `FireBullets` inside the weapon's attack. [Shotgun `PrimaryAttack`](https://github.com/ValveSoftware/source-sdk-2013/blob/be57e3d01ac7d7aa6a2cacbfef187c0b46616db0/src/game/server/hl2/weapon_shotgun.cpp#L443-L473).

Portable contract for AoE: one result is tied to a specific explosion event/tick; a set of goals is selected based on one state of the world at the time of this event. Moving projectile contact also compares projectile and target on a common sweep tick/section. The player history for hitscan does not automatically provide a history of enemies, alien projectiles, or all blast recipients.

## What to Move to Bend + Iroh

Transport Iroh does not assign tee times. A reputable Bend host remains the only source of HP, death, pickup and rewards; A pure Bend model can simultaneously calculate a limited combat forecast for an immediate image. For each input, you should distinguish between its stable input ID/sequence and the world tick where the host applied it; the snapshot can separately report the last applied input ID and canonical world tick. This follows from the separation of the Source fields and coincides with the current Bend/browser boundary of the project; Switching to another engine or a complete rollback of the world does not follow from this.

For prediction, keep projectiles, enemies and all future automatic player volleys **derivable from known state** in one Bend scene at one combat tick. Reproducible volleys from observed loadout/cooldown/held-input can be enabled; the unknown future input change remains an inevitable uncertainty and is corrected according to the next authoritative snapshot. In the already recorded case, the host's volley kills the target before the guest's projectile: a forecast without this volley mistakenly leaves the target alive and wastes piercing on the wrong contact. This is particularly important because simple owner prediction works more easily with a clear object owner and a mostly static environment; our projectile interacts with a shared moving combat world. [Glenn Fiedler: Networked Physics](https://gafferongames.com/post/networked_physics_2004/). There is no need for a fictitious “lag compensation projectile” here: we need a known future contribution to the same predicted world and confirmation of the exact result of the host.

Keep snapshot display/interpolation and cosmetic effect age separate from the combat tick: the smoothed coordinate of a distant enemy should not quietly become a collision world. `+800 ms` for incoming observations and outgoing input delay are two independent scenarios. The result of the report does not change the current work on the main bug and does not suggest migration to Source.

## Regression ideas

1. **Queue and Clock:** The host advances the world for a few ticks with no input, then accepts a burst of sequential commands. Check the order of application, continuous world ticks and that ACK/receipt does not become a forecast tick; Save both counters in the snapshot.
2. **Host Future Barrage:** The observed target dies from the host's automatic barrage before the guest projectile makes contact. The guest projectile passes through it, saves pierce and hits the next target on the same authoritative tick. Repeat with reuse of the physical slot, but with different shot/target generations.
3. **Moving Target and AoE:** enemy crosses the sweep/radius border between shots; compare the target and projectile on the same tick/segment, record the contact point/time, recipient list, damage number and remainder of the pierce. The duplicate image does not repeat the one-time blast damage; periodic hits differ by tick.
4. **Separate delay and burst snapshots:** Separately delay only incoming observations by 800 ms, separately - sending input; separately deliver a bunch of pictures at the same time. In the first scenario, do not invent 800 ms input latency; in a burst scenario, do not accelerate projectile age by the number of incoming frames and do not pass off delayed/batch display as new world ticks. In the second scenario, check the actual accumulation/application of commands and the reconciled prefix.
5. **Prediction/confirmation:** a client spawn effect can appear immediately, but only the host confirms damage/death. With a known volley state, the effect is compared with the stable identity shot; an unknown future action is not reported as a confirmed hit.
