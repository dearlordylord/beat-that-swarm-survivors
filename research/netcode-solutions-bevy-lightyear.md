# Bevy/Lightyear: выстрелы, rollback и боевые зависимости

Проверено **25 октября 2026** по первичным источникам. Для кода зафиксирован официальный тег [Lightyear 0.30.0](https://github.com/cBournhonesque/lightyear/releases/tag/0.30.0) (`382e772`, выпущен 14 сентября 2026): в его manifest указаны Bevy 0.19, Bevy Replicon 0.44.1 и Avian 0.7 ([Cargo.toml](https://github.com/cBournhonesque/lightyear/blob/0.30.0/Cargo.toml#L199-L249)). Текущий README Replicon относит 0.45 к Bevy 0.20, поэтому отдельно обновить Replicon в этой связке нельзя без смены совместимой версии Bevy/Lightyear ([таблица совместимости](https://github.com/simgine/bevy_replicon#bevy-compatibility)). Книга Lightyear — рабочие заметки, не полная спецификация; ниже её утверждения проверены по тегированным примерам/API там, где это было возможно.

## Что относится к нашей ошибке

Главный практический пример — Lightyear `spaceships`: удалённый выстрел предсказывается **только если клиент уже получил его настоящий input для этого тика**. Текущую команду берут из `LeafwingBuffer[tick]`, проверяют, что `last_remote_tick >= tick`, и требуют предыдущий sample; firing/cooldown работает в `FixedUpdate`. Для cooldown сравнивают локальный `Weapon` с `ConfirmedHistory<Weapon>` и сохраняют `last_fire_tick` в предсказуемом состоянии. Пришедшие заранее удалённые inputs могут породить пулю до симуляции тика; если они запоздали, серверная пуля приходит обычной репликацией и клиент откатывается к корректному состоянию. Это прямо описано в [README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/README.md#predicted-bullet-spawning-and-input-delay) и реализовано в [`shared.rs`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L254-L471); отдельные тесты проверяют, что без remote input для требуемого тика выстрел не появляется ([тесты](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L803-L855)).

Для Bend это поддерживает нужное различие: **порядок ACK/доставки не задаёт world tick исполнения**. Lightyear привязывает `ActionState` к tick, записывает input в серверный буфер и обрабатывает его на соответствующем fixed tick; `FixedPreUpdate`/`InputSystems::WriteClientInputs` задаёт локальный sample, а симуляция читает его в `FixedUpdate`. `LocalTimelineSync` назначает tick с учётом input delay; whole-tick correction сдвигает вместе input, prediction и prespawn histories ([ticks и input schedules](https://cbournhonesque.github.io/lightyear/book/tutorial/basic_systems.html)). Это контракт «команда для T → симуляция T», а не гарантия, выводимая из FIFO ACK. Задержка наблюдения на госте в 800 мс не проверяет задержку input до допуска/исполнения у хоста: измерять отдельно `intendedTick`, `receivedTick` и `appliedTick`.

В `spaceships` предсказуемые пули — это не попытка угадать неизвестное будущее: все игроки дают inputs, сервер немедленно рассылает их, а при настроенном input delay удалённый input может прийти до симуляции своего тика. Если input отсутствует, система ждёт его для remote fire; позднее получение исправляется rollback/replay. Поэтому выстрел хоста, которого нет в истории гостя, не становится известным из ACK позиции или из детерминированного projectile-кода. Для piercing/AoE этот отсутствующий birth меняет набор живых целей и порядок расхода pierce — такой прогноз не может быть окончательным.

## Что действительно демонстрируют Bevy-примеры

### Предсказанное рождение и идентичность

В `spaceships` client/server используют одну fixed-tick firing-логику, `Weapon` с `last_fire_tick`, и детерминированную `PreSpawned` hash по `(owner, tick)`. `PreSpawned` сопоставляет самостоятельно созданные клиентскую и серверную сущности; документация уточняет, что компонент должен появиться в `FixedMain`, а его hash либо строится из tick/archetype, либо явно задаётся одинаковым на обеих сторонах ([API Lightyear 0.30.0](https://docs.rs/lightyear_replication/0.30.0/lightyear_replication/prespawn/struct.PreSpawned.html), [код стрельбы](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L254-L428)). Это механизм matching для spawn, **не** алгоритм, угадывающий remote fire и не долговечный ID каждого damage event.

Более широкий [projectiles demo](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L1-L49) позволяет независимо переключать траекторию, представление, hit policy и timeline (`Q/E/R/T`). Он сравнивает три представления: сущность с обновляемым состоянием, fire-data с tick/origin/direction для детерминированного восстановления и кольцевой shot buffer на 32 записи с монотонным `sequence`; последний обрабатывает reuse слотов и позволяет пометить авторитетный finish tick ([описание](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L24-L49), [ShotRecord и diff](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/representation/shot_buffer.rs#L37-L128)). Fire-data экономит сетевые обновления только для воспроизводимой траектории; пример прямо оставляет изменяемую физику, отскоки и homing для state entity. Для нескольких пуль одного владельца за тик hash должен включать ordinal: сам пример ограничивает себя одним выстрелом на игрока за tick и предупреждает о необходимости pellet ordinal для shotgun ([hash и оговорка](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/representation/mod.rs#L50-L80)).

### Prediction — явная выборка, не автоматический dependency closure

Lightyear записывает confirmed/prediction histories для зарегистрированных компонентов, а `PredictionTarget` выбирает, какие сущности предсказывает клиент. Несовпадение восстанавливается из confirmed state и fixed simulation переигрывает inputs до текущего tick; логика должна исполняться и на клиенте, и на сервере ([prediction tutorial](https://cbournhonesque.github.io/lightyear/book/tutorial/advanced_systems.html)). Это не документированный автоматический обход игровой причинности. В projectiles demo `AllPredicted` явно включает всех игроков и input rebroadcast, но комментарий к политике перечисляет недостающие/поздние remote inputs как причину correction и отдельно предупреждает: prediction движения само по себе не задаёт remote firing, collision или outcome ([политика](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/timeline/all_predicted.rs)). Его общий fire handler также предсказывает выстрел клиента-владельца, а для remote player ждёт authoritative projectile, даже в режиме `AllPredicted` ([`shoot_weapon`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/shared.rs#L203-L289)). Значит, «предсказывать всех игроков» не равно «включить все будущие remote weapon births».

Для проблемы с пирсингом closure пришлось бы определить от результата конкретного удара: положения и жизни снаряда, состояний и жизней целей, их spawn/despawn, cooldown/weapon state и **всех выстрелов, уже известных на этот tick**, которые способны раньше изменить HP/цель. Неизвестный будущий remote input нельзя получить из локального replay. Если полный набор причин не доступен, Lightyear-подобная архитектура оставляет damage/kill/pierce за хостом, а локальный hit/AoE — provisional presentation.

### Контакты, AoE и authoritative effects

Официальный `projectiles` demo реализует hitscan и линейный снаряд, но не area damage и не piercing-рецепт: linear hit проверяет пройденный сегмент, выбирает одну первую collision query цель, затем завершает снаряд и применяет hit/score на сервере ([траектории](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/trajectory/linear.rs), [server hit policy](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/server_current.rs)). В изученных Lightyear/Avian/Replicon материалах готового AoE recipient resolver или автоматического combat dependency closure не нашёл; это вывод о просмотренных API/примерах, не заявление о невозможности реализовать AoE на Bevy.

Встроенный пример сравнивает три решения о доверии и времени попадания: сервер проверяет текущий collider; сервер откатывает target к view-time клиента через Avian lag compensation; либо клиент сообщает hit (явно помечено как insecure) ([описание политик](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L37-L49)). Avian-интеграция хранит только tick-indexed `Position`, `Rotation`, `ColliderAabb`; `LagCompensationSpatialQuery` перепроверяет query по исторической позе и interpolation delay. В source shape считается неизменной, а history ограничена `max_collider_history_ticks` (по умолчанию 35 ticks) ([history API/source](https://docs.rs/lightyear_avian2d/0.30.0/src/lightyear_avian2d/lag_compensation/history.rs.html), [rewound query source](https://docs.rs/lightyear_avian2d/0.30.0/src/lightyear_avian2d/lag_compensation/query.rs.html)). Это полезно для hit-test по старой позиции цели; это не rollback полного игрового мира, будущих выстрелов, cooldown, списка AoE recipients или повторного урона.

В этом же demo принятый результат и геометрия impact создаются на авторитетной стороне и impact реплицируется как presentation entity; отдельно client-reported режим защищает от повторной отправки одним локальным набором `(PeerId, fireTick)`, но в source прямо требует от сервера отдельно проверять sender, cadence, target, replay/duplicates и shot identity ([`accept_hit`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/mod.rs#L116-L155), [client dedupe и caveat](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/client_reported.rs#L1-L47)). Этот ключ соответствует ограничению примера, а не повторяющемуся AoE/pierce: для Bend событие лучше привязать к `(shotId, targetLifeId, pulseOrHitOrdinal, worldTick)` и сделать повторную доставку идемпотентной. Хост авторитетно публикует получателей/результат; клиент может заранее показать круг/вспышку, но не должен превращать локальную цель и списанный pierce в canonical HP.

### Avian rollback и сглаживание

В `LightyearAvianPlugin` каноническая физика — Avian `Position`/`Rotation`; их регистрируют для replication/prediction, а projectile также требует восстановить velocity. Для клиента rollback pipeline: принять replication → восстановить canonical physics pose → переиграть fixed simulation → исправить frame history; smoothing выполняется после этого в render pipeline и не должен попасть обратно в следующий simulation tick ([Avian integration order](https://cbournhonesque.github.io/lightyear/book/concepts/advanced_replication/avian.html)). Тег Lightyear 0.30 добавил easing policies для visual correction и дополнил коррекцию Avian velocity, но это только сглаживание перехода к corrected sample, не подтверждение контакта или сходимость при постоянно отсутствующем remote событии ([release 0.30.0](https://github.com/cBournhonesque/lightyear/releases/tag/0.30.0)). Для проверки Bend отделять canonical correction от render offset; не использовать затухающий визуальный offset в `sweep`, выборе цели или pierce.

## Границы библиотек и переносимость в Bend/Iroh

- **Lightyear** — Bevy/Rust ECS стек с ticked inputs, репликацией, prediction/rollback, interpolation, prespawn matching и Avian hooks. Его README описывает server-authoritative архитектуру; это готовая реализация для Bevy, не модуль для Bend World/Iroh ([README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/README.md)). Переносимы контракты: world-tick input ledger, replay одинаковой fixed logic, стабильный ShotId, explicit authority, canonical/presentation split.
- **Bevy Replicon** — server-authoritative ECS replication, visibility, events и serialization, но без встроенного I/O. В ecosystem перечислены дополнительные prediction/rollback crates; часть отмечена как unmaintained. Сам по себе Replicon не назначает наши world ticks, не создаёт выстрелы и не вычисляет AoE ([README и ecosystem](https://github.com/simgine/bevy_replicon#features)).
- **bevy_ggrs** уместен только как короткое сравнение другого режима: это P2P rollback; Bevy snapshots охватывают только явно зарегистрированные компоненты/ресурсы, rollback восстанавливает entity set и remap'ит Entity IDs. Для него нужна вся детерминированная игровая логика и состояние cooldown/projectile/HP, а текущая цель — authoritative host поверх Iroh, поэтому это не замена transport или локальный фикс ([architecture](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md), [crate 0.22.0 для Bevy 0.19](https://docs.rs/crate/bevy_ggrs/0.22.0)).

**Применение к Bend/Iroh без переноса:** хранить для каждого input `player`, `seq`, `intendedWorldTick`, а на host фиксировать `receivedAtTick` и `appliedWorldTick`. ACK подтверждает принятое исполнение/префикс с tick, а не только FIFO-порядок доставки. Обрабатывать команду на её назначенном тике либо явно отвергать/перепроигрывать; не переносить молча старый input на следующий тик. Предсказывать попадания гостя как предварительные, пока история не включает соответствующие remote weapon births; canonical host подтверждает damage, hit list и pierce. Логический ShotId должен переживать reuse storage slot и rollbacks; event ID для повторных hit pulses включает target life и ordinal. Iroh остаётся transport — эти модели являются игровым протоколом/состоянием, а не основанием менять транспорт.

## Проверочные сценарии

1. Задержать input **до admission host**, не callback отображения snapshot. Логировать `intendedTick`, `receivedTick`, `appliedTick`, `seq`; вводы должны исполняться на заявленном tick или иметь явный late-input policy. Отдельно прогнать 800 мс задержки наблюдения и не считать её input-delay тестом.
2. На тике `k` host стреляет; пуля гостя летит piercing по двум целям. Варьировать: remote fire известен до `k`, приходит после `k`, теряется/повторяется, приходит рядом с ACK; менять cooldown и порядок получения. Сверять ShotId, birth tick, первую цель, pierce, HP и подтверждённые события, а не только позицию и скорость пули.
3. Включить одновременно shot spawn, kill/despawn, reuse пула и два выстрела одного игрока за tick. Проверить generation/ordinal в ID, однократное применение одного и того же `(shot, target-life, pulse)` после replay и одинаковую canonical историю у host/guest.
4. Проверить late authoritative correction: combat state сразу совпадает на общем simulation tick; отдельно render correction затухает, не меняя следующий collision query.
5. Для чтения/ручного сравнения: Lightyear projectiles demo запускается server/client командами из [README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#running); `Q/E/R/T` меняют траекторию, представление, hit policy и client timeline. Не запускал эти примеры и не выполнял сетевой benchmark в рамках этого research.
