# Bevy/Lightyear: shots, rollback and combat dependencies

Retrieved **October 25, 2026** from primary sources. The code has an official tag [Lightyear 0.30.0](https://github.com/cBournhonesque/lightyear/releases/tag/0.30.0) (`382e772`, released September 14, 2026): its manifest lists Bevy 0.19, Bevy Replicon 0.44.1 and Avian 0.7 ([Cargo.toml](https://github.com/cBournhonesque/lightyear/blob/0.30.0/Cargo.toml#L199-L249)). The current Replicon README refers 0.45 to Bevy 0.20, so you cannot separately update Replicon in this bundle without changing the compatible version of Bevy/Lightyear ([compatibility table](https://github.com/simgine/bevy_replicon#bevy-compatibility)). The Lightyear book is working notes, not a complete specification; Her statements below have been verified against tagged examples/APIs where possible.

## What about our error?

The main practical example is Lightyear `spaceships`: a distant shot is predicted **only if the client has already received its real input for that tick**. The current command is taken from `LeafwingBuffer[tick]`, they check that it is `last_remote_tick >= tick`, and the previous sample is required; firing/cooldown works in `FixedUpdate`. For cooldown, compare local `Weapon` with `ConfirmedHistory<Weapon>` and keep `last_fire_tick` in a predictable state. Arriving previously deleted inputs can generate a bullet before the tick simulation; if they are late, the server bullet arrives through normal replication and the client rolls back to the correct state. This is explicitly described in [README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/README.md#predicted-bullet-spawning-and-input-delay) and implemented in [`shared.rs`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L254-L471); separate tests check that without remote input for the required tick the shot does not appear ([tests](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L803-L855)).

For Bend, this maintains the desired distinction: **ACK/delivery order does not set the execution world tick**. Lightyear binds `ActionState` to tick, writes the input to the server buffer and processes it on the corresponding fixed tick; `FixedPreUpdate`/`InputSystems::WriteClientInputs` sets the local sample, and the simulation reads it into `FixedUpdate`. `LocalTimelineSync` assigns tick taking into account input delay; whole-tick correction moves input, prediction and prespawn histories together ([ticks and input schedules](https://cbournhonesque.github.io/lightyear/book/tutorial/basic_systems.html)). This is a "command for T → simulate T" contract, not a guarantee derived from the FIFO ACK. An 800 ms observation delay on the guest does not check the input delay before admission/execution on the host: measure `intendedTick`, `receivedTick` and `appliedTick` separately.

In `spaceships`, predictable bullets are not an attempt to guess the unknown future: all players give inputs, the server sends them out immediately, and with the input delay configured, the remote input can arrive before its tick is simulated. If input is missing, the system waits for it for remote fire; later receipt is corrected by rollback/replay. Therefore, a host shot that is not in the guest's history does not become known from the ACK position or from the deterministic projectile code. For piercing/AoE, this missing birth changes the set of living targets and the order of pierce consumption - such a forecast cannot be final.

## What Bevy Examples Really Show

### Predicted birth and identity

`spaceships` client/server uses one fixed-tick firing logic, `Weapon` with `last_fire_tick`, and deterministic hash `PreSpawned` with `(owner, tick)`. `PreSpawned` matches self-created client and server entities; The documentation specifies that the component must appear in `FixedMain`, and its hash is either built from tick/archetype or explicitly set to be the same on both sides ([API Lightyear 0.30.0](https://docs.rs/lightyear_replication/0.30.0/lightyear_replication/prespawn/struct.PreSpawned.html), [shooting code](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/spaceships/src/shared.rs#L254-L428). This is a spawn-matching mechanism, **not** an algorithm that guesses remote firing or a durable ID for every damage event.

The wider [projectiles demo](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L1-L49) allows you to independently switch trajectory, presentation, hit policy and timeline (`Q/E/R/T`). It compares three views: entity with updatable state, fire-data with tick/origin/direction for deterministic recovery, and a 32-entry ring shot buffer with monotonic `sequence`; the latter handles slot reuse and allows you to mark an authoritative finish tick ([description](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L24-L49), [ShotRecord and diff](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/representation/shot_buffer.rs#L37-L128)). Fire-data saves network updates only for the reproducible trajectory; the example explicitly leaves mutable physics, bounces and homing to the state entity. For multiple pellets from the same owner per tick, the hash must include ordinal: the example itself limits itself to one shot per player per tick and warns about the need for pellet ordinal for shotgun ([hash and clause](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/representation/mod.rs#L50-L80)).

### Prediction - explicit selection, not automatic dependency closure

Lightyear records confirmed/prediction histories for registered components, and `PredictionTarget` selects which entities the client predicts. The mismatch is restored from the confirmed state and fixed simulation replays the inputs until the current tick; the logic must be executed on both the client and the server ([prediction tutorial](https://cbournhonesque.github.io/lightyear/book/tutorial/advanced_systems.html)). This is not a documented automatic bypass for game causality. In the projectiles demo, `AllPredicted` explicitly includes all players and input rebroadcast, but the policy comment lists missing/late remote inputs as a reason for correction and separately warns: motion prediction itself does not set remote firing, collision or outcome ([policy](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/timeline/all_predicted.rs)). Its general fire handler also predicts the shot of the owner client, and for the remote player it expects an authoritative projectile, even in `AllPredicted` mode ([`shoot_weapon`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/shared.rs#L203-L289)). This means that “predict all players” is not the same as “include all future remote weapon births”.

For the piercing problem, the closure would have to be determined from the result of a specific hit: the position and life of the projectile, the states and lives of the targets, their spawn/despawn, cooldown/weapon state, and **all shots already known for that tick** that are capable of changing HP/target earlier. An unknown future remote input cannot be obtained from a local replay. If the full set of reasons is not available, Lightyear-like architecture leaves damage/kill/pierce to the host, and local hit/AoE to provisional presentation.

### Contacts, AoE and authoritative effects

The official `projectiles` demo implements hitscan and linear projectile, but not area damage and no piercing recipe: linear hit checks the traversed segment, selects one first collision query target, then completes the projectile and applies hit/score on the server ([trajectories](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/trajectory/linear.rs), [server hit policy](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/server_current.rs)). In the materials studied by Lightyear/Avian/Replicon, I did not find a ready-made AoE recipient resolver or automatic combat dependency closure; This is a conclusion about the APIs/examples looked at, not a statement about the impossibility of implementing AoE on Bevy.

The built-in example compares three decisions about trust and hit time: the server checks the current collider; the server rolls back the target to the client's view-time via Avian lag compensation; or the client reports hit (explicitly marked as insecure) ([policy description ](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#L37-L49)). Avian integration stores only tick-indexed `Position`, `Rotation`, `ColliderAabb`; `LagCompensationSpatialQuery` rechecks the query based on historical pose and interpolation delay. In source, shape is considered unchanged, and history is limited to `max_collider_history_ticks` (35 ticks by default) ([history API/source](https://docs.rs/lightyear_avian2d/0.30.0/src/lightyear_avian2d/lag_compensation/history.rs.html), [rewound query source](https://docs.rs/lightyear_avian2d/0.30.0/src/lightyear_avian2d/lag_compensation/query.rs.html)). This is useful for hit-testing on the target's old position; This is not a rollback of the entire game world, future shots, cooldowns, list of AoE recipients, or re-damage.

In the same demo, the accepted result and the impact geometry are created on the authoritative side and the impact is replicated as a presentation entity; separately, the client-reported mode protects against re-sending with one local set of `(PeerId, fireTick)`, but in source it directly requires the server to separately check sender, cadence, target, replay/duplicates and shot identity ([`accept_hit`](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/mod.rs#L116-L155), [client dedupe and caveat](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/src/hit_detection/client_reported.rs#L1-L47)). This key corresponds to the example constraint, not the repeated AoE/pierce: for Bend, it is better to bind the event to `(shotId, targetLifeId, pulseOrHitOrdinal, worldTick)` and make the re-delivery idempotent. The host authoritatively publishes the recipients/result; the client can show the circle/flash in advance, but should not turn the local target and decommissioned pierce into canonical HP.

### Avian rollback and anti-aliasing

In `LightyearAvianPlugin`, the canonical physics is Avian `Position`/`Rotation`; they are registered for replication/prediction, and projectile also requires velocity to be restored. For the client rollback pipeline: accept replication → restore canonical physics pose → replay fixed simulation → correct frame history; smoothing is performed after this in the render pipeline and should not go back to the next simulation tick ([Avian integration order](https://cbournhonesque.github.io/lightyear/book/concepts/advanced_replication/avian.html)). The Lightyear 0.30 tag added easing policies for visual correction and supplemented the Avian velocity correction, but this only smoothes the transition to the corrected sample, does not confirm contact or convergence with a permanently missing remote event ([release 0.30.0](https://github.com/cBournhonesque/lightyear/releases/tag/0.30.0)). To check Bend, separate canonical correction from render offset; Don't use fading visual offset in `sweep`, target selection or pierce.

## Library Boundaries and Portability in Bend/Iroh

- **Lightyear** - Bevy/Rust ECS stack with ticked inputs, replication, prediction/rollback, interpolation, prespawn matching and Avian hooks. Its README describes the server-authoritative architecture; This is a ready implementation for Bevy, not a module for Bend World/Iroh ([README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/README.md)). Portable contracts: world-tick input ledger, replay of the same fixed logic, stable ShotId, explicit authority, canonical/presentation split.
- **Bevy Replicon** - server-authoritative ECS replication, visibility, events and serialization, but without built-in I/O. The ecosystem lists additional prediction/rollback crates; part is marked as unmaintained. Replicon itself does not assign our world ticks, does not create shots and does not calculate AoE ([README and ecosystem](https://github.com/simgine/bevy_replicon#features)).
- **bevy_ggrs** is only relevant as a short comparison of another mode: this is P2P rollback; Bevy snapshots only cover explicitly registered components/resources, rollback restores the entity set and remaps Entity IDs. It needs all deterministic game logic and cooldown/projectile/HP state, and the current target is an authoritative host on top of Iroh, so it's not a transport replacement or a local fix ([architecture](https://github.com/gschup/bevy_ggrs/blob/main/docs/architecture.md), [crate 0.22.0 for Bevy 0.19](https://docs.rs/crate/bevy_ggrs/0.22.0)).

**Application to Bend/Iroh without transfer:** store input `player`, `seq`, `intendedWorldTick` for each, and record `receivedAtTick` and `appliedWorldTick` on the host. The ACK confirms the received execution/prefix with a tick, not just the FIFO delivery order. Process the command on its assigned tick or explicitly reject/replay; Do not silently carry over the old input to the next tick. Predict guest hits as preliminary until history includes matching remote weapon births; canonical host confirms damage, hit list and pierce. The logical ShotId must survive reuse storage slot and rollbacks; event ID for repeat hit pulses includes target life and ordinal. Iroh remains transport - these models are a game protocol/state, not a reason to change transport.

## Test scripts

1. Delay input **until admission host**, not callback display snapshot. Log `intendedTick`, `receivedTick`, `appliedTick`, `seq`; inputs must be executed on the declared tick or have an explicit late-input policy. Separately run the 800 ms observation delay and do not consider it an input-delay test.
2. On tick `k` host fires; The guest's bullet flies piercing at two targets. Vary: remote fire is known before `k`, comes after `k`, is lost/repeated, comes next to ACK; change cooldown and order of receipt. Check ShotId, birth tick, first target, pierce, HP and confirmed events, and not just the position and speed of the bullet.
3. Enable simultaneous shot spawn, kill/despawn, pool reuse and two shots from one player per tick. Check generation/ordinal in ID, single use of the same `(shot, target-life, pulse)` after replay and the same canonical history for host/guest.
4. Check late authoritative correction: combat state immediately matches the general simulation tick; Separately, render correction fades out without changing the next collision query.
5. For reading/manual comparison: Lightyear projectiles demo is run server/client commands from [README](https://github.com/cBournhonesque/lightyear/blob/0.30.0/demos/projectiles/README.md#running); `Q/E/R/T` change trajectory, presentation, hit policy and client timeline. I did not run these examples and did not perform the network benchmark as part of this research.
