# Unreal netcode: снаряды, AoE и предсказание в GAS

Проверено **25 октября 2026** по официальной документации Epic для **Unreal Engine 5.8**. Ниже — первичные источники и практические выводы для browser host/Iroh; это не предложение переносить игру на Unreal.

## Паттерны Unreal

**Обычный projectile:** Unreal описывает серверный путь напрямую: клиент отправляет команду стрельбы, сервер создаёт projectile actor, копии реплицируются клиентам, движение реплицируется с authority, а столкновение уничтожает снаряд и наносит урон на сервере. `UProjectileMovementComponent` умеет сглаживать неровные обновления сетевой позиции, но само сглаживание не предсказывает попадание. Это надёжный базовый путь, однако он оставляет задержку до появления авторитетного снаряда у стрелка. В Lyra граната тоже создаётся только при authority; актор гранаты сам проверяет детонацию и применяет эффекты. ([Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine), [ProjectileMovementComponent API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UProjectileMovementComponent), [Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**Hitscan-подобное оружие:** Lyra локально выполняет native targeting traces, отправляет target data серверу на проверку, а серверный путь применяет Gameplay Effect к подтверждённым целям. В описании melee тот же принцип виден как server-only trace → проверки цели/команды → Gameplay Effect. Клиент может сразу показать трассер или предварительный маркер, но попадание и здоровье подтверждает authority. Это ближе к мгновенному запросу контакта, чем к симуляции движущегося тела. ([Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**AoE и урон:** встроенный `ApplyRadialDamage` помечен `BlueprintAuthorityOnly` и наносит урон локально авторитетным акторам в радиусе. В GAS/Lyra аналогичный порядок — вычислить подтверждённые цели, затем на сервере применить к каждой Gameplay Effect; Lyra damage execution учитывает команду, затухание и данные контакта. Поэтому предсказывать можно моментальный визуальный взрыв, но локальный AoE-query сам по себе не является подтверждением списка целей или изменения HP. ([ApplyRadialDamage API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UGameplayStatics/ApplyRadialDamage), [Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**PredictionKey, отказ и rollback:** GAS создаёт ключ при локальной активации; клиент сразу выполняет допустимые побочные действия и отправляет запрос серверу. Отказ вызывает rollback связанных с ключом действий; при успехе клиент ждёт, пока репликация состояния догонит ключ. Ключи, вернувшиеся с сервера, предназначены только исходному клиенту. Окно начальной активации заканчивается вместе с `ActivateAbility`: документация прямо предупреждает, что GAS не предсказывает одним таким ключом действия через несколько кадров. Значит, PredictionKey подходит для связи активации и её локальных последствий, но не заменяет долгоживущий ID выстрела/снаряда и его временную историю. ([FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey))

**Урон нельзя считать автоматически предсказуемым:** обзор GAS говорит, что rollback для отвергнутой способности поддерживают многие не-мгновенные Gameplay Effects, но он не покрывает damage и прочие мгновенные изменения атрибутов/тегов. Подробная страница `FPredictionKey` описывает специальную delta-схему для отдельных мгновенных attribute modifiers с bookkeeping и повторным агрегированием, но это дополнительная механика, а не автоматический rollback произвольного AoE damage execution. Для здоровья безопасный базовый шаблон — сервер единожды подтверждает контакты и применяет эффекты; клиентские числа/вспышки остаются предварительной косметикой. ([GAS overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system), [FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey))

**Gameplay Cues не дают глобального exactly-once:** GAS использует prediction key, чтобы владелец не проиграл повторно cue, пришедший вместе с уже предсказанным эффектом. Но Epic отдельно указывает, что репликация Gameplay Cues ненадёжна и некоторые клиенты могут cue пропустить; cues предназначены только для косметики. Это дедупликация локального предсказания, а не гарантия ровно одной доставки всем участникам. Критичные подтверждения попаданий/урона должны идти через состояние или надёжный прикладной протокол, с собственным ID события для локальной идемпотентности. ([FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey), [GAS overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system))

**Время ввода и коррекция:** `UCharacterMovementComponent` записывает на клиенте `FSavedMove` с вводом и временем, сервер повторяет движение и проверяет результат, затем подтверждает ход либо присылает коррекцию; клиент применяет серверную коррекцию и повторяет оставшиеся сохранённые ходы. В Network Prediction API фиксированный серверный input buffer содержит `LastConsumedFrame`, причём Epic уточняет, что это номер клиентского кадра и он не равен серверному `PendingFrame`. Это полезный явный пример разделения локального номера ввода и серверного мира. ([Networked Character Movement](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine), [TServerRecvData_Fixed API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction/TServerRecvData_Fixed), [Network Prediction API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction))

## Применение к Bend browser host / Iroh

Это вывод из перечисленных паттернов, а не описание API Iroh. Сохранить общую Bend-симуляцию и единственный авторитетный host. Для выстрела связывать **ID команды**, **целевой world tick** и **неизменяемый ID жизни снаряда**; не выводить время игры из номера/порядка сетевого сообщения. Локальный снаряд можно рисовать немедленно, но его рождение должно использовать позицию игрока из того же предсказанного world tick. При приходе authority сопоставлять эту жизнь снаряда и согласовывать её траекторию, не пересоздавая её из устаревшей позиции владельца и не добавляя повторно прошедшие шаги.

Для взрыва host вычисляет попадания и урон на одном авторитетном tick; клиенты могут предварительно показать взрыв и числа, привязанные к ID события, а затем принять подтверждённый результат. Игровая логика, здоровье и результат контакта не должны зависеть от того, доставилась ли косметическая cue. Для replay брать модель Character Movement как ориентир: snapshot задаёт anchor, подтверждённый prefix ввода убирается, а оставшиеся шаги воспроизводятся по world tick, включая нейтральные интервалы. Важно симулировать projectile и цель на совместимом времени контакта: само предсказание только владельца не решает рассогласование столкновения.
