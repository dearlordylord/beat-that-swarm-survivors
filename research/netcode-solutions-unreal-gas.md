# Unreal netcode: projectiles, AoE and prediction in GAS

Reviewed **October 25, 2026** from Epic's official documentation for **Unreal Engine 5.8**. Below are primary sources and practical conclusions for browser host/Iroh; This is not a proposal to port the game to Unreal.

## Unreal patterns

**Normal projectile:** Unreal describes the server path directly: the client sends a fire command, the server creates a projectile actor, copies are replicated to clients, movement is replicated to authority, and a collision destroys the projectile and deals damage to the server. The `UProjectileMovementComponent` can smooth out jagged network position updates, but the smoothing itself does not predict hits. This is a reliable base path, but it leaves a delay before the authoritative projectile appears at the shooter's disposal. In Lyra, a grenade is also created only with authority; The grenade actor himself checks the detonation and applies the effects. ([Networking Overview](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine), [ProjectileMovementComponent API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UProjectileMovementComponent), [Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**Hitscan-like weapons:** Lyra performs native targeting traces locally, sends target data to the server for validation, and the server path applies a Gameplay Effect to confirmed targets. In melee's description, the same principle is visible as server-only trace → target/command checks → Gameplay Effect. The client can immediately show a tracer or preliminary marker, but the hit and health are confirmed by the authority. This is closer to an instantaneous contact query than to simulating a moving body. ([Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**AoE and Damage:** The built-in `ApplyRadialDamage` is marked `BlueprintAuthorityOnly` and deals damage to locally established actors in the radius. In GAS/Lyra, the procedure is similar - calculate confirmed targets, then apply the Gameplay Effect to each on the server; Lyra damage execution takes command, decay, and contact data into account. Therefore, an instant visual explosion can be predicted, but a local AoE-query in itself does not confirm a list of targets or a change in HP. ([ApplyRadialDamage API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UGameplayStatics/ApplyRadialDamage), [Abilities in Lyra](https://dev.epicgames.com/documentation/unreal-engine/abilities-in-lyra-in-unreal-engine))

**PredictionKey, failure and rollback:** GAS creates a key upon local activation; the client immediately performs the allowed side actions and sends the request to the server. Failure causes the key-related actions to rollback; if successful, the client waits for state replication to catch up with the key. The keys returned from the server are intended only for the original client. The initial activation window ends with `ActivateAbility`: the documentation explicitly warns that GAS does not predict actions after several frames with one such key. This means that PredictionKey is suitable for connecting activation and its local consequences, but does not replace the long-lived shot/shell ID and its temporal history. ([FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey))

**Damage is not automatically predictable:** The GAS review says that rollback for a rejected ability is supported by many non-instant Gameplay Effects, but it does not cover damage and other instant attribute/tag changes. The `FPredictionKey` detail page describes a special delta scheme for individual instant attribute modifiers with bookkeeping and re-aggregation, but this is an additional mechanic rather than automatic rollback of arbitrary AoE damage execution. For health, a safe basic template - the server confirms contacts once and applies effects; client numbers/flashes remain pre-cosmetics. ([GAS overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system), [FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey))

**Gameplay Cues do not give a global exactly-once:** GAS uses a prediction key to prevent the owner from re-playing a cue that came with an already predicted effect. But Epic specifically points out that Gameplay Cues replication is unreliable and some clients may miss the cue; cues are for cosmetics only. This is local prediction deduplication rather than guaranteeing exactly one delivery to all participants. Critical hit/damage confirmations must go through a state or trusted application protocol, with its own event ID for local idempotency. ([FPredictionKey API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayAbilities/FPredictionKey), [GAS overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-the-unreal-engine-gameplay-ability-system))

**Input time and correction:** `UCharacterMovementComponent` writes on the client `FSavedMove` with input and time, the server repeats the movement and checks the result, then confirms the move or sends a correction; the client applies the server correction and repeats the remaining saved moves. In the Network Prediction API, the fixed server input buffer contains `LastConsumedFrame`, and Epic specifies that this is the client frame number and is not equal to the server `PendingFrame`. This is a useful explicit example of separating the local input number and the server world. ([Networked Character Movement](https://dev.epicgames.com/documentation/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine), [TServerRecvData_Fixed API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction/TServerRecvData_Fixed), [Network Prediction API](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/NetworkPrediction))

## Application to Bend browser host/Iroh

This is an inference from the listed patterns, not a description of the Iroh API. Save the general Bend simulation and the only authoritative host. For a shot, link **team ID**, **target world tick** and **immutable projectile life ID**; Do not deduce the game time from the number/order of the network message. A local projectile can be drawn immediately, but its spawn must use the player's position from the same predicted world tick. When the authority comes, compare this life of the projectile and coordinate its trajectory, without recreating it from the outdated position of the owner and without re-adding past steps.

For an explosion, the host calculates hits and damage on one authoritative tick; clients can preview the explosion and numbers associated with the event ID, and then accept the confirmed result. Game logic, health, and contact outcome should not depend on whether a cosmetic cue is delivered. For replay, take the Character Movement model as a guide: snapshot sets the anchor, the confirmed input prefix is removed, and the remaining steps are played back by world tick, including neutral intervals. It is important to simulate the projectile and target at a compatible contact time: predicting the owner alone does not resolve the collision mismatch.
