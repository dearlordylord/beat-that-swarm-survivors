# Unity Netcode for Entities: Shot and Hit Matching

Retrieved October 25, 2026. The basis is the official Unity documentation **Netcode for Entities 1.10.0** (Unity Editor 6000.0; pages marked version 1.10.0). The official Unity repositories were reviewed for comparison with working examples. This is an overview of mechanisms and portable ideas for the current Bend/Iroh scheme, not a recommendation to change the engine or network stack.

## Conclusion for our error

NFE does not have a described automatic calculation of the transitive prediction dependency closure - the set of all objects whose future can change the result of the contact. There is rollback/replay, switching prediction for individual ghosts and `GhostGroup`, which synchronizes the delivery of their pictures. These mechanisms only help with explicitly selected objects and a general tick model. This is an inference from the boundaries of the described APIs, and not a statement about internal undocumented capabilities.

For the case under consideration, it is the game dependence that is important: the predicted own projectile consumes pierce and selects the next target based on the state of the enemies. If another player's shot should kill or change the target earlier, the remote volley excluded from the forecast leaves the enemy alive: its own projectile hits the wrong target and spends pierce on it to the intended target. Therefore, a local battle forecast must either include shots from all players that are known or predicted by an explicitly specified assumption, or consider contacts/damage to be preliminary to the authoritative result. The unknown future input of a remote player cannot be recovered from local determinism.

## NFE mechanisms and portable solutions

### 1. Entry is tied to world tick, not delivery time

`ICommandData` contains `Tick`; the client collects commands in `GhostInputSystemGroup`, and the prediction/server loop reads the command for the current tick through the input/command buffer. Packets carry the current and several previous commands to protect against loss. `TargetCommandSlack` gives the server a queue to receive a future input before simulating the corresponding tick. The documentation is straightforward: the server takes the *N* tick input when simulating the *N* tick, if it has not yet been executed. [Command stream](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html), [prediction sequence and command slack](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/intro-to-prediction.html#client-prediction-sequence).

The practical contract for Bend is to store at least `player`, `seq`, `intendedWorldTick`, input value/events, and separately capture `receivedAtTick` and `appliedWorldTick`. The command receipt ACK does not replace the “command → executed world tick” correspondence. For a late input, you must choose an explicit policy: it remains on the original tick with rollback/replay or is rejected/executed using a safe fallback; you can’t silently transfer it to the next tick and assume that history coincided. The status and ACK snapshot stream is also not itself an execution ACK input. [Command stream](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html).

Don't mix observation delay with input delay. In the local probe, 800 ms were added to the callback for receiving messages on the guest; host continued the simulation. This measures late observation, not late command delivery. To infer network latency, input a separate test should delay commands to the admission host and write them to `intendedWorldTick`/`appliedWorldTick`. See [study projectile visibility](coop-projectile-visibility.md#verified-causal-clock-mismatch-without-claiming-input-delay-injection).

### 2. Predict causally related combat sampling

In the full snapshot, the NFE client rolls back predicted ghosts, then repeats the simulation until its current predicted tick. With a partial snapshot, only the entities included in the snapshot are rolled back and repeated; the rest remain on the newer tick. Unity specifically points out that B can interact with frozen C and get the wrong result. Suggested measures: anticipation instead of prediction, changing the affected object by the initiator's system, joint sending of `GhostGroup`, priority of critical chunks, or limiting contacts with entities with `Simulate`. The last two options do not eliminate misprediction in all cases. [Prediction edge cases](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html#interactions-between-predicted-ghosts-using-partial-snapshots).

`GhostGroup` guarantees that root and children are sent together and therefore closes the particular partial snapshot hole. But this is a snapshot replication mechanism, not a general combat dependency resolver. The group has only one root, nesting is not supported, children inherit the relevancy of root, ignore their own send rate/importance; serialization is more expensive and can increase packet fragmentation. Grouping an entire wave of enemies and projectiles together for the duration of an AoE is potentially too broad and expensive. [Ghost groups: behavior and limitations](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-groups.html).

`GhostPredictionSwitchingQueues` allow the client to locally convert individual ghosts from interpolation to prediction and vice versa. Unity gives examples of its own controller, dynamic collisions, weapons, and related projectiles. For most others, ghosts recommends interpolation. But the predicted timeline is approximately ping ahead of the server, and interpolated is behind; switching can cause a jump to more than `2 × ping`, and smoothing of the transition is limited by transform position/rotation. This system helps select the prediction working region, but does not report the missing remote input and does not make the contact authoritative. [Prediction switching](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-switching.html).

In a game with global nearest-target selection, the boundary cannot be automatically drawn along the visible camera: the closure includes all enemies, players, projectile and effects that actually affect target selection, damage, pierce, knockback and spawn/despawn. If it is expensive or the remote future input is unknown, it is more holistic to leave combat decisions on authoritative playback, and present instant local action as anticipation.

### 3. Future shots and identification of predicted spawn

Ghost mode determines who can predict a remote player: in `OwnerPredicted` only the owner does this, other clients interpolate; in `Predicted` all clients simulate it if input values ​​are available to them. If there is no replicated input, NFE repeats the last known input. To accurately predict the future remote fire, you need a tick-indexed firing input/event or an already confirmed spawn; Mere knowledge of movement/held direction is not enough to know that a one-time weapon will work on a specific future tick. [Predicted and owner-predicted modes](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/intro-to-prediction.html#predicted-and-owner-predicted-modes), [input events and replicated inputs](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html#input-events).

NFE requires spawn logic to be executed on both the server and the client; in the prediction loop `IsFirstTimeFullyPredictingTick` protects against re-birth of projectile during replay of the same tick. Predicted spawn gives the client an immediate local object. When the server ghost arrives, `GhostSpawnClassificationSystem` matches it with the local one, and the erroneous local spawn is destroyed. For an unrecognized predicted spawn, you can enable a return to the spawn tick and re-simulation when other ghosts are updated; this mitigates but does not eliminate the problem of mixed tics. [Predicted spawning](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-spawning.html#implement-predicted-spawning-for-player-spawned-objects), [spawn rollback and interaction](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html#predicted-spawn-interactions-with-other-predicted-ghosts).

Default NFE classification compares by ghost type and spawn tick in a five-tick window. Unity warns that multiple bullets of the same type in a window cannot be reliably distinguished by just a tick. For volleys and reuse of the pool slot, you need your own stable shot identity: for example `(owner, inputSeq, spawnTick, ordinal)` plus a separate generation/lifetime target. [Classification limitations and custom classification](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-spawning.html#ghost-classification-and-entity-matching).

The official Unity [FPS Sample](https://github.com/Unity-Technologies/FPSSample/blob/master/Documentation/SourceCode.md) draws a useful boundary: the server creates replicated projectiles, the client can create predicted projectile/visual, and when the server version arrives, it compares them and transfers the client visual to the authoritative entity; unconfirmed prediction is deleted. In [ProjectileSystemsClient.cs](https://github.com/Unity-Technologies/FPSSample/blob/master/Assets/Scripts/Game/Modules/Projectile/ProjectileSystemsClient.cs), the pattern compares type, owner, birth tick, and start/end position. This is a historical Unity sample, not an NFE 1.10 API guarantee; for several identical shots, an explicit unique shot ID is more reliable than fuzzy matching.

### 4. AoE: predict geometry, confirm recipient set

In the NFE materials reviewed, there is no ready-made contract that automatically agrees on a list of targets for an arbitrary AoE. Portable solution: host allows hit on world tick `t` according to one version of collision world and releases confirmed result with `eventId`, source/shot lifetime, `tick`, pulse/ordinal, point/radius and list `(targetId, targetBirth)` plus final damage. The client can show the local provisional zone and provisional recipients from its predicted cohort, but canonical HP, kill, pierce and repeat damage events are confirmed by the host. This is a design recommendation, not a built-in Unity feature.

For periodic auras and piercings, each hit/pulse gets a separate identity; deduplication on only the `(shot,target)` pair will lose legitimate re-hits. Unity FPS Sample describes individual hit-collision damage events that game systems consume, as well as a separate `SplashDamageSystem` for area damage - a useful boundary between collision detection and AoE damage application. [FPS Sample collision/damage overview](https://github.com/Unity-Technologies/FPSSample/blob/master/Documentation/SourceCode.md).

### 5. Rollback physics and lag compensation have a narrow scope

With NFE, predicted physics is executed in a prediction loop, potentially several times in one frame. `PhysicsWorldHistorySingleton` allows the server to view the historical predicted collision world at a specific tick; The documentation gives an example of checking whether the player hit the collider he saw. Example from Unity [Megacity Metro](https://github.com/Unity-Technologies/megacity-metro/blob/master/Assets/Scripts/Gameplay/Mix/Shooting/ShootingSystem.cs) passes `PhysicsWorldHistorySingleton` and `NetworkTime.ServerTick` to the shooting query inside `PredictedSimulationSystemGroup`.

This is useful for hitscan/ray/sphere query bound to input tick. In our scheme, the geometry is calculated by Bend `Contact.sweep`, so we transfer the history/tick contract itself, not the Unity API. Historical collision world itself does not roll back all game ECS, cooldowns, remote weapon births, recipient AoE order, pierce, HP and event history. A homing/ballistic persistent projectile whose subsequent contacts change the course of the simulation requires a consistent tick-replay state or an authoritative contact; historical raycast alone will not replace it. NFE also warns that quantization and prediction batching increase discrepancies/risk of misprediction, and replay has a finite history. [Physics prediction and lag compensation](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/physics.html#using-lag-compensation-predicted-collision-worlds), [quantization and rollback limits](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html).

### 6. Canonical state separate from visible correction

NFE prediction smoothing is designed to soften the transition between the recalculated and previously predicted states; registered callbacks are launched during reconciliation after a new snapshot, not every render frame. Callback modifies the passed component data. Therefore, in Bend it is useful to store two explicit projections: the canonical combat state is immediately restored with authority and re-simulated; render-only offset fades separately and is never involved in target selection or collision. Keeping the old projectile trajectory as the game truth hides the error but prevents convergence. [Prediction smoothing](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-smoothing.html).

## Recommended checks for Bend + Iroh

- Log separately `clientSeq`, `intendedWorldTick`, `hostReceivedTick`, `appliedWorldTick`, input value, `authoritySnapshotTick` and `observationSeq`. A test with an 800 ms snapshot/callback delay should not be considered the incoming input delay; make a separate network input-delay case.
- From one canonical anchor, replay commands by world tick; compare complete combat states after variations of arrival order, burst delivery, loss/duplication and delay. Late-input policy must be observable and deterministic.
- Make a counterexample from the current glitch: remote shot kills/moves the enemy before its own piercing shot; check that the target and the remainder of the pierce correspond to the authoritative timeline. Repeat if there is no future remote input: the result must remain provisional until confirmed.
- Check AoE at radius border, multiple targets, target killed before explosion, reused target/shot slot and re-pulse. Check the exact world tick and lifetime IDs, and not just the proximity of coordinates.
- Check predicted spawn matching for several shots of the same type in one tick and after pool reuse. Compare logical identity, not just physical slot/type.
- For each visible correction, immediately check canonical hit/HP, and render-only smoothing separately check for limited convergent offset.
