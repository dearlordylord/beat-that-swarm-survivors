# Unity Netcode for Entities: согласование выстрелов и попаданий

Проверено 25 октября 2026. Основа — официальная документация Unity **Netcode for Entities 1.10.0** (Unity Editor 6000.0; страницы помечены версией 1.10.0). Для сопоставления с рабочими примерами просмотрены официальные репозитории Unity. Это обзор механизмов и переносимых идей для текущей Bend/Iroh-схемы, не рекомендация менять движок или сетевой стек.

## Вывод для нашей ошибки

В NFE нет описанного автоматического расчёта транзитивного prediction dependency closure — множества всех объектов, чьё будущее может изменить результат контакта. Есть rollback/replay, переключение prediction у отдельных ghosts и `GhostGroup`, который синхронизирует доставку их снимков. Эти механизмы помогают лишь при явно выбранных объектах и общей модели тиков. Это вывод из границ описанных API, а не утверждение о внутренних недокументированных возможностях.

Для рассматриваемого случая важна именно игровая зависимость: предсказанный собственный снаряд расходует pierce и выбирает следующую цель по состоянию врагов. Если выстрел другого игрока должен убить или изменить цель раньше, исключённый из прогноза remote volley оставляет врага живым: собственный снаряд попадает в неверную цель и тратит на неё pierce до intended target. Поэтому локальный прогноз боя должен либо включать выстрелы всех игроков, которые известны или предсказываются по явно заданному допущению, либо считать контакты/урон предварительными до authoritative результата. Неизвестный будущий ввод удалённого игрока нельзя восстановить из локального детерминизма.

## Механизмы NFE и переносимые решения

### 1. Вход привязан к world tick, а не к времени доставки

`ICommandData` содержит `Tick`; клиент собирает команды в `GhostInputSystemGroup`, а prediction/server loop читает команду для текущего тика через input/command buffer. Пакеты несут текущую и несколько предыдущих команд для защиты от потери. `TargetCommandSlack` даёт серверу очередь, чтобы получить будущий input до симуляции соответствующего тика. Документация прямо описывает: сервер берёт input тика *N*, когда симулирует тик *N*, если тот ещё не был исполнен. [Command stream](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html), [prediction sequence и command slack](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/intro-to-prediction.html#client-prediction-sequence).

Практический контракт для Bend: хранить как минимум `player`, `seq`, `intendedWorldTick`, значение/события input и отдельно фиксировать `receivedAtTick` и `appliedWorldTick`. ACK приёма команды не заменяет соответствие «команда → исполненный world tick». Для запоздавшего input надо выбрать явную политику: он остаётся на исходном тике с rollback/replay или отклоняется/исполняется по безопасному fallback; нельзя молча перекинуть его на следующий тик и считать, что история совпала. Поток состояния и ACK снимков также не является сам по себе ACK исполнения input. [Command stream](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html).

Не смешивать задержку наблюдений с задержкой input. В локальном probe 800 ms добавлялись к callback получения сообщений на госте; host продолжал симуляцию. Это измеряет запоздалое наблюдение, не опоздавшую подачу команды. Для вывода о сетевой задержке input отдельный тест должен задерживать команды до admission host и записывать их `intendedWorldTick`/`appliedWorldTick`. См. [исследование projectile visibility](coop-projectile-visibility.md#verified-causal-clock-mismatch-without-claiming-input-delay-injection).

### 2. Предсказывать причинно связанную боевую выборку

На полном снимке клиент NFE откатывает predicted ghosts, затем повторяет simulation до своего текущего predicted tick. При partial snapshot откатываются и повторяются только включённые в снимок сущности; остальные остаются на более новом тике. Unity отдельно указывает, что B может взаимодействовать с «замороженным» C и получить неправильный результат. Предложенные меры: anticipation вместо prediction, изменение затронутого объекта системой инициатора, совместная отправка `GhostGroup`, приоритет критичных chunks либо ограничение контактов сущностями с `Simulate`. Последние два варианта не устраняют misprediction во всех случаях. [Prediction edge cases](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html#interactions-between-predicted-ghosts-using-partial-snapshots).

`GhostGroup` гарантирует совместную отправку root и children и поэтому закрывает конкретную дыру partial snapshot. Но это механизм репликации снимка, а не общий combat dependency resolver. У группы только один root, вложенность не поддержана, children наследуют relevancy root, игнорируют собственный send rate/importance; сериализация дороже и может увеличить фрагментацию пакетов. Группировать всю волну врагов и снарядов на время AoE — потенциально слишком широкая и дорогая связь. [Ghost groups: behavior и limitations](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-groups.html).

`GhostPredictionSwitchingQueues` позволяют клиенту локально перевести отдельные ghosts из interpolation в prediction и обратно. Unity приводит в качестве примеров собственный controller, динамические столкновения, оружие и связанные projectile. Для большинства остальных ghosts рекомендует interpolation. Но predicted timeline примерно на ping впереди server, а interpolated — позади; переключение может вызвать скачок до более чем `2 × ping`, а smoothing перехода ограничен transform position/rotation. Эта система помогает выбрать рабочий регион prediction, но не сообщает недостающий remote input и не делает контакт authoritative. [Prediction switching](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-switching.html).

В игре с global nearest-target выборкой границу нельзя автоматически провести по видимой камере: в closure входят все враги, игроки, projectile и эффекты, реально влияющие на target selection, damage, pierce, knockback и spawn/despawn. Если это дорого или remote future input неизвестен, целостнее оставить боевые решения на authoritative playback, а мгновенное локальное действие представить как anticipation.

### 3. Будущие выстрелы и идентификация predicted spawn

Режим ghost определяет, кто может предсказывать удалённого игрока: в `OwnerPredicted` это делает только владелец, остальные клиенты интерполируют; в `Predicted` его симулируют все клиенты, если им доступны input values. При отсутствующем replicated input NFE повторяет последний известный input. Для точного прогноза будущего remote fire нужен tick-indexed firing input/event или уже подтверждённый spawn; одного знания movement/held direction недостаточно, чтобы знать, что одноразовое оружие сработает в конкретный будущий тик. [Predicted и owner-predicted modes](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/intro-to-prediction.html#predicted-and-owner-predicted-modes), [input events и replicated inputs](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/command-stream.html#input-events).

NFE требует выполнять spawn-логику и на server, и на клиенте; в prediction loop `IsFirstTimeFullyPredictingTick` защищает от повторного рождения projectile во время replay того же тика. Predicted spawn даёт клиенту немедленный локальный объект. Когда приходит серверный ghost, `GhostSpawnClassificationSystem` сопоставляет его с локальным, а ошибочный локальный spawn уничтожается. Для нераспознанного predicted spawn можно включить возврат к spawn tick и повторную симуляцию, когда обновляются другие ghosts; это смягчает, но не устраняет проблемы смешанных тиков. [Predicted spawning](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-spawning.html#implement-predicted-spawning-for-player-spawned-objects), [spawn rollback и interaction](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html#predicted-spawn-interactions-with-other-predicted-ghosts).

Default NFE classification сопоставляет по ghost type и spawn tick в пяти-тиковом окне. Unity предупреждает: несколько пуль одного типа в окне нельзя надёжно различить лишь тиком. Для volleys и повторного использования pool slot нужен собственный стабильный shot identity: например `(owner, inputSeq, spawnTick, ordinal)` плюс отдельная generation/lifetime цели. [Classification limitations and custom classification](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/ghost-spawning.html#ghost-classification-and-entity-matching).

Официальный Unity [FPS Sample](https://github.com/Unity-Technologies/FPSSample/blob/master/Documentation/SourceCode.md) проводит полезную границу: server создаёт replicated projectiles, клиент может создать predicted projectile/visual, а при приходе server-версии сопоставляет их и переносит client visual на authoritative entity; неподтверждённый prediction удаляется. В [ProjectileSystemsClient.cs](https://github.com/Unity-Technologies/FPSSample/blob/master/Assets/Scripts/Game/Modules/Projectile/ProjectileSystemsClient.cs) образец сравнивает тип, владельца, tick рождения и начальную/конечную позицию. Это исторический Unity sample, не API-гарантия NFE 1.10; для нескольких одинаковых выстрелов явный уникальный shot ID надёжнее такого fuzzy matching.

### 4. AoE: предсказывать геометрию, подтверждать набор получателей

В просмотренных NFE материалах нет готового контракта, который автоматически согласует список целей произвольного AoE. Переносимое решение: host разрешает hit на world tick `t` по одной версии collision world и выпускает подтверждённый результат с `eventId`, source/shot lifetime, `tick`, pulse/ordinal, точкой/радиусом и списком `(targetId, targetBirth)` плюс итоговым damage. Клиент может показать локальную provisional зону и provisional recipients из своей predicted cohort, но canonical HP, kill, pierce и повторный damage event подтверждает host. Это проектная рекомендация, не встроенная функция Unity.

Для периодических аур и piercing каждый hit/pulse получает отдельную идентичность; дедупликация только по паре `(shot,target)` потеряет законные повторные удары. Unity FPS Sample описывает отдельные hit-collision damage events, которые потребляют игровые системы, а также отдельный `SplashDamageSystem` для area damage — полезная граница между collision detection и применением AoE damage. [FPS Sample collision/damage overview](https://github.com/Unity-Technologies/FPSSample/blob/master/Documentation/SourceCode.md).

### 5. Rollback physics и lag compensation имеют узкую область действия

При NFE predicted physics исполняется в prediction loop, потенциально несколько раз за один frame. `PhysicsWorldHistorySingleton` позволяет server посмотреть исторический predicted collision world на конкретном тике; документация приводит как пример проверку, попал ли игрок по collider, который он видел. Пример из Unity [Megacity Metro](https://github.com/Unity-Technologies/megacity-metro/blob/master/Assets/Scripts/Gameplay/Mix/Shooting/ShootingSystem.cs) передаёт `PhysicsWorldHistorySingleton` и `NetworkTime.ServerTick` в shooting query внутри `PredictedSimulationSystemGroup`.

Это полезно для hitscan/ray/sphere query, привязанного к input tick. В нашей схеме геометрию считает Bend `Contact.sweep`, поэтому переносим сам контракт истории/тиков, не Unity API. Исторический collision world сам по себе не откатывает весь игровой ECS, cooldowns, remote weapon births, порядок AoE получателей, pierce, HP и историю событий. Для homing/ballistic persistent projectile, чьи последующие контакты меняют ход симуляции, требуется согласованное tick-replay состояние или авторитетный контакт; один historical raycast не заменит его. NFE также предупреждает, что quantization и prediction batching увеличивают расхождения/риск misprediction, а replay имеет конечную history. [Physics prediction и lag compensation](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/physics.html#using-lag-compensation-predicted-collision-worlds), [quantization и rollback limits](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-details.html).

### 6. Canonical state отдельно от видимой коррекции

NFE prediction smoothing предназначен смягчать переход между пересчитанным и ранее предсказанным состояниями; зарегистрированные callbacks запускаются во время reconciliation после нового snapshot, не каждый render frame. Callback изменяет переданный component data. Поэтому в Bend полезно сохранять две явные проекции: canonical combat state немедленно восстанавливается с authority и повторно симулируется; render-only offset затухает отдельно и никогда не участвует в выборе цели или collision. Сохранение старой траектории projectile как игровой истины скрывает ошибку, но препятствует сходимости. [Prediction smoothing](https://docs.unity3d.com/Packages/com.unity.netcode@1.10/manual/prediction-smoothing.html).

## Рекомендуемые проверки для Bend + Iroh

- Логировать отдельно `clientSeq`, `intendedWorldTick`, `hostReceivedTick`, `appliedWorldTick`, input value, `authoritySnapshotTick` и `observationSeq`. Тест с 800 ms задержкой snapshot/callback не считать задержкой входящего input; сделать отдельный сетевой input-delay case.
- С одного canonical anchor повторно проигрывать команды по world tick; сравнивать полные combat states после вариаций arrival order, burst delivery, потери/дублирования и задержки. Late-input policy должна быть наблюдаема и детерминирована.
- Сделать контрпример из текущего сбоя: remote shot убивает/сдвигает врага раньше собственного piercing shot; проверить, что target и остаток pierce соответствуют authoritative timeline. Повторить при отсутствии будущего remote input: результат должен оставаться provisional до подтверждения.
- Проверить AoE на границе радиуса, несколько целей, цель, убитую перед взрывом, reused target/shot slot и повторный pulse. Сверять точный world tick и lifetime IDs, а не только близость координат.
- Проверить predicted spawn matching для нескольких выстрелов одного типа в один тик и после pool reuse. Сравнивать logical identity, не только физический slot/type.
- При каждой видимой коррекции немедленно проверять canonical hit/HP, а render-only smoothing отдельно проверять на ограниченный сходящийся offset.
