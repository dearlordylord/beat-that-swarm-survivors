# 04 - system sandbox: Noita, Magicka and Teardown

## Conclusion

**If you choose by the fraction of the game loop that is conveniently shown through ECS, the Magicka-like arena is the most straightforward option of the three.** Spell composition, projectiles, targets, effects and statuses become game entities/components with multiple overlapping systems. A Noita-like game provides a broader and more recognizable systemic sandbox, but its main difference is the material simulation; it should remain a separate grid subsystem. Teardown makes ECS connections visible in object manipulation, but voxel world and physics can obscure ECS.

The main recommendation is therefore **not a literal Magicka copy, but a small spell-combat roguelite with composite effects, four interacting states (`Wet`, `Burning`, `Slowed`, `Shielded`) and friendly fire**, as the most honest ECS-first playable example. Statuses can be represented by separate optional components or a single `StatusState`/bitset; The choice depends on whether independent ownership, queries, and lifecycle are needed. The number of marker components in itself is not an indicator of ECS value. If the goal of the study is to show the boundary between ECS gameplay and cellular simulation, the next level is a Noita-like room with the same entities plus a very small separate mesh of materials. In both variants, the same creature falls under different independent rules, allowing Bendvy requests and phases to be shown. The authors of Noita describe the materials of each pixel and the scaling of falling-sand simulation; representing each cell as an ECS entity would be an architectural misconception.

**Brief order:** Magicka-like combat is best for pure ECS-first MVP; A Noita-like hybrid is better for extended system display; Teardown-like heist should be postponed until the renderer/physics host appears. In 2024, the author of Teardown described ECS only in the new engine as a selective technique, and not as "pure ECS"; This is not evidence that ECS should store the voxel volumes themselves.

## Magicka-first: finished solo slice without co-op

Without co-op, recognition rests on the single-player challenge: the mage player collects elements in the spell queue, chooses a release form and survives waves of enemies - all these pillars are confirmed by the Paradox page and the manual. For a rich friendly-fire trace, you can add one simple AI ally, but this is a clear expansion of the clone, and not a statement about the original single player mode. [Paradox: Magicka](https://www.paradoxinteractive.com/games/magicka/about), [Magicka manual](https://cdn.akamai.steamstatic.com/steam/apps/42910/manuals/Magicka%20manual%20body%20--%20English.pdf)

### Specific route of the composition

This is a proposed game model and not a statement about Magicka's source code. She uses facts from the manual: water-soak, lightning effectiveness against wet targets, different release forms and friendly fire. Water and lightning here are **two sequentially cast compositions**, not one spell queue, because the manual identifies water and lightning as opposing elements.

1. The player collects `SpellRecipe{elements:[Water], delivery:Force}`. Resolver interprets the selected water profile and builds the effect. When projectile encounters any `Damageable`, it sets the wet state (for example, `Wet{duration}` as a separate component or an entry in `StatusState`) and publishes `StatusApplied{target, Wet}`; water also moves the target.
2. The same encounter request allows enemy, allied NPC and player: they all have `Position`, `Collider`, `Health`, `Faction`. Friendly fire means that allied status does not exclude it from damage. Faction affiliation is stored in `Faction`; a local match on a closed enum of a faction or element is acceptable as long as it only resolves the corresponding rule and does not route all systems by creature type.
3. The player collects `SpellRecipe{elements:[Lightning], delivery:Force}` separately. Normal hit resolution reads the lightning profile and the current state of the target. Hit system selects `Health + Position + Collider`; the wet state can be a separate optional-read component or part of `StatusState`, in which case the electrical modifier is applied to any wet target - enemy or ally. Dry targets receive the normal lightning profile. At the end of the duration, the status system deletes the component or clears the value; The result of the hit in both cases changes.
4. The second NPC in the area does not receive a separate handler just because of its appearance: its inclusion/exclusion is determined by the collider overlap and the target filter. With the Area form, the spatial set of contacts changes; `Self/Item` and `Weapon` change the delivery profile and target set. Spell composition changes the profile of the effect, and the state of the target changes the interaction of the profile with the target. Local match by profile enum is appropriate; meaningful composition is evident in individual requests and delivery, hit, status and damage systems.
5. `Hit`, `StatusApplied`, `DamageApplied`, `AllyDowned` and `WaveCleared` are available to several independent consumers: damage, statuses, wave director, magazine and HUD. The HUD signal about the death of an ally comes after a successful world update.

Schematically, the resolver can read the `ElementRule{element:Lightning, when_target_has:Wet, damage_scale:...}` entry and apply the general operation to the selected target; equivalently, a small private `SpellElement` enum can be matched against the profile by local match. ECS value does not require zero discriminant branches. The risk arises when one universal handler for `ActorKind`, element and status flags owns cast, delivery, collision, damage, expiry and AI at once. `Burning` or `Shielded` can be separate components or values in `StatusState`; separate membership is justified if independent systems actually own them or select rows from them. The implementation should still keep a small closed set of rules and precise failures without turning the resolver into a hidden universal scripting language.

### Entities, Relationships and Schedule

| Essence | Possible composition | What changes behavior |
| --- | --- | --- |
| Mage | `Position`, `Velocity`, `Collider`, `Health`, `ElementBuffer`, `Wand`, `Faction`, `PlayerInput` | Movement and input apply only to this family; all magic then uses the same delivery/effect paths as the AI-caster |
| Ally or enemy | `Position`, `Collider`, `Health`, `Faction`, `AIState`, `SpellCaster`/`ContactDamage`; statuses - `StatusState` or individual optional components | Same hit/status/damage systems; AI and player controls differ by the presence of `AIState`/`PlayerInput`, not by enemy type |
| Cast entity/projectile | `Position`, `Velocity`, `Collider`, `SpellProfile`, `Lifetime`, `CastBy` | Generic movement/collision; profile and chosen shape determine the response |
| Area or effect over time | `Position`, `AreaShape`/`StatusField`, `Lifetime`, `SpellProfile` | Reuses overlap/effect readers, then deleted over lifecycle |
| Weapon/Staff | `Equipment`, `SpellModifier`, `Cooldown` or related entity | The `EquippedBy(player → item)` link determines which modifiers are available; removal/equip are published in the structural change phase |

One suitable graph fact is `CastBy(projectile → caster)`: needed for attribution, friendly-fire traces and deferred hit event. The slice should check that the despawn of the source correctly removes dependent links/events. Relation is not needed for every status if its source does not affect gameplay in any way.

Schedule order: `Input/ElementBuffer` → cast-system builds profile, temporarily consumes buffer and sets cast entity command → explicit spawn barrier → barrier result system publishes `CastCommitted` only after accepted spawn → movement and contact → several `Hit` readers → effect/status and health updates → death/wave transitions → lifecycle barrier → delivery UI/audio after commit. Systems start in the author's schedule order; parallel execution is not assumed or declared. A Projectile created on the current barrier is updated for the first time in the next motion phase, so it does not receive a random additional tick. Victory occurs when the last enemy of the second wave dies, defeat occurs when the magician dies; after the wave, the slice shows the completed result.

### Why is ECS needed here at all if this is a small arena?

For one player and two enemies, a monolithic loop through an array of structures is also feasible. ECS does not provide proven runtime acceleration here. The benefit comes if slice preserves the orthogonal responsibilities of the systems: the general `Health` is used by the hit, periodic damage and healing systems; status changes vulnerability through a separate optional component or field `StatusState`; `SpellProfile` applies to enemy, ally and player; optional `AIState` gives the AI ​​its own data domain without duplicating the overall health model. Local match on the enum of an element or form is the normal way to interpret a profile. What makes ECS different here are intersecting queries, independent systems, and clear ownership of changes, rather than a ban on match or number of components.

This advantage should be confirmed by a regular App, and not by direct manual orchestration within the game code. [The usual App guide](../../../bendvy/docs/reference/ordinary-app.md) describes registration as the main path, checked component access and explicit attach/run. The existing browser [arena demo](../../../bendvy/examples/arena/README.md) already uses composite `Body` and direct orchestration. The new arena should show a real difference in responsibility and access: for example, `Health`, `Faction`, `SpellProfile`, `AIState` plus either independent `Wet`/`Burning` or `StatusState`; registered systems; intersecting queries; events and meaningful structural phases. The large `Body` in itself does not disprove ECS, just as many small marker components in itself do not prove it.

| Selection criterion | How Magicka-first slice shows it | Residual constraint |
| --- | --- | --- |
| Combination | One spell recipe specifies the elemental profile and delivery method; one enemy/ally composition gets shared hit/status/damage behavior | To prove this, you need at least two profiles and two delivery forms, otherwise it’s one projectile with a parameter |
| Overlapping queries | For example, `Health + Wet` and `Health + Burning`, or `Health + StatusState` with separate status consumers; also `SpellCaster + ElementBuffer`, `AIState + Position`, `Collider + SpellProfile` | The same goal must participate in different systems with independent responsibility at different ticks |
| Change of state/composition | Cast changes the Wet/Burning state (by value or membership), duration removes the effect, shield/weapon equip changes the following result | The change should change the gameplay result; structural addition/removal is a separate option, not a mandatory criterion |
| Events and phases | `Hit` read damage and status systems; `StatusApplied` read AI/wave/log/HUD; cast and despawn use explicit barriers | The result of the event reader and the order of effects are set by the ordinary schedule |
| Relationships and cleanup | `CastBy(projectile → caster)` and `EquippedBy(player → wand)`; despawn checks for backlink cleanup/consistency | One real connection and one deletion trace are enough; other connections are not established to cover the API |
| Short cut recognition | Solo wizard, element queue, cast form selection, ally friendly fire, survival waves and win/lose | Without spell composition / cast forms you will get a generic twin-stick arena, and not a Magicka-like battle |
| Load outside ECS | Simple 2D collision/query host, controls and renderer | A full-fledged networked co-op is not needed; without a renderer there will be a headless consumer, not playable |
| Novelty beyond the arena | Separate ownership of independently changeable data, multiple registered systems with overlapping requests, event reactions and barrier-confirmed cast | Composite payload is acceptable; the new consumer adds little if the same rules are still executed in one manual universal pass |

## Adversarial check: maximum ECS versus small first cut

Magicka remains the most straightforward small ECS-first playable **in the Noita/Magicka/Teardown comparison**, but this does not prove that it leads all candidates in terms of maximum ECS coverage. Space Station 14 covers more independent domains - arms/containers, tools, damage, atmosphere and power - and has a public ECS guide with open implementation of individual systems; It pays for this with a social multiplayer part and specialized environmental solvers. FTL gives a rich chain crew → order/room/system → power/weapon target → hit/crash; FTL-like with predefined rooms saves pause and tactical orders without a ship geometry editor. Baba Is You reveals **dynamic membership** the most: physical text circulates, the rule is recalculated, properties like `YOU`/`PUSH` change the corresponding queries. But its author describes a query-shaped rule system using Lua/table data, not ECS architecture; the property becomes an ECS component only in the proposed Bendvy implementation. [SS14: ECS guide](https://docs.spacestation14.com/en/robust-toolbox/ecs.html), [SS14: atmosphere system](https://github.com/space-wizards/space-station-14/blob/971889f18a6b5f14b926d139ba3910b2872e14de/Content.Server/Atmos/EntitySystems/AtmosphereSystem.cs), [SS14: power system](https://github.com/space-wizards/space-station-14/blob/971889f18a6b5f14b926d139ba3910b2872e14de/Content.Server/Power/EntitySystems/PowerNetSystem.cs), [FTL: Subset Games](https://store.steampowered.com/app/212680/FTL_Faster_Than_Light/), [Baba: creator’s GDC slides](https://media.gdcvault.com/gdc2020/presentations/Reading%20the%20rules_Teikari_Arvi.pdf)

If the goal means a maximum of different mechanisms, SS14/ship-sim may be stronger; if there is a maximum runtime add/remove at a low host price, Baba is a serious competitor. If the goal is the shortest live consumer Bendvy, where almost every game choice passes through independent component queries, Magicka remains convincing. The following extensions deepen its system composition without the universal `ActorKind` dispatcher; local matches on the element's profile remain valid:

1. **Fire and cold as temporary state changes:** new lines `ElementRule` set `Burning` or `Slowed` as a separate membership or as values of `StatusState`; existing status, damage and movement systems update suitable combinations of `Health`, `Velocity` and status. With fire you can cause panic in the enemy, with ice you can buy time for your ally; This does not require a separate handler for each creature class.
2. **Persistent spell areas:** `AreaShape + SpellProfile + Lifetime` use the same overlap/`Hit`/effect path as a Force projectile, but change the affected geometry and application duration. The player can block the passage with fire, cover an ally with a shield, or force the target to leave the danger zone. The new combination is component and profile data, not a new type of attacker.
3. **Staff or Relic as a switchable modifier:** an entity with `SpellModifier` is connected to the mage through `EquippedBy`; normal cast resolution reads its data and changes the radius, duration or status of the next profile. Find, pick up and change an item creates meaningful ownership and checks cleanup connections without requiring `if wand.kind == FireStaff`.

Even after these additions, **relationships remain the least central Bendvy feature**: `CastBy` gives attribution, `EquippedBy` is only useful for actually picking up/changing an item and removing the owner. They do not form such a dense game graph as crew assignment, containment or powered-room ownership in the station/ship model. If the owner is never read and does not change during the game, do not consider relation as an indicative result and leave Magicka in the category “maximum ECS benefit with a small first slice”, and not “maximum relations”. All three expansions are design findings, not mechanics that this note attributes to Magicka.

The minimum useful transaction history is cast-system failure before its commit: tentative update `ElementBuffer`, staged projectile command and `CastQueued` event belong to the same ECS transaction. If the immediate reservation/spawn operation returns failure and the callback returns failure before commit, rollback saves the buffer and discards uncommitted changes and publications; if the callback processed the failure as a success, there will be no automatic rollback. This is a game reason to use the existing rollback/commands boundary. **Late explicit barrier refusal is a separate outcome:** if the cast system has already completed successfully, the later barrier refusal does not automatically rollback its commit, and `CastCommitted` should not be published. The slice must explicitly choose to keep elements in a buffer until the cast entity is confirmed, or to perform separate compensation after the observed barrier outcome, and check both outcomes. Animation/sound and HUD show a successful cast only based on the accepted result. The Inspector can give the developer a specific debug view of the current spell queue/status/equipped item upon failure or re-cast. Snapshot/restore is not needed by the first slice and should not promise an exact runtime checkpoint for readers/queues. ECS does not rollback host IO. [Ordinary App guide](../../../bendvy/docs/reference/ordinary-app.md), [current parity coverage](../../../bendvy/docs/parity/coverage.md)

### What makes a cut recognizable and what can be thrown away?

Leave: elemental buffer, choice of form Force/Area/Self/Item/Weapon, several enemies, allied target unprotected from friendly fire, one spell-result matrix and wave survival/challenge with win/lose. Remove: network co-op, campaign scripting, large set of spells, long progression/equipment economy and material grid. If after these cuts there is no choice between element and form, and a successful battle is reduced to one projectile damage, this is already a generic arena, not recognizable by Magicka slice. You can later add a staff/equipment modifier and a second round of elements, keeping the local scope.

## Noita extension: hybrid arena with small material mesh

This is a **design proposal**, not a description of Noita's internal code, and not a required part of Magicka-first slice. The cellular grid does not become thousands or millions of ECS entities. ECS owns game entities and those effects that require addressability, independent query and lifecycle.

### Entities and Components

| Essence | Components/Data | What systems use it? |
| --- | --- | --- |
| Player | `Position2`, `Velocity2`, `Collider`, `Health`, `Faction`, `InputIntent`, `SpellCaster`, `Mana`, `WandLoadout` | input, movement, collisions, spells, damage, death, UI observer |
| Enemy | `Position2`, `Velocity2`, `Collider`, `Health`, `Faction`, `AIState`, `ContactDamage`, `StatusState` or zero or more individual statuses (`Wet`, `Burning`, `Frozen`) | AI, movement, collision, status tick, damage, loot/death |
| Projectile | `Position2`, `Velocity2`, `Collider`, `ProjectileEffect`, `Lifetime`, `CastBy` (relation to owner) | movement, collision, expiry, hit/effect resolution |
| Effect or pickup | `Position2`, `Lifetime`, `PickupKind`, `Sensor` or `StatusPayload` | overlap, apply effect, collect, cleanup |
| Material world | `MaterialGrid` as owner of chunked array/cells; material, liquid/powder, temperature or other required fields | grid update and reactions; creates change messages near subjects |

`Wet` and `Burning` can be added/removed as independent facts about the entity or stored in the general `StatusState`. Separate components are useful if status tick, damage, AI or display independently own/select such states; composite state is also acceptable if these fields change together and are read through a common access path. In both cases, one enemy participates in several system responsibilities, such as damage, status tick and `AIState + Position2`. One `ActorKind` enum or a large `Body` structure does not automatically disqualify the model from ECS; a weak option is a universal pass that routes all rules using kind and flags, instead of independent systems and declared access. Noita sources support many material types and chemical/thermal/electrical interactions, but the specific fields listed below are **our proposed design decomposition**.

Possible connections: `CastBy(projectile → caster)` for damage attribution; `AppliedBy(status → source)` only if the behavior is truly source dependent; `Equipped(player → wand/item)` or inventory link if ownership of a game object must be tracked separately. For the first slice, do not build a complex graph model of objects: it is enough to check one connection, delete it and cleanup upon the death/deletion of the owner.

### Phases and event cycle

1. **Input/cast intent:** input turns into `CastIntent`; the wand system selects a limited set of modifiers and builds the effect from the data. For automatic behavior, this system consumes declared queries/resources.
2. **Spawn barrier:** create a projectile entity with `Position`, `Velocity`, `Collider`, an effect profile, `Lifetime` and an owner relation. An explicit barrier makes the projectile visible to the next phase.
3. **Motion/collision:** systems select moving bodies and projectiles by component. Host collision service provides pairs of contacts; The ECS layer receives `Hit` messages. Do not implement a full-fledged physics solver in Bendvy.
4. **Effect resolution:** The damage system reads `Health`, `Faction` and the status of `Wet`/`Burning` via optional reads or `StatusState`. For example, a wet target receives an electrical response; the lightning profile can be selected by local match, and the fire effect sets `Burning` as a state value or a separate component. The general hit/effect system works with suitable targets of different families, without requiring a universal dispatcher according to `ActorKind`.
5. **Material step:** grid module updates a limited set of cells and publishes changes of type `MaterialReaction`/`ContactChanged`. A separate ECS system applies these observations to entities that cross the world ↔ grid boundary.
6. **Status/AI:** status systems reduce duration and apply periodic damage; AI reads position, threats, status and local grid hazards. The systems use different queries, and not a common pass with a chain of checks of all varieties of `Actor`.
7. **Lifecycle barrier:** health, life time or pickup are created by commands `despawn`/`spawn`. An explicit barrier publishes cleanup, loot, and death events in a fixed order.
8. **Observers:** HUD, battle log and replay/test consumer independently read `Hit`, `StatusApplied`, `CellReaction`, `EntityDied` or `LootCollected`. Observers do not control the authoritative order of world mutations.

### Vertical cut: one chamber and one room

Limit the stage to one player, two enemy types, a short room, and a small multi-material grid. The three spells should activate different interactions: for example, straight bolt, water/wet and electric pulse; add at least one reaction material (for example, a flammable puddle) only after grid updates and events are connected to the ECS. The goal of the slice is not parity with Noita content, but a completed causal trace:

`input → CastIntent → projectile creation → collision → effect/status → health change → death/loot → independent observer reports`.

The test history should include re-launching the enemy in two states (e.g. wet/dry), two projectile types, and one environmental contact to confirm that the new rules use composition. Fix in advance the order of systems and the complete result; make no claims of equivalence or performance to Noita. It will be useful to keep observations about component changes, events, and queued structural commands for each stage.

## What Bendvy already provides, and what slice lacks

[Bendvy README](../../../bendvy/README.md) lists world-scoped entities, typed components/resources, heterogeneous queries with required/optional selections and filters, declared access, systems/schedules/local state, deferred commands and explicit barriers, transactional rollback, typed bundles, relations, state machines, Inspector/Check. This is close to the proposed actor/spell/status loop: query combinations, phases, lazy creation/deletion, relation-owner and event readers can be part of a normal application.

The parity map has a limited verified deterministic fixed-step simulation with spawn/move/damage/removal/hit/death event traces; this is a good example for reusing a form of test trace, but not a finished physical subsystem. [Bendvy simulation evidence](../../../bendvy/docs/parity/simulation.md) and [core map](../../../bendvy/docs/reference/core-map.md) describe the scope and current boundaries. In core map math support and Pixi render adapter are marked as deferred, browser loop/input/capture is deferred; Rust renderer/PBR/assets/audio/editor are not included in the declared parent scope. Therefore, the game prototype will require a separate host/runtime layer for:

- input, window and game fixed-step loop;
- `Position2` math/transform and collision broadphase/contact generation;
- material network and cellular reactions;
- sprites, particles, animation, camera, audio and asset loading.

These items are a list of the needs of the proposed slice, compared with the publicly described core scope, and not an audit of each path in the repository. Before implementation, you need to check the current examples/packages and agree on which host services are temporary and which become part of the product. Deferred renderer/physics should not be presented as already built-in ECS capabilities.

## Counterarguments and rejection criteria

- **Game value can come from the grid, not from the ECS.** If in a simulation most of the state and all the interesting interactions lie in the material grid, the ECS only issues commands and receives events. Then Noita remains a good demonstration of systematicity, but weaker in meeting the goal of “unlocking ECS.” This is the main counterargument.
- **The whole summary can be written as a short AoS update.** In one arena with one player and two enemies, ECS is not obviously necessary. The basis for it here is separate spell/status/faction/AI responsibilities, their intersecting queries and independent event observers; This is an architectural hypothesis to be tested in a real gaming consumer. Enum and local matches by themselves do not disprove ECS. If one universal handler by `ActorKind`/flags has cast, collision, status, damage and AI, the ECS advantage of the slice weakens - even if the fields are spread out over many marker components.
- **It's tempting to have an entity per cell.** This mixes an arbitrary number of updated adjacent values with structured, rare game objects. Noita documentation describes pixel/material simulation; GDC specifically calls falling-sand simulation. The decision to store tiles in a dense/sparse grid is a conclusion about the corresponding architecture, an unconfirmed detail of the internal implementation of Noita.
- **Magicka can be more honest as the first ECS sample.** If the first playable is needed quickly, the composition of elements, the application of statuses and friendly fire create rich queries without a separate sand engine. But a cooperative network is not needed to show the spell-system; its addition will significantly expand the host scope.
- **Teardown can overshadow the ECS meaning.** Fussing with voxel content, mesh/lighting, collision and fracture risks making the new engine the main result of the project. The authors describe the associated complexities and huge state volumes. This game is justified later, when the goal is precisely the joint work of ECS gameplay with the already existing destructible-world host.
- **Without independent systems, everything will be pulled together into a universal handler.** If cast, collision, status, damage and AI are collapsed into one pass, which dispatches all the rules according to `ActorKind` and flags, the slice will not show the independent responsibilities of the systems. Local match on closed `SpellElement` or delivery enum is acceptable. Before choosing a concept, you need to draw a table of systems × owned/query data and check that the intersections reflect real game responsibilities.
- **The game should not become an ECS benchmark.** Quantitative optimization deferred by [Bendvy SPEC](../../../bendvy/docs/SPEC.md). The success of this research is the chosen executable scope and accurate observations, not FPS or the number of “entities”.

Abandon the Noita-hybrid in favor of a Magicka-like arena if the design of the first slice cannot show several intersecting entity queries without a material mesh, or if the grid boundary is so large that the tests observe almost only it. Postpone the entire systemic-sandbox option if the required host package must include full-fledged physics/renderer to give the game meaning; then Bendvy's current goal is better achieved by headless simulation and a more compact ECS-first scenario.
