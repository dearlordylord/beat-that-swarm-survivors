# 22 — Counterargument: ECS as data-oriented querying, not only gameplay composition

**Purpose.** Recheck the candidate synthesis under a second plausible reading of “maximum ECS exposure.” The comparison below is conceptual: it makes no claim about runtime speed and does not rank games by entity count alone. It does not change the project’s deferred performance work.

## The main challenge

The current candidate criteria give substantial weight to independent mechanics composing on the same entity. That favors a small Space Station 14 scenario: the same crew member, tool, or door can participate in damage, interaction, movement, containment, power, atmosphere, and objective systems. This is a strong demonstration of gameplay composition.

But “show ECS at its best” can instead mean making the *data-oriented system model* legible: many rows share a narrow component shape; systems select those rows declaratively; each system states its reads and writes; disjoint system work is visible; membership and structural changes happen at deliberate boundaries. Under that meaning, a swarm/simulation or a deliberately scoped factory game can be a better fit than a station scenario. The conclusion depends on which of these the user wants to foreground.

This second reading is not an invented property of ECS. Bevy’s official guide describes a system as operating on a specific set of component types, and gives movement over entities with `Position + Velocity` as its standard example. The Bevy ECS guide also presents selective query data and filters, declared read/write references, and scheduling based on dependencies. Its current docs describe access and storage tradeoffs; this memo treats them as design axes, not as a universal speed guarantee or evidence about Bendvy. ([Bevy ECS overview](https://bevy.org/learn/quick-start/getting-started/ecs/#ecs), [Bevy ECS README](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md#using-bevy-ecs), [Bevy `Query` docs](https://docs.rs/bevy_ecs/latest/bevy_ecs/system/struct.Query.html#performance))

| Meaning of “maximum ECS” | What the consumer should make visible | Stronger candidate families |
|---|---|---|
| **Compositional gameplay** | Independent capabilities overlap on the same objects; adding a capability lets a new object participate in existing systems; event reactions and lifecycle work are independently owned. | Space station, immersive/colony simulation, some RPG or ship-management slices. |
| **Data-oriented systems** | Broad, regular component queries; narrow declared access; reusable passes across entity roles; visible disjoint writes and structural barriers; limited per-row type dispatch. | Swarm simulation, RTS combat/economy passes, shapez-like production actors. |
| **Both** | Reusable behavior across unlike objects *and* stable, repeatedly processed homogeneous sets. | A carefully scoped hybrid, such as mobile Mindustry-like combat plus a modest factory loop, but with graph/grid work clearly separated. |

The synthesis may therefore overfit *component flexibility* if it calls the station scenario the overall ECS winner without stating that it optimizes the first row. A game can be rich in systems yet provide little clean bulk-query evidence. Conversely, a large homogeneous swarm can show the query/access contract repeatedly while offering fewer examples of capability composition and relations.

The strongest challenge to the earlier station-first synthesis is therefore not “swarm has more entities.” It is that the station slice may be *interaction-dense and row-light*, while a well-shaped swarm or factory slice can repeatedly exercise the ordinary query model. Conversely, a naive swarm clone that keeps a `Body.kind` switch and a monolithic update loop is a weak data-oriented consumer even if it simulates many bodies.

## Membership churn is a design variable, not a genre verdict

Component presence can represent durable capabilities (`Damageable`, `CanMove`, `Produces`) or transient states (`Stunned`, `Powered`, `InHands`). The second style can cause frequent component insertion/removal if every status is modeled as a structural membership change. The SS14 candidate includes many dynamic conditions such as tool held/dropped, damage/status, containment, and powered/offline machinery, but the sources reviewed here do **not** establish that a compact SS14 scenario would have a high rate of component churn. Treat that as a representation risk to examine, not a fact about the game.

Likewise, swarm and factory games are not automatically stable: projectiles spawn and despawn, enemies die, pickups appear, jobs start and complete, machines may stall, and upgrades may add or remove behavior. A meaningful comparison should ask which transitions alter the component set and which simply update component values. A boolean or enum inside an existing component may avoid structural churn but can also move behavior back into per-row branching. The right answer is workload-specific.

Bevy’s official ECS docs illustrate the tradeoff rather than prescribing one representation: table storage is described as iteration-friendly with slower component insertion/removal, while sparse-set storage reverses that tradeoff. This supports examining both repeated iteration and structural lifecycle in the candidate. It does not prove Bendvy uses the same storage design or inherits those costs. ([Bevy component storage](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md#component-storage))

For a fair qualitative comparison, record at least:

- the stable required component sets of the repeated systems;
- which state transitions add/remove components versus update existing values;
- how much work is a narrow homogeneous pass versus a per-entity branch or target lookup;
- whether independent system access declarations remain narrow, or collapse into a broad “whole entity” style;
- which part of the game is a grid, graph, spatial, or cellular solver outside those queries.

These are architecture observations; none implies a throughput result.

## Spatial and network solvers are a separate axis

Factories and RTS games are particularly easy to over-credit. Belts, pipelines, power grids, tile maps, visibility, collision, and navigation can involve large amounts of simulation. Their data may be stored in ordinary resources, arrays, graphs, or specialized structures; a game’s total simulation work is not the same thing as work done by ECS component queries. SS14 has comparable boundaries in atmos, power, containment, maps, and physics; the station study already calls these out.

Keep these questions separate in the final selection:

1. **Does the gameplay state naturally compose as entities, components, and scheduled systems?**
2. **Does the candidate repeatedly expose broad, narrow, data-shaped queries?**
3. **How much of the core loop belongs to specialized grid/network/spatial solvers?**
4. **Can the first slice show the chosen ECS property without first building those solvers?**

A graph-heavy candidate can still be a good game and a good software project. But its graph solver should not be counted as proof of the ECS API’s query or access model.

## What current Bendvy can honestly demonstrate

Bendvy’s [specification](../../../bendvy/docs/SPEC.md#L59-L78) treats declared query selection and read/write access, deterministic schedules, and deferred structural commands as central ECS contracts. It also says initial CPU systems run through a simple sequential schedule and retain parallel execution as future work; “sequential orchestration does not justify ignoring efficient storage or traversal.” ([SPEC, execution and storage notes](../../../bendvy/docs/SPEC.md#L112-L121))

The public low-level [query traversal](../../../bendvy/src/ecs/query.bend#L83-L89) selects current rows by required main and selected auxiliary membership, provides current-row component get/set, and in this route also provides whole-resource get/set in the same transaction. The source says writes roll back on failure and structural commands remain deferred to an explicit barrier. The reviewed [API audit](18-api-audit-review.md#L7-L19) adds the important scope: current-row writes and canonical ordinary component-write plus whole-resource access exist; a generic outgoing-relation-to-arbitrary-target-component join/write is not the standard row operation. A game whose defining loop is “read one entity’s relation, then mutate a linked entity immediately” may therefore need staging, a specialized traversal, or a different slice boundary.

That limitation matters more to a station/RTS-style interaction scenario than to a straightforward movement or production pass. It does not make those games impossible; it means the vertical slice must show where relation-derived decisions are collected and committed instead of implying that every target write is a normal component query. The current sequential scheduler can show deterministic registration order, declared access, overlap, and barrier effects. It cannot currently demonstrate actual parallel execution or justify speed claims. The 2026-10-20 amendment in [SPEC](../../../bendvy/docs/SPEC.md#L8-L27) explicitly defers performance qualification and optimization; no benchmark or profiling evidence is claimed here.

## Conditional recommendation and evidence a consumer could expose

- If the user means **most independent mechanisms composing on shared entities**, retain the station-emergency slice as a leading candidate. Its evidence should be two genuinely different repair/evacuation routes and reusable damage/tool/status systems, while reporting atmosphere, power, spatial lookup, and interaction as separate work.
- If the user means **the clearest demonstration of homogeneous data queries and declared access**, prefer a deliberately redesigned survivors-style or shapez-style slice. For swarm, make movement act on multiple roles without a `kind` switch and separate steering, firing, lifetime, damage, and cleanup. For shapez, keep producers and processor state as queryable entities while the board/conveyor connectivity remains an explicit solver boundary. Either choice must add something beyond the current compound-`Body` arena example.
- If the user means **both**, a small Mindustry-like or RTS hybrid can work only if the proposal states which systems are ordinary ECS queries and which are custom grid/navigation/resource solvers. Its richness does not automatically make it the top ECS showcase.

A future consumer can make this distinction reviewable without claiming speed. It can publish its component model and, for each registered system, show the required/excluded component set, read/write capabilities, schedule position, and barrier dependency. A deterministic scenario can expose which entity roles matched each query and the before/after component-state trace; any match counts should be produced by explicit consumer-owned counters or the host’s own inspection code, not presented as built-in query introspection unless that API is added. Show one shared system operating across multiple roles without kind dispatch, plus a separate system whose access does not overlap its peers. Record structural additions/removals on the same scripted run and visibly identify grid/graph results as solver outputs.

That is honest evidence of component selection, declared access, composition, lifecycle, and schedule semantics. It is not a cache-locality measurement, a scheduler parallelism demonstration, or a performance comparison. If the project later wants those claims, they belong to the separately authorized measurement work, not this candidate choice.

## Evidence and inference ledger

**Primary-source facts used:** Bevy documents query data as selecting matching entities, shows `Position + Velocity` movement and `With`/`Without` filters, describes read/write-based scheduler conflict and parallel eligibility, and documents the table versus sparse-set iteration/insertion-removal tradeoff. SS14’s official ECS guide and pinned source examples support a real data/component/entity-system architecture with multiple cross-cutting systems, while the source report warns that the engine also has specialized managers/services. Mindustry’s cited source shows generated component/entity families and specialized grid/conveyor data, not a proven Bendvy-like query/archetype ECS. Shapez’s pinned source shows filtered systems. These candidate facts and exact source links are in the source-backed [candidate reports](07-space-station.md#what-the-primary-sources-establish), [factory comparison](02-factory.md), and [RTS comparison](05-rts.md).

**Design inferences:** station activity may be more interaction-heavy than batch-heavy in a small clone; swarm or shapez may expose regular queries more often; transient states may or may not be encoded through structural membership; the proposed candidate ranking by interpretation; and the suggested consumer observations. These are hypotheses to check in a concrete slice, not facts about original game performance or Bendvy performance.

**No measurements:** this memo did not run, benchmark, profile, or optimize a game or Bendvy. Its claims are limited to source-visible architecture and the current documented/API-level Bendvy contract.
