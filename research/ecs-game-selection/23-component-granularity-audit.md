# 23 — Component granularity audit: ECS value is not marker count

## Scope and finding

This is a conceptual audit of [the synthesis](REPORT.md), the [evaluation contract](00-evaluation-contract.md), and studies [04](04-systemic-sandbox.md), [10](10-rule-puzzles.md), and [14](14-singleplayer-immersive-sim.md). It changes no candidate report and makes no implementation or performance claim.

Several passages set up an unnecessarily strict counterfactual: an ECS model is weak if it uses any `kind` branch or stores a group of properties in flags, and Baba Is You should physically add/remove one component per derived rule. That is too strong. The useful distinction is **independent capability/data ownership and system selection versus a central resolver that owns unrelated behavior**. A discriminant branch can correctly interpret a closed enum; a composite component can hold related or mutually exclusive state; separate markers are useful when independent systems need independent presence, ownership, or lifecycle. None of these representations proves or disproves ECS by itself.

Bevy's primary component documentation explicitly accepts structs, enums, and zero-sized marker types as components; the broader ECS guide describes a movement query over `Position + Velocity` as the ordinary system pattern. The type shape is a design choice; the significant question is what data a system owns and which entities it selects. ([Bevy `Component`](https://docs.rs/bevy_ecs/latest/bevy_ecs/component/trait.Component.html), [Bevy ECS concepts](https://docs.rs/bevy/latest/bevy/ecs/)) SS14's own guide similarly presents reusable `Damageable`, `PowerReceiver`, and `Buckle` capabilities shared by otherwise different entity families. It argues for composition across actual functionality, not one marker for every field or state value. ([SS14 ECS guide](https://docs.spacestation14.com/en/robust-toolbox/ecs.html))

## A less biased granularity test

Split a capability into its own component when at least one of these is materially useful to the design:

- It is independently present or absent across otherwise similar entities, and that membership changes which system should select the entity.
- Different systems own or mutate it independently, or it has its own expiry, stacking, cleanup, persistence, authorization, or event lifecycle.
- Multiple entity families share it, so a system can operate on the capability without duplicating the behavior for each family.
- Independent queries over that capability express an important gameplay rule or make the owner of mutations clearer.

Keep values together when they share one invariant, are always changed and consumed together, or represent alternatives that cannot coexist. An enum for an actor's current control mode or spell's element is a sensible component value. A status bitset or `StatusState` struct can represent several coexisting statuses. A discriminant match is also reasonable when it is local to interpreting that value, such as choosing the elemental response for a spell profile. The warning sign is a growing cross-product switch that routes movement, damage, inventory, AI, status expiry, rendering, and cleanup through one handler, or duplicates the same behavior separately for each `EntityKind`.

Therefore, revise the interpretation of `00`'s “combining” criterion mentally: ask whether combinations of capabilities produce behavior without a new monolithic *combination class or universal dispatcher*. Do not require zero branches. Likewise, runtime composition should include player-visible changes in effective behavior and rule state; score actual structural membership changes separately if the project specifically wants to test structural ECS composition. Do not award a candidate merely for many tiny marker types or penalize a data-oriented enum/flags representation by default.

## Corrections by candidate

**Baba Is You.** The game's rule semantics are global: a parsed sentence changes what a noun means across the board. The proposal in study 10 can derive an `ActiveRules` resource from the positioned word tiles, then let movement/push, blocking, and goal systems consult that rule table while querying the relevant positioned entities. That avoids inserting/removing `Pushable`, `Stop`, `Win`, or `Controlled` on every affected wall/object each time a sentence changes. It is a design inference from the documented rule mechanic, not a claim about the commercial game's implementation. Physical property components remain a valid alternative if they need independently queried membership or lifecycle; the rule table is not “less ECS” merely because derived rules are a resource. ([Baba Is You official page](https://store.steampowered.com/app/736260/Baba_Is_You/), [creator's GDC slides](https://media.gdcvault.com/gdc2020/presentations/Reading%20the%20rules_Teikari_Arvi.pdf); see also [study 10](10-rule-puzzles.md).)

This weakens Baba's score specifically for **runtime structural add/remove**, not for dynamic rule composition. It remains a strong compact test of whether a player's move changes the data that independent movement, obstacle, and victory systems interpret. Study 10's statement that a large `Flags` field makes its ECS claim “fall sharply” should be narrowed: the score falls if a single board-wide resolver absorbs the independent rules, not just because properties share a flags value. The active-rule table can preserve several independent consumers without materializing every derived noun-property as component membership.

**Magicka.** The four proposed markers (`Wet`, `Burning`, `Slowed`, `Shielded`) are options, not a requirement. A target may instead hold `StatusState{wet, burning, slow, shield, ...}` or a status bitset if the game treats that as one owned state value. The Water → Wet → Lightning interaction still works: a resolver reads the status value and applies the wet-target modifier. Separate `Wet`, `Burning`, and other components become more persuasive when they have independent duration/stack/clear rules, separate system owners, or consumers that genuinely benefit from required-presence selection. A localized `match` over a spell's element/profile is compatible with composition; the problem would be one universal spell-kind switch that also owns all target, delivery, status, collision, and cleanup logic. The Magicka source facts and combat trace remain as documented in [study 04](04-systemic-sandbox.md); this audit changes only the proposed data granularity.

This narrows Magicka's argument from “four statuses mean four ECS components” to **one compositional spell pipeline whose data is consumed by distinct delivery, hit, status, and wave systems**. That is still a strong direct ECS consumer. Its weakest differentiator against SS14 is not status representation but the smaller natural relation/lifecycle surface in a bounded solo arena.

**SS14.** The broad lead survives this correction. Its case comes from independent capabilities reused across families—such as the official guide's shared damage and power examples—plus interaction/event/lifecycle breadth, not from having one marker per visible state. Keep cohesive state in a struct or finite enum where one subsystem owns it; keep capabilities separate where different families and systems use them independently. Since the guide and pinned source study document a real ECS design, this is better architecture evidence than inferring an ECS from a game's mechanics alone. It still carries the largest host and cross-entity integration cost identified in the synthesis.

## Bendvy-specific consequence

The project contract makes this granularity choice concrete but does not establish a mandatory style. The [ordinary App reference](../../../bendvy/docs/reference/ordinary-app.md) says component-query `Args` and `Out` are `Data`, while component payloads may be affine `Type` values through owner-preserving bindings and `Data` projections. The [ordinary query builder](../../../bendvy/src/ecs/ordinary-query-builder.bend) defines `optional` as a read-only selection that keeps rows where the component is absent; the [query implementation](../../../bendvy/src/ecs/query.bend) keeps structural commands deferred until an explicit barrier. Finite-valued typed component state is already an implemented Bendvy capability ([#47 report](../../../bendvy/docs/reports/component-state-completion.md)).

So an always-present actor/status payload updated as data may be simpler on the current standard route than repeated optional writable-marker changes. Conversely, independent component families still make sense when their membership and ownership are valuable; they entail the corresponding command/barrier boundary. This affects the *cost and shape* of a slice, not whether flags/enums qualify as ECS. Do not silently claim optional-write filtering, automatic parallel execution, or free atomicity across later structural barriers.

## Ranking effect

The audit does **not** change the top recommendation for “maximum ECS breadth”: SS14 remains first because its independent cross-family capabilities, event paths, relations, and lifecycle interactions span more of the game. It removes a poor proxy—number of distinct status/trait markers—from that justification.

For the smallest clear dynamic-composition experiment, Baba remains a finalist but loses any advantage awarded solely for inserting/removing a component on every rule change. Its parser-derived table may be the more coherent slice. For a short playable combat consumer, Magicka remains strong after collapsing some statuses into one state component; its value is the interaction among spell recipes, delivery, targets, statuses, and waves, not the marker count. The relative Baba/Magicka order should therefore depend on the desired experiment: rule-driven global behavior change versus independent real-time combat systems. The correction narrows the claimed gaps; it does not force a new overall winner.

No timing inference follows from component granularity. The trade-off here is semantic ownership, query shape, and explicit structural-barrier work. Whether separate components or a composite value performs better would require a controlled consumer benchmark, which is outside this audit.
