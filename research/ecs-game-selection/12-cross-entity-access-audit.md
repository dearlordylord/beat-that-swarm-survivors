# 12 — аудит доступа между сущностями в текущем Bendvy

**Дата проверки:** 2026-10-20. Проверял исходники и сохранённые отчёты read-only; код и тесты не запускал.

## Вывод

Bendvy поддерживает пакетную запись по нескольким строкам одного компонентного семейства и отдельный публичный recognized-App путь, который в одной query-транзакции сочетает writer текущей сущности с записью глобального ресурса. Но обычный component writer адресует только текущую сущность строки. Relation-query может вернуть detached target/source handles, однако его view read-only; явная запись в другой handle идёт через deferred command и барьер. Поэтому штатный App API всё ещё не даёт короткого канонического пути «найти связанный объект, прочитать его компоненты и атомарно изменить обе стороны».

Граница проходит не между «resource API есть» и «resource API отсутствует», а между канонической закрытой композицией и произвольными query-комбинациями. `recognized-query-declaration` предоставляет `write`, `resource_write` и `pair`, а `recognized-app-component.add` регистрирует такой runner в executable App. Этот узкий маршрут покрывает компонент + общий ресурс; он не обещает все ordinary query combinators или адаптеры для произвольных selectors. Для relation target joins и иных custom grants по-прежнему нужен отдельный, проверяемый путь.

Самые прямые для имеющегося API сценарии из исследованных кандидатов — пакетное попадание Magicka-подобного заклинания по нескольким сущностям здоровья и push-chain Baba Is You по одному семейству `GridPosition`. FTL-подобный общий power не является пробелом: его можно сочетать с компонентом crew через recognized pair; dynamic crew→room lookup и запись компонентов связанной комнаты остаются фазовым/custom-query вопросом. Взаимодействие SS14-подобных actor + tool + door сильнее всего выявляет нехватку штатного межсущностного join-а.

Тонкость relation API: outgoing lookup не отсутствует полностью. `RQ.optional_relation` и `RQ.read_relation` существуют и могут вернуть target в detached row. Ограничение в том, что этот relation row — read-only, а ordinary relation capability для runtime-систем описывает `inverse`, `relate`, `unrelate`. Встроенный `inverse_app` — полезный путь, если target уже известен, например получить occupants для известной комнаты; он не является обратным «дай target для текущего crew member» API.

Тонкость resource API: не следует выводить отсутствие общей транзакции из раздельных App factories. Есть два уровня: отдельные legacy component и resource-field registrations — разные runners, но specialized recognized runner штатно сочетает component row и ресурс через `pair`; это показано sparse consumer-ом. Если же изменения оставлены в двух независимо зарегистрированных системах, это две операции расписания: успешная первая не откатывается вместе с поздним отказом второй. ## Безопасный текущий шаблон для пакетного действия

Для действия, которое затрагивает несколько целей с одинаковым writable component:

1. До мутаций получить detached target list из ввода, сохранённого состояния или Inspector/relation view и построить immutable `Args:Data` план вида `[(handle, replacement)]`. Relation observations не включают ещё не применённые relation commands.
2. Обработать план одним query traversal семейства цели. Для каждой текущей строки сопоставить её handle с планом и вызвать declared current-row setter. `compose.each` оборачивает traversal в один `Tx`; ошибка поздней строки откатывает ранее записанные journaled writes и убирает staged events/commands из этого вызова. [Compose transaction scope](../../../bendvy/src/ecs/compose.bend#L257-L267), [finish/rollback](../../../bendvy/src/ecs/transaction.bend#L71-L95)
3. Если handle нужен для сопоставления, низкий слой может выдать `compose.handle_read`. В обычном callback handle не передаётся отдельным аргументом: callback получает `Ops(H)`, `Args` и opaque `H`. У recognized builder перечисленная закрытая поверхность — `write`, `resource_write`, `pair`, а не arbitrary selectors/handle joins; для handle-плана потребуется подходящий query path или пользовательская declaration. [handle grant](../../../bendvy/src/ecs/compose.bend#L99-L106), [legacy component body signature](../../../bendvy/src/ecs/ordinary-app-component.bend#L66-L75), [recognized API boundary](../../../bendvy/src/ecs/recognized-query-declaration.bend#L15-L22)
4. Если действие должно также менять общий ресурс вместе с компонентом текущей строки, стандартный поддержанный App путь — `Recognized.pair(write, resource_write)` плюс `recognized-app-component.add`; sparse fixture показывает такой код. Отдельный selected-resource-field factory всё ещё полезен для системы, выбирающей собственный resource-field declaration; он не нужен для этого same-row component + whole-resource случая. Если нужны arbitrary selectors, target components или неподдержанный grant, разделить работу по фазам либо написать проверяемую custom declaration; несколько регистраций не образуют одну транзакцию. [recognized App registration](../../../bendvy/src/ecs/recognized-app-component.bend#L87-L102), [sparse declaration/body](../../../bendvy/test-fixtures/connected-performance/sparse-motion64/consumer/s-perf/canonical-api-v1/sparse-runtime-v1/motion.bend#L41-L68), [sparse registration](../../../bendvy/test-fixtures/connected-performance/sparse-motion64/consumer/s-perf/canonical-api-v1/sparse-runtime-v1/motion-driver.bend#L76-L76)
5. Различать отказ **до commit** и отказ deferred-команды **после commit**. Если callback одного system/query возвращает failure до `finish(Success)`, его journaled component и resource writes откатываются, а staged outputs/commands очищаются. При успехе `finish` фиксирует непосредственные writes и лишь ставит команды в очередь; если поздняя повторная проверка или barrier отвергает structural command, ранее committed values назад автоматически не откатываются. Relation-команды также возвращают queue status отдельно от outcome; ошибки барьера публикуются как notices. [recognized App rollback guarantee](../../../bendvy/src/ecs/recognized-app-component.bend#L91-L96), [transaction finish/rollback](../../../bendvy/src/ecs/transaction.bend#L71-L95), [insert revalidation](../../../bendvy/src/ecs/compose.bend#L281-L287), [relation queue result](../../../bendvy/src/ecs/ordinary-app-relation.bend#L165-L173)

Этот шаблон даёт пакетную атомарность для immediate updates одинакового семейства; recognized pair расширяет её на общий resource write в том же query transaction. Он не даёт join-а компонентов arbitrary target и не делает atomic immediate writes двух семейств плюс применение structural command на последующем barrier.

## Конкретное ограничение и критерий остановки

Ключевой недостающий стандартный ergonomic unit — не «relation API» вообще, а композиция: *текущая entity → outgoing relation target → query target components → journaled target write в той же транзакции*. Вторая недостающая часть — принятие результатов structural barrier в одну all-or-nothing операцию с immediate entity/resource writes. Источники подтверждают deferred commands и notices, но не такую общую commit transaction.

Для первого clone Baba-подобное ядро остаётся самым прямым способом показать multi-row write одного семейства; Magicka также хорошо подходит и может в том же recognized query транзакционно обновлять общий ресурс. FTL становится заметно жизнеспособнее, если срез ограничен обработкой crew-family + global power и конкретный relation-driven target update можно вынести в фазу. Если основной ввод — приказ выбранному crew member, а главный результат меняет связанную room entity, до фиксации выбора нужно прототипировать selector/relation adapter. Считать этот срез blocker-ом только если такое требование определяет результат игры либо поздний отказ barrier должен отменять уже committed значения.

## Пересмотр после проверки recognized API

Первоначальная версия этого аудита слишком широко утверждала, что ordinary App для component-query + resource-field требует вручную собирать `Ops`/declaration либо координировать отдельные systems. Это утверждение не учитывало специализированный публичный маршрут: `recognized-query-declaration` содержит `write`, `resource_write` и `pair`, а `recognized-app-component.add` передаёт его `RecognizedSystem.runner` при регистрации.
