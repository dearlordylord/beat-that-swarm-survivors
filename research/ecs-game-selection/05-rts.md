# RTS: maximum ECS and best first clone - different answers

## Conclusion

Within the RTS hypothesis, the highest ECS coverage ceiling is for macro RTS like Supreme Commander / Beyond All Reason: economic agents, production, combat units, weapons, projectiles, targets, ownership, order queues and life cycles provide many independent intersecting queries. But a complete SupCom/BAR-like clone is a bad first cut: the path to a recognizable game is easily hijacked by pathfinding, obstacle avoidance, spatial indexing, command of large armies, and network determinism.

For a first clone, I recommend a compact **Red Alert/OpenRA-like solo RTS skirmish** with one resource chain, a small static map, one ground mobility and one victory objective. Game cycle: order the collector to mine ore → get money for the refinery → put a fighter in the factory queue → send him to the enemy base → destroy the headquarters. This gives the player a real decision and a win/lose outcome rather than just another arena fight. Original maps, rules and temporary graphics help limit the amount of content.

In both answers it is necessary to separate **architectural suitability** and **speed**. There is no evidence that the current Bendvy makes this scenario faster than the alternative implementation, and by its specification the initial schedule is sequential. The value of the ECS slice here is in entity compositions, system permissions, explicit phases, composition changes, and event processing.

## What Primary Sources Show

Official documentation [0 A.D. by entity components](https://docs.wildfiregames.com/entity-docs/nightly.html) describes an entity as a set of components, each of which defines a piece of behavior. The list includes `Ownership`, `Position`, `Health`, `ResourceGatherer`, `ResourceSupply`, `ResourceDropsite`, `ProductionQueue`, `Cost`, `UnitAI`, `Attack` and `Formation`. `ResourceGatherer` works with entities carrying `ResourceSupply`; `ProductionQueue` serves unit training and research; `Cost` sets the cost and production time. This is a good map of game mechanics and possible lineups.

However, this is **not evidence of archetype-based or data-oriented ECS**. [The 0 A.D. component guide](https://docs.wildfiregames.com/pyrogenesis/writing-components.html) shows C++ component interfaces and implementations, JS wrappers, `HandleMessage` and synchronous delivery of `PostMessage`/`BroadcastMessage`. A separate [serialization page](https://docs.wildfiregames.com/pyrogenesis/serialization.html) distinguishes between base deterministic, derived deterministic, and non-deterministic state; in [public simulation API ](https://docs.wildfiregames.com/pyrogenesis/classCSimulation2.html) there is a move `Update(turnLength, commands)`, and the command stores the player and data ([`SimulationCommand`](https://docs.wildfiregames.com/pyrogenesis/structSimulationCommand.html)). This confirms the real importance of command order and deterministic state, but does not mean that Bendvy will automatically have a lockstep network.

[OpenRA](https://docs.openra.net/en/release/traits/) offers useful rules and subsystem boundaries: `PathFinder` computes A* routes and attaches to the world actor with `ActorMap` and `Locomotor`; `Harvester`, `ProductionQueue`, `PlayerResources` and the refinery demonstrate a recognizable economic chain. This is an actor/trait configuration, not evidence that the original game uses modern flat ECS storage. Source [Production](https://github.com/OpenRA/OpenRA/blob/bleed/OpenRA.Mods.Common/Traits/Production.cs) - primary point for queue details.

In BAR, the original engine should be considered a model of **mechanical scale**, but not a direct Bendvy template: in [Recoil `CUnit`](https://github.com/beyond-all-reason/RecoilEngine/blob/master/rts/Sim/Units/Unit.h), a unit object with separate command, movement, script and weapon subsystems is visible; [projectile](https://github.com/beyond-all-reason/RecoilEngine/blob/master/rts/Sim/Projectiles/Projectile.cpp) has its own class and movement update. These links do not prove that all of Recoil is designed only object-wise, but they do show that specific unit/projectile paths are not pure examples of ECS. For StarCraft-like parts, only genre properties are used here; This report makes no statements about Blizzard's internal implementation.

## ECS load and compositions

A useful decomposition does not require a separate component or a separate class for each unit name:

| Family | Composition example | Independent consumers |
|---|---|---|
| Player | `PlayerState`, `Wallet`, diplomacy relations | cost check, resource deposit, victory, HUD/score |
| Mine | `Position`, `ResourceSupply`, optional `Selectable` | resource search, extraction, depletion and removal |
| Collector | `Position`, `Move`, `Health`, `OrderQueue`, `Gatherer`, `Cargo`, `OwnedBy` | orders, movement, loot, unloading, combat, player choice |
| Production | `Position`, `Health`, `OwnedBy`, `ProductionQueue`, `RallyTarget` | queue validation, money debiting, release, database loss |
| Combat unit | general `Position`, `Move`, `Health`, `OwnedBy`, `OrderQueue`; optional `Weapon`, `Armor` | movement, target acquisition, attack, damage, death and choice |
| Projectile | `Position`, `Velocity`, `Damage`, `Lifetime`, team/owner, relationship `Source` or `Target` | projectile pitch, hit check, damage, expiration |

This creates real intersections: one mobile entity participates in the systems of orders, movement, visibility/choice, combat and death; producer - in the systems of possession, economy, queue, emergence of essence and destruction. The new fast unit may be distinguished by the absence of `Armor` or the presence of `Weapon`, rather than a new monolithic `kind` branch in each cycle. This is a **design hypothesis** for Bendvy, not a fact about the implementation of OpenRA or 0 A.D.

Relationships are justified where the link is a game link: `OwnedBy` for the owning player, `AssignedTo` for the collector and selected resource node, `Target` for ordering an attack. Clearing them when the target is removed is part of correctness, not a demonstration gimmick. It is easier to keep the route status, transported volume of ore and production time in the data of the corresponding entity. There is no need to turn every cell of the map into an entity: the map/graph and spatial index are better off remaining a regular resource for the navigation service.

## Operating passage through Bendvy

Below is a suggested passage of one player order. It uses the existing ordinary App and explicit order systems; this is not a description of an already implemented RTS.

| Player Action/Input | Compositions, requests and relationships | Phase and visibility limit | Observed result |
|---|---|---|---|
| `Gather(worker, node)` | The command system verifies the owner of `worker`, writes it down as `OrderQueue`, and puts it as `AssignedTo(worker, node)`; ownership error rejects command | Input `PlayerCommand` as data; separate phase of taking orders; barrier after structural change of bond | The interface sees the accepted order; an incorrect order does not change the world |
| The collector goes and extracts | Request `Position + Move + OrderQueue + Gatherer + Cargo`; node request `Position + ResourceSupply`; route reads static map as Resource | `MoveOrders` → `Gather`; when the radius is reached, the node loses stock, the assembler increases the load | Movement, loading of cargo and depletion of the deposit are visible |
| Collector unloads cargo | `Cargo + AssignedTo/Dropsite`; `PlayerState + Wallet`; the deposit links the owner to the player's account | `Deposit` after movement; write-off of cargo and crediting of money must be one transaction; only after success is `ResourceDelivered` published | Money increases exactly once; failure does not lose cargo |
| The player orders a fighter from the factory | `OwnedBy + ProductionQueue + Wallet`; the cost is checked and written off along with the entry into the queue in **one system transaction** | `AcceptProduction`; refusal before commit in case of insufficient funds leaves the queue and account unchanged; timers are processed by phase `Produce` | The player sees the paid position in the queue and the remaining time |
| Production ends | Factory reads `ProductionQueue`; ready position puts the command for the appearance of the entity with `Position + Move + Health + OwnedBy + OrderQueue + Weapon` | The command becomes visible only on an explicit structural barrier; the new unit starts moving from the next simulation step. Late barrier refusal does not cancel the previous payment transaction: save a ready position for retry or perform a separate compensating operation | After a confirmed spawn, there is a controllable combat unit; until this is not there, it cannot be considered produced |
| Unit attacks headquarters | `OrderQueue + Target + Weapon + Position`; the attack creates a separate projectile with data on the source, speed, damage and lifespan | `Acquire/Fire` → barrier → `ProjectileStep` → separate hit check/collision service → `Damage` | A hit changes health and spawns `DamageApplied`; only after commit do statistics/UI readers see the event |
| Headquarters destroyed | `Health` reaches zero; the target's connections are deleted; the headquarters is set for removal; independent reader receives `UnitDied` | `DeathCleanup` → barrier → `VictoryCheck` → post-commit event reader | The game shows victory; if your headquarters is destroyed - defeat |

The phases can be registered in this sequence through the ordinary App. According to [local description ordinary App](../../../bendvy/docs/reference/ordinary-app.md), systems are executed in order of registration, and the initial/intermediate barrier is set explicitly; You cannot rely on automatic concurrency or automatic application of deferred commands. Therefore, the projectile created when fired should not go through several movements in the same step. Events are needed for independent readers of statistics, winning conditions and the host layer, and not as a replacement for the current state of the entity.

## First vertical cut on the current Bendvy

[Bendvy already has a fixed ECS step](../../../bendvy/docs/parity/simulation.md) with spawn/move/damage/remove and hit/death events, including explicit barriers, independent readers and failure/retry. This means the new example should add a strategic loop rather than re-prove conventional combat. [Specification ](../../../bendvy/docs/SPEC.md) calls the first game a minimal reproducible CPU simulation and explicitly specifies a sequential schedule with possible future concurrency exploration. [arena](../../../bendvy/examples/arena/README.md) already has enemies, pickups, bolts, area pulses/chains, targeting, damage and cleanup; The RTS expansion should therefore include real resources, ownership, orders, production and victory conditions.

Suggested cut:

- One player against a simple scripted opponent; two sides, one map of about 16x16 cells, one ground type of movement, one mined resource.
- Two headquarters, one mine, one player collector, one factory and a small supply of starting funds. The factory can produce one cheap combat unit.
- The player chooses where to send the collector and when to queue the fighter; then gives the order to attack or defend the headquarters. The enemy executes a fixed script of orders.
- Win/lose - destruction of the headquarters. The HUD can be a simple host representation of the invoice, order and events; The simulation decision on victory is made by the ECS.
- The grid and occupancy are stored by the resource. For a small map, deterministic BFS/A* without dynamic formations and avoiding moving crowds is sufficient; the traffic system applies the next route step. Render, input and sound remain the host layer.

Mechanics must navigate through registered systems, component requests, transactional changes, explicit barriers, and the ordinary App. If checking a purchase or writing a paid order to the queue falls **before commit**, the rollback of this system should leave both the wallet and the queue without partial changes. But the later application of a separate deferred spawn command is not included in this transaction: an earlier successful commit is not rolled back due to the failure of a subsequent step. Therefore, the order remains in the “paid, ready to appear” state until confirmed activation; it can be repeated or compensated for explicitly. This follows from the limits of rollback for a single system and the rule not to identify commit with the use of structured commands in [SPEC Bendvy](../../../bendvy/docs/SPEC.md#L120), and not from the guarantee of end-to-end atomicity.

Queue and world state are useful for reading/snapshot; snapshot should not be passed off as an execution checkpoint, since [SPEC Bendvy](../../../bendvy/docs/SPEC.md) separately limits the runtime states of queues and readers. Any external "win" publication is done after a successful commit.

## Strongest Counterarguments: FTL and Mindustry

**Why FTL might be a better RTS first clone.** Official page [FTL from Subset Games](https://store.steampowered.com/app/212680/FTL_Faster_Than_Light/) confirms combat pause, crew orders, energy redistribution, weapon target selection, random encounters and permadeath. Even in a small fixed layout, these decisions naturally traverse crew, rooms/systems, health, energy, weapons, projectiles, and hazards. At the same time, in the proposed 08-slice, the ship's plan is fixed, the route is short, and most of the cause-and-effect chain remains local to the ship: there is no need to model operational logistics between resource nodes and the factory or drive troops across a large map. In terms of “closing a recognizable first cut to an infrastructure project,” FTL is RTS’s strongest competitor. It is a weaker choice if the specific goal is to examine mobile unit ownership, production queues, and long economic chains; rooms/power system does not replace this set.

**Why Mindustry can be better than an RTS in terms of the breadth of the game loop.** Small factory-defense naturally combines placement/building, mining, processing, transport, ammo, turret, enemy wave and victory state. On pinned primary sources, this is a hybrid, but specific model: [`UnitComp`](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/entities/comp/UnitComp.java) actually implements health, physics, hitbox, status, command and weapon interfaces at once; [README](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/README.md) says that game entity classes are generated from component classes and UnitTypes definitions. But the adjacent grid/transport contour remains independent: [Tile](https://mindustrygame.github.io/docs/mindustry/world/Tile.html) stores the `Building build` field, and [ConveyorBuild](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/world/blocks/distribution/Conveyor.java) stores parallel arrays of objects/coordinates and links to the next belt. Therefore, Mindustry bypasses RTS if the full cycle “built a base → established supply → survived the wave” is more important, and the path of units can be limited to one base track. It loses to RTS in terms of its focus on orders, possession, different army compositions and a separate attack target.

**When RTS should win despite the price.** If the research question is how much ECS holds self-orders and long entity-lifecycle, and not just room systems FTL or building/transport graph Mindustry, RTS wins only under a verifiable constraint: the first cut remains a completed economic skirmish, the player actually chooses between loot, waiting for release and attack/defense; it uses ownership and target relationships, independent requests for worker/production/combat/projectile/death, and routes are reduced to a small static map and do not require a separate dynamic avoidance/spatial engine. Then one game party checks the single path “player gave order → order and attitude changed → economic transaction → unit appeared on barrier → combat → death event → victory”, which FTL and Mindustry as proposed slices cover differently, but not simultaneously. If for the sake of such a path you have to build a full-fledged navigation, RTS no longer wins: for a short, complete game FTL is easier, and for a factory supply/wave loop Mindustry is more specific.

## Objections and criteria for rejecting a hypothesis

Yes, this script can be written with one array of structures and a short loop `switch(kind)`. For 20 objects, this solution may be simpler. ECS makes sense only if the individual requests truly express different responsibilities and intersections of entities: movement does not iterate through the production queue, loot does not check weapons, general damage works on the building and unit, and adding another type changes its composition and queue data instead of adding branches to all cycles. Therefore, the benefit is the preparation and maintenance of mechanics, not the declared acceleration.

The main hidden cost is navigation and interactions in space. The OpenRA documentation separates A* `PathFinder` and its world-level dependencies separately from actors; The list of services not automatically provided by ECS is given in [coordination evaluation contract](00-evaluation-contract.md), not in SPEC Bendvy. SPEC separately specifies a consistent initial schedule and explicit deferred barriers. To make a cut, you need to prohibit mobile obstacles and complex formations, keep a small fixed map and highlight route search as a separate pure service. Bendvy cannot be credited with having a ready-made pathfinder or multi-threading.

**Kill or greatly reduce the RTS hypothesis** if before the completed cycle "order → loot → production → attack → victory" you need to write dynamic multiplayer navigation, crowd/formation avoidance, complex spatial broadphase or lockstep/network replication. In this case, the engine infrastructure will absorb the ECS consumer check; It’s safer to leave a static script route or select an existing arena slice. It is precisely the hypothesis of maximum ECS expansion that should be killed if, after simplification, there are no independent queries/phases/relations and everything comes down to a single `kind` cycle: then RTS adds more content than meaning for ECS.

Finally, don’t reduce the scenario to “squads stand in the arena and deal damage”: after the cut, there should be a player’s choice, a resource decision, the release of a new entity and a clear win/loss. On the other hand, transactions, inspection or events should not be added for the sake of API coverage: purchase abandonment, queue, loot statistics and victory messages should be the game objectives they serve.

## Valuation under the selection contract

Based on the [overall evaluation contract](00-evaluation-contract.md) criteria, RTS scores strongly for combination, crossover requests, roster changes, stages and events, and ownership and goal relationships. The novelty in relation to the arena is also high: there is already movement and combat, here they are associated with orders, economics, production queue and completion of the party. The suitability of the first cut is high only for a compact single card; the SupCom/BAR version has a low one due to pathfinding, complex content and network simulation. This is a qualitative assessment, not a measurement or a comparative benchmark.

Summary for the parent rating: **RTS is a strong candidate for maximum ECS coverage among genre options; compact OpenRA/Red Alert-like skirmish economy is a reasonable first clone; BAR/SupCom-scale is a subsequent stress cut, not a starting goal.**
