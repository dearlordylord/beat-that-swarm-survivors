# Hypothesis 2: Factorio/Mindustry/shapez for Bendvy ECS demo

**State:** research hypothesis, not a game selection or implementation decision.

**Preliminary conclusion (assessment based on primary sources):** if the goal is the most visual display of query/composition ECS within the factory genre, the strongest candidate is shapez-like: its sources directly show entity component storage and systems with a filter of required components. [Entity](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/entity.js), [GameSystemWithFilter](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/game_system_with_filter.js). **If the main criterion is maximum ECS across the study, Mindustry is not yet the leader:** separate grid/graph solvers do not count as ECS breadth, and its original query composition is less well established than shapez's. For global comparison, SS14, Baba Is You and Cosmoteer remain. **Mindustry remains a conditional choice** for broad factory-defense with many actor systems if we deliberately rearchitect its buildings and actors into small shared Bendvy components; production graphs still remain separate models. This is a hypothesis about the breadth of a **game built on Bendvy**, not a claim about the original's ECS architecture.

This comparison **does not claim** that the internal architecture of Factorio, Mindustry or shapez is equivalent to Bendvy or Bevy ECS. I only use what the primary sources explicitly describe: the game loop, accessible parts of the source code, and specific algorithmic boundaries.

**Comparison specifically based on ECS depth.** If the question is which initial candidate factory shows component queries more clearly, shapez-like is stronger: its game systems have explicit filters for the required set of components. Mindustry-like potentially gives more actor families, but the README confirms code generation of types from components and `UnitTypes`, rather than the equivalent Bendvy query model. With a literal transfer of the boundaries of the original, its characteristic factory part remains a tile/grid/graph simulation; the examined unit/bullet components themselves do not show that buildings share the same query intersections with them. Mindustry is a hypothesis about a broader **game deliberately rearchitected on Bendvy**, not a confirmed ECS leader.

## Clarification on the "maximum ECS" goal, not the fastest clone

The difference is visible in the sources. In shapez, `Entity` stores component storage, and `GameSystemWithFilter` takes a list of required components and maintains a set of entities that have **all** of them; membership is revised as components are added or removed. This is a specific query-like game API, although its JS objects and storage are not equal to Bendvy. [Entity](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/entity.js), [GameSystemWithFilter](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/game_system_with_filter.js). Mindustry README describes the assembly of entity classes from component classes and `UnitTypes`; `UnitComp` aggregates many interfaces into one type, and `EntityGroup<T>` is a typed group with regular iteration and an optional predicate. These facts confirm generation and composition, but do not in themselves show an arbitrary all-of query on a runtime set of components, as in shapez. [Industry README](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/README.md), [UnitComp.java](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/entities/comp/UnitComp.java), [EntityGroup.java](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/entities/EntityGroup.java).

Therefore, if **maximum ECS exposure is the main criterion**, Mindustry cannot be put first only for the combination of factory and combat: after separating grid occupancy, belt transport and connectivity, there remains less query composition proven by the source code, and these graph tasks should not be counted as ECS breadth. Within the factory subfamily, the conditional choice for an ECS-oriented clone is a shapez-like production puzzle; Mindustry-like is worth keeping in comparison if the team is willing to re-architect buildings, units, projectiles and statuses around small, intersecting Bendvy components, rather than carrying over the original types as is.

In a global candidate comparison, this factory output does not designate a winner. Space Station 14's development documentation explicitly explains the composition of game objects and the system approach; Baba Is You confirms player-changeable rules, and the author's talk describes parsing physical words into sentences; Cosmoteer dev notes confirm crew missions, component damage, and ship separation when communications are lost. These sources show the mechanics and engineering loads without proving the ECS architecture of commercial games. At the maximum ECS criterion, the global shortlist should include these options along with shapez, and the Mindustry selection should remain conditional. [SS14 ECS guide](https://docs.spacestation14.com/en/robust-toolbox/ecs.html), [Baba Is You](https://store.steampowered.com/app/736260/Baba_Is_You/), [GDC talk by its developer](https://gdcvault.com/play/1026590/Reading-the-Rules-of-Baba), [Cosmoteer developer notes: crew and ammo](https://blog.cosmoteer.net/2011/02/starship-builder-crew-ammo.html), [ship combat](https://blog.cosmoteer.net/2012/02/starwright-ship-combat.html).

Current Bendvy can express such clones through typed components, heterogeneous queries, and explicit ordering systems; structural changes must pass through public commands/barriers. But it does not provide ready-made tile occupancy, belt/resource graph, movement/pathfinding, collision, rendering or input. For a Mindustry- or shapez-like port, these solver/domain and host parts remain separate models; their volume must be taken into account separately from the ECS value. This output does not require a new API, performance infrastructure or benchmark before selecting a game.

Factorio is especially useful as a warning about boundaries: in FFF #82 the developer writes that the items on belts were separate game entities, but then the sequences became internal structures on invisible paths; FFF #176 describes storing distances between objects and updating the boundaries of a long line. Developer notes 2015–2024 separately describe the compact presentation of items on belts and transport lines, reading the contents of the entire transport line, the rendered Fluid Manager and A*-pathfinding. These notes outline specialized simulation/domain tasks, but do not prove the ECS architecture of Factorio itself; they also don't allow Factorio to be called "non-ECS". [FFF #82](https://www.factorio.com/blog/post/fff-82), [FFF #176](https://www.factorio.com/blog/post/fff-176), [FFF #405](https://www.factorio.com/blog/post/fff-405), [FFF #421](https://www.factorio.com/blog/post/fff-421).

## What Mindustry-like can add to an existing example - when rearchitecting

Bendvy [browser arena](../../../bendvy/examples/arena/README.md) already runs enemies, pickups, bolts, pulses and chains, but gameplay stores many fields in one `Body` and example orchestrates direct query calls. A simple arena therefore already shows the life of entities and damage; another game just about running enemies risks repeating the same demo.

Factory-defense changes not the fact that entities move and take damage, but the **composition structure and number of subsystem interactions**. ECS is not the only possible way to implement the game; The value being tested here is whether duplication and branching across types is reduced when the same `Health`, `Team`, `Position`, `Targeting` or `Status` is needed by different families of actors/buildings. If there are few combinations and reused passes, ECS will give a weak practical gain:

- A moving enemy can have `Position + Velocity + Team + Health + PathGoal + Statuses`; fixed building - `GridCell + Footprint + Team + Health`; turret - `GridCell + Team + Inventory/Ammo + Targeting + Weapon`; projectile - `Position + Velocity + Damage + Lifetime + Owner`. These are designed sets of components, not descriptions of the original code.
- Requests cross different game roles: `Health + Team` for taking damage; `Velocity + PathGoal` for movement; `Inventory + Recipe + CraftProgress` for manufacturing; `Ammo + Targeting + Team` for shooting. A new building variation should appear through a combination of capability components and query systems, and not through a new monolithic `Body` with more and more optional fields.
- Deferred commands and barriers are suitable for placement/demolition, wave appearance, projectile birth and removal of dead actors. Events `ItemProduced`, `ItemDelivered`, `Hit`, `UnitDied`, `WaveStarted` can have independent readers: for example, the victory state, log and host animation read one publication without sharing one cursor. This proposal relies on the Bendvy API; The game does not have a ready-made accepted event/victory semantics until the application itself is designed.
- Directed relationships can be useful for `target`, `owner`, `supports/powered-by` or containment, but power network and transport topology should not automatically replace relation queries. For frequent neighbor hops and bulk updates, a separate adjacency/path graph may be clearer and cheaper.

The practical conclusion is to use ECS at the level of actors, building capabilities, lifecycle and gaming systems; grid-occupancy, belt routing, resource pools and pathfinding are considered separate domain models that ECS systems read and update with explicit boundaries. Render, input and audio remain the host layer, not the ECS.

## Proposed first cut

Not a full campaign. A small ultimate map with a basic core, one ore, one miner, a belt route, a furnace/ammo maker, one turret, one enemy type and one wave.

One fixed tick should indicate a completed loop:

1. Host translates the player's command to place/rotate/demolish a building into a typed command; map index rejects an occupied square or places a building entity. Structural visibility comes at an obvious barrier.
2. Mining/production system receives raw materials; a separate transport graph transfers the quantity to outputs; processor with inventory/recipe moves progress, consumes inputs, creates ammo.
3. Wave system creates enemy composition `Position + Velocity + Team + Health + PathIntent`; movement uses a simple route through the cells. The Turret system selects a suitable target and commands the release of the projectile.
4. Projectile system moves the `Position + Velocity + Damage + Lifetime + Owner`; collision/bounds leaves broadphase/grid and geometry as a separate function. Damage system updates Health, publishes hit/death and sets cleanup/drop commands; cleanup becomes visible on the next barrier.
5. Two independent event readers update the same sim picture in different ways: wave counter/win condition and game log/host-effects. The final headless output shows the state of the core, ammunition, position and HP of the enemy, hits and the total of the wave; the browser host can complete the same simulation later.

This is a slice with several honest ECS systems and one small domain graph subsystem. It does not require making each item on the pipeline a separate entity: streaming quantities can be stored in transport model/buffers. In motion, live `Unit`, `Projectile` and optional dropped pickup are separate entities because they have independent state, target, collisions and life cycle.

## Compatible with current Bendvy

**Repository facts at the time of reading:** [root README Bendvy](../../../bendvy/README.md) lists world-scoped entity and typed components/resources, heterogeneous queries, declared accesses, systems/schedules, deferred commands/barriers, rollback, relations, machines and read-only inspection. It also states that this is ECS, and not a full-fledged game engine. [SPEC](../../../bendvy/docs/SPEC.md) requires a deterministic fixed-step console script with move/damage/removal/events and says that the initial systems are executed sequentially on the CPU; the parallel executor remains a separate follow-up. [Parity index](../../../bendvy/docs/parity/README.md) marks #63 as a closed fixed-step ECS scenario and #64 as preparing a copy of Tower Defense; accepted #64 is currently planning a separate integration copy of Tower Defense; the original project remains read-only.

**Consequence (estimate, not verified by application spike):** The current API, according to the declared capabilities, is sufficient for prototyping typed-actors, declared queries, schedule ordering, barriers, relation/event consumers and headless output. But it itself does not provide a ready-made renderer/input loop, tile map, transport graph, routing, collision, AI pathfinding, content/recipe progression or game maps. This needs to be written and checked separately as a domain/host layer. Not a single ECS capability page proves that this particular scene scale has already been adopted in JS and Native. The study does not imply FPS, entity count or acceleration; quantitative optimization of Bendvy in the current SPEC is postponed.

## Objections and conditions that will refute the hypothesis

1. **Industry may turn out to be an object tower defense with ECS only for mobile entities.** Sources confirm component-generation for Unit/Bullet, but do not describe the entire game as query-driven ECS. Tile holds `Building`, and `ConveyorBuild` stores item arrays and a chain of neighbors. If a pilot leaves turrets, vehicles, and all system intersections in specialized branches, it is not a good showcase for composition; It’s better to first test the simplest shapez-like production vertical slice.
2. **The graph part can absorb all the work.** If an honest simulation of belts/power and grid occupancy requires constant bespoke traversals, and the actors use only 1-2 separate monolithic queries, the result will be basically a graph simulator with an ECS library. This directly refutes "maximum ECS exposure".
3. **Factorio scale is not transferred through inspiration.** Primary materials describe special transport lines, segment updates fluid and algorithmic pathfinding. A clone that models each item/inserter/pipe as an entity and promises scale is not proven by sources about Bendvy. If the target outcome is a huge factory, Factorio-like may be the right long-term product, but it is not a limited showcase without solving a separate problem about graph simulations.
4. **shapez can win on actual completion.** If the criteria is to get the first visible game on a small map and show building/queries/schedule components without developing combat AI, shapez v1 is simpler and open. Its official README indicates that the original shapez is open source, but the repository is no longer developed by the team, which has migrated to Shapez 2. It also already demonstrates filterable component systems, so a new Bendvy clone must add interactions the existing arena does not demonstrate. [Official README and project status](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/README.md)
5. **Licenses require not to mix "clone mechanic" and transfer of materials.** Official sources of Mindustry and shapez are marked GPL-3.0; This does not prohibit independent play by genre/ideas, but code and assets from these repositories cannot be included in a product without an informed licensing decision. This study does not suggest copying sources, texts, levels, visual assets or trademarks. [Mindustry LICENSE](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/LICENSE), [shapez LICENSE](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/LICENSE)

**Functional falsifier before choosing a game:** in a working narrow section, different family compositions must intersect several ordinary systems; appearance/deletion/death should change query membership through public barriers; at least two independent consumers must observe events; adding a new turret or enemy variation should primarily change the composition of the components/data and not force you to edit each pass of the game loop. If this does not work, the Mindustry-like selection is not justified enough.
