# Гипотеза 2: Factorio / Mindustry / shapez для демонстрации Bendvy ECS

**Состояние:** исследовательская гипотеза, не решение о выборе игры или внедрении.

**Предварительный вывод (оценка по первичным источникам):** если цель — самый наглядный показ query/composition ECS внутри factory-жанра, сильнейший кандидат — shapez-like: его исходники прямо показывают entity component storage и системы с фильтром обязательных компонентов. [Entity](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/entity.js), [GameSystemWithFilter](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/game_system_with_filter.js). **Если главный критерий — максимум ECS во всём исследовании, Mindustry пока не лидер:** отдельные grid/graph-решатели не засчитываются как ECS-широта, а её оригинальная query-композиция подтверждена слабее, чем у shapez. Для глобального сравнения остаются SS14, Baba Is You и Cosmoteer. **Mindustry остаётся условным выбором**, если нужен широкий factory-defense с большим числом акторных систем и мы готовы намеренно переархитектурировать его здания и акторов на небольшие общие Bendvy-компоненты; тогда графы производства всё равно остаются отдельными моделями. Это гипотеза о широте **игры, построенной на Bendvy**, не утверждение об ECS-архитектуре оригинала.

Это сравнение **не утверждает**, что внутренняя архитектура Factorio, Mindustry или shapez равна Bendvy или Bevy ECS. Я использую только то, что первичные источники явно описывают: игровую петлю, доступные части исходников и особые алгоритмические границы.

**Сравнение именно по глубине ECS.** Если вопрос — какой исходный factory-кандидат яснее показывает component queries, shapez-like сильнее: его игровые системы имеют явные фильтры по обязательному набору компонентов. Mindustry-like потенциально даёт больше семейств акторов, но README подтверждает кодогенерацию типов из компонентов и `UnitTypes`, а не эквивалентную Bendvy query-модель. При буквальном переносе границ оригинала её характерная фабричная часть остаётся tile/grid/graph симуляцией; просмотренные unit/bullet компоненты сами по себе не показывают, что здания разделяют с ними такие же query-пересечения. Mindustry — гипотеза о более широкой **игре, намеренно переархитектуренной на Bendvy**, а не подтверждённый лидер по ECS.

## Уточнение по цели «максимум ECS», а не самый быстрый клон

Разница видна в исходниках. В shapez `Entity` хранит component storage, а `GameSystemWithFilter` принимает список обязательных компонентов и поддерживает набор сущностей, имеющих **все** из них; при добавлении и снятии компонентов membership пересматривается. Это конкретный query-подобный игровой API, хотя его JS-объекты и storage не равны Bendvy. [Entity](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/entity.js), [GameSystemWithFilter](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/src/js/game/game_system_with_filter.js). Mindustry README описывает сборку entity-классов из component-классов и `UnitTypes`; `UnitComp` агрегирует много интерфейсов в одном типе, а `EntityGroup<T>` — типизированная группа с обычной итерацией и опциональным предикатом. Эти факты подтверждают генерацию и композицию, но сами по себе не показывают произвольный all-of query по runtime-набору компонентов, как в shapez. [Mindustry README](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/README.md), [UnitComp.java](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/entities/comp/UnitComp.java), [EntityGroup.java](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/core/src/mindustry/entities/EntityGroup.java).

Поэтому, если **максимальное раскрытие ECS — главный критерий**, Mindustry нельзя ставить первым только за сочетание фабрики и боя: после отделения grid occupancy, belt transport и connectivity остаётся меньше доказанной исходным кодом query-композиции, а эти графовые задачи не следует засчитывать как ECS-широту. Внутри factory-подсемейства условный выбор для ECS-ориентированного клона — shapez-like production puzzle; Mindustry-like стоит оставить в сравнении, если команда готова переархитектурировать здания, юнитов, снаряды и статусы вокруг небольших пересекающихся Bendvy-компонентов, а не переносить исходные типы как есть.

В глобальном сравнении кандидатов этот factory-вывод не назначает победителя. У Space Station 14 разработческая документация прямо объясняет композицию игровых объектов и системный подход; Baba Is You подтверждает меняемые игроком правила, а доклад автора описывает разбор физических слов в предложения; dev-заметки Cosmoteer подтверждают задачи экипажа, покомпонентный урон и разделение корабля при потере связей. Эти источники показывают механики и инженерные нагрузки, не доказывая ECS-архитектуру коммерческих игр. При максимальном ECS-критерии глобальный shortlist должен включать эти варианты наряду с shapez, а выбор Mindustry оставаться условным. [SS14 ECS guide](https://docs.spacestation14.com/en/robust-toolbox/ecs.html), [Baba Is You](https://store.steampowered.com/app/736260/Baba_Is_You/), [GDC talk by its developer](https://gdcvault.com/play/1026590/Reading-the-Rules-of-Baba), [Cosmoteer developer notes: crew and ammo](https://blog.cosmoteer.net/2011/02/starship-builder-crew-ammo.html), [ship combat](https://blog.cosmoteer.net/2012/02/starwright-ship-combat.html).

Текущий Bendvy может выразить такие клоны через типизированные компоненты, разнородные запросы и системы с явным порядком; структурные изменения должны проходить через публичные команды/барьеры. Но он не предоставляет готовые tile occupancy, belt/resource graph, movement/pathfinding, collision, rendering или input. Для Mindustry- или shapez-подобного порта эти solver/domain и host-части остаются отдельными моделями; их объём нужно учитывать отдельно от ECS-ценности. Этот вывод не требует нового API, производительной инфраструктуры или benchmark до выбора игры.

Factorio особенно полезен как предупреждение о границах: в FFF #82 разработчик пишет, что предметы на belts были отдельными игровыми entity, но затем последовательности стали внутренними структурами на невидимых путях; FFF #176 описывает хранение расстояний между предметами и обновление границ длинной линии. В заметках разработчиков 2015–2024 отдельно описаны компактное представление предметов на belts и transport lines, чтение содержимого всей transport line, вынесенный Fluid Manager и A*-pathfinding. Эти заметки очерчивают специализированные симуляционные/domain-задачи, но не доказывают архитектуру ECS самого Factorio; они также не позволяют называть Factorio «не ECS». [FFF #82](https://www.factorio.com/blog/post/fff-82), [FFF #176](https://www.factorio.com/blog/post/fff-176), [FFF #405](https://www.factorio.com/blog/post/fff-405), [FFF #421](https://www.factorio.com/blog/post/fff-421).

## Что Mindustry-like может добавить к уже имеющемуся примеру — при переархитектурировании

Bendvy [browser arena](../../../bendvy/examples/arena/README.md) уже запускает enemies, pickups, bolts, pulses и chains, но gameplay хранит много полей в одном `Body` и example оркестрирует прямые query вызовы. Простая arena поэтому уже показывает жизнь сущностей и урон; ещё одна игра только про бегущих врагов рискует повторить ту же демонстрацию.

Factory-defense меняет не сам факт, что entities бегают и получают урон, а **структуру композиции и количество взаимодействий между подсистемами**. ECS не является единственным возможным способом реализовать игру; проверяемая ценность здесь — сокращается ли дублирование и ветвление по типам, когда одинаковые `Health`, `Team`, `Position`, `Targeting` или `Status` нужны разным семействам акторов/построек. Если комбинаций и переиспользуемых проходов мало, ECS даст слабый практический выигрыш:

- Подвижный враг может иметь `Position + Velocity + Team + Health + PathGoal + Statuses`; неподвижная постройка — `GridCell + Footprint + Team + Health`; турель — `GridCell + Team + Inventory/Ammo + Targeting + Weapon`; снаряд — `Position + Velocity + Damage + Lifetime + Owner`. Это проектируемые наборы компонентов, а не описание оригинального кода.
- Запросы пересекают разные игровые роли: `Health + Team` для получения урона; `Velocity + PathGoal` для движения; `Inventory + Recipe + CraftProgress` для изготовления; `Ammo + Targeting + Team` для стрельбы. Новая вариация здания должна появляться через комбинацию capability-компонентов и query систем, а не через новый монолитный `Body` со всё большим количеством необязательных полей.
- Отложенные команды и барьеры пригодны для размещения/сноса, появления волны, рождения снарядов и удаления погибших акторов. События `ItemProduced`, `ItemDelivered`, `Hit`, `UnitDied`, `WaveStarted` могут иметь независимых читателей: например, состояние победы, журнал и host-анимация читают одну публикацию, не деля один курсор. Это предложение опирается на API Bendvy; у игры нет готовой принятой семантики событий/победы до проектирования самого приложения.
- Направленные отношения могут пригодиться для `target`, `owner`, `supports/powered-by` или containment, но сеть питания и транспортную топологию не стоит автоматически заменять relation queries. Для частых соседних переходов и массового обновления отдельный adjacency/path graph может быть яснее и дешевле.

Практический вывод — использовать ECS на уровне actors, building capabilities, lifecycle и игровых систем; grid-occupancy, belt routing, resource pools и pathfinding считать отдельными domain-моделями, которые ECS-системы читают и обновляют с явными границами. Рендер, ввод и аудио остаются host-слоем, а не ECS.

## Предлагаемый первый срез

Не полная кампания. Маленькая конечная карта с базовым ядром, одной рудой, одним добытчиком, belt-маршрутом, печью/производителем боеприпаса, одной турелью, одним типом врага и одной волной.

Один фиксированный tick должен показать законченный цикл:

1. Host переводит команду игрока разместить/повернуть/снести постройку в типизированную команду; map index отклоняет занятую клетку или размещает building entity. Структурная видимость наступает на явном barrier.
2. Mining/production system получает сырьё; отдельный transport graph переносит количество по выходам; processor с inventory/recipe двигает progress, расходует inputs, создаёт ammo.
3. Wave system создаёт врага-композицию `Position + Velocity + Team + Health + PathIntent`; движение использует простой маршрут по клеткам. Turret system выбирает подходящую цель и командует выпуск снаряда.
4. Projectile system двигает `Position + Velocity + Damage + Lifetime + Owner`; collision/bounds оставляет broadphase/grid и геометрию отдельной функцией. Damage system обновляет Health, публикует hit/death и ставит cleanup/drop commands; cleanup становится виден на следующем barrier.
5. Два независимых читателя событий обновляют одну и ту же sim-картину по-разному: счётчик волны/условие победы и игровой журнал/host-effects. Конечный headless output показывает состояние ядра, боезапас, позицию и HP врага, попадания и итог волны; browser host может дорисовать ту же симуляцию позже.

Это срез с несколькими честными ECS-системами и одной небольшой domain-графовой подсистемой. Он не требует делать из каждого item на конвейере отдельного entity: потоковые количества можно хранить в transport model/буферах. В движении живые `Unit`, `Projectile` и опциональные dropped pickup — отдельные entity, потому что у них независимые состояние, цель, коллизии и жизненный цикл.

## Совместимость с текущим Bendvy

**Факты репозитория на момент чтения:** [корневой README Bendvy](../../../bendvy/README.md) перечисляет world-scoped entity и typed components/resources, heterogeneous queries, declared accesses, systems/schedules, deferred commands/barriers, rollback, relations, machines и read-only inspection. Там же указано, что это ECS, а не полноценный игровой движок. [SPEC](../../../bendvy/docs/SPEC.md) требует детерминированный fixed-step консольный сценарий с перемещением/уроном/removal/events и говорит, что начальные systems исполняются последовательно на CPU; параллельный executor остаётся отдельным follow-up. [Parity index](../../../bendvy/docs/parity/README.md) помечает #63 как закрытый fixed-step ECS scenario и #64 как подготовку копии Tower Defense; принятый #64 пока планирует отдельную integration-копию Tower Defense; исходный проект остаётся read-only.

**Следствие (оценка, не проверенный application spike):** текущий API по заявленным возможностям достаточен для прототипирования typed-actors, declared queries, schedule ordering, barriers, relation/event consumers и headless output. Но он сам не даёт готового renderer/input loop, tile map, transport graph, routing, collision, AI pathfinding, content/recipe progression или игровых карт. Это надо писать и отдельно проверить как domain/host слой. Ни одна страница ECS capability не доказывает, что именно такой масштаб сцены уже принят на JS и Native. Исследование не предполагает FPS, entity count или ускорение; количественная оптимизация Bendvy в текущем SPEC отложена.

## Возражения и условия, которые опровергнут гипотезу

1. **Mindustry может оказаться объектной башенной защитой с ECS только у мобильных сущностей.** Источники подтверждают component-generation у Unit/Bullet, но не описывают всю игру как query-driven ECS. Tile держит `Building`, а `ConveyorBuild` хранит item arrays и цепочку соседей. Если пилот оставит турели, машины и все пересечения систем в специализированных ветках, это не лучший демонстратор композиции; лучше сначала протестировать простейший shapez-подобный production vertical slice.
2. **Графовая часть может поглотить всю работу.** Если честная симуляция belts/power и занятости grid требует постоянных bespoke обходов, а actors используют только 1–2 отдельных монолитных query, получится в основном graph simulator с ECS-библиотекой. Это прямо опровергает «максимальное раскрытие ECS».
3. **Factorio масштаб не переносится через вдохновение.** Первичные материалы описывают специальные транспортные линии, segment updates fluid и алгоритмический поиск пути. Клон, который моделирует каждый item/inserter/pipe как entity и обещает масштаб, не доказан источниками о Bendvy. Если целевой результат — именно огромная фабрика, Factorio-like может стать верным долгосрочным продуктом, но это не ограниченный showcase без решения отдельной задачи о графовых симуляциях.
4. **shapez может выиграть по реальной завершённости.** Если критерий — получить первую видимую игру на маленькой карте и показать компоненты строений/queries/schedule без разработки combat AI, shapez v1 проще и открыт. Его официальный README указывает, что исходный shapez является open source, но репозиторий больше не развивается командой, перешедшей на Shapez 2. Он также уже демонстрирует фильтруемые component systems, поэтому новый Bendvy-клон должен добавить взаимодействия, которых не показывает existing arena. [Официальный README и статус проекта](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/README.md)
5. **Лицензии требуют не смешивать «клон механик» и перенос материалов.** Официальные исходники Mindustry и shapez помечены GPL-3.0; это не запрещает независимую игру по жанру/идеям, но код и ассеты из этих репозиториев нельзя включать в продукт без осознанного решения по лицензии. В этом исследовании не предлагается копировать исходники, тексты, уровни, визуальные assets или trademarks. [Mindustry LICENSE](https://github.com/Anuken/Mindustry/blob/84fd6bf8f42128bbdaa4799670694a83b6c61adb/LICENSE), [shapez LICENSE](https://github.com/tobspr-games/shapez.io/blob/8a79de5255fb6756f3a1d26579b1e9bc36e0c811/LICENSE)

**Функциональный falsifier до выбора игры:** в работающем узком срезе разные family compositions должны пересекать несколько обычных systems; появление/удаление/смерть должно менять query membership через публичные barriers; хотя бы два independent consumers должны наблюдать события; добавление новой вариации турели или врага должно преимущественно менять состав компонентов/данные и не вынуждать править каждый проход игрового цикла. Если это не проходит, Mindustry-like selection недостаточно обоснован.

## Границы и проверка источников

- Factorio: официальные developer blogs и официальная mod API документация (runtime docs сейчас публикуются по версиям); source/asset implementation не использовались. [Runtime API: LuaEntity](https://lua-api.factorio.com/latest/classes/LuaEntity.html), [LuaTransportLine](https://lua-api.factorio.com/latest/classes/LuaTransportLine.html).
- Mindustry: собственный GitHub source репозитория закреплён на просмотренном commit `84fd6bf8f42128bbdaa4799670694a83b6c61adb`; официальный сайт и release Javadocs использованы для игрового цикла и tile/building boundary.
- shapez: официальный GitHub source закреплён на `8a79de5255fb6756f3a1d26579b1e9bc36e0c811` (ветка `master` на дату исследования); readme заявляет open-source игру и обработку shapes. Исходник/ассеты не запускались и не переносились.
- Bendvy: прочитаны текущие README, SPEC, parity index, workflow navigation и описание arena; репозиторий только читался.
- Это исследование выбора/архитектурной пригодности, не кодовый spike и не benchmark. Все прогнозы о степени использования ECS — inference по предлагаемому vertical slice, не наблюдение готового приложения.
