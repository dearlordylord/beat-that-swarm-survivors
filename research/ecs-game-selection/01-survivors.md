# Candidate study: survivor-style games as a Bendvy ECS showcase

**Hypothesis 1 of 10.** This first-pass study compares *Vampire Survivors*, *Brotato*, and *Halls of Torment* as references for a small playable game that demonstrates Bendvy's ECS. Game-loop facts below come from first-party store/publisher pages. The ECS models, vertical slice, and ranking are design inferences. No implementation, benchmark, or performance claim was made.

## Recommendation

Among these three survivor references, **Brotato's wave → combat → shop loop** is the clearest short-run prototype: it combines a changing crowd, weapon instances, and a between-wave build decision. That is not yet a case for Brotato as the best ECS clone across the wider candidate set. The adversarial cross-review below finds a Magicka-inspired spell challenge stronger for independent component composition, while Brotato remains a good choice if the top priority is a compact, recognizable wave-and-shop loop. *Vampire Survivors* is the closest match to Bendvy's existing swarm example, while *Halls of Torment* has more published content breadth than is useful for a first game slice.

This is a recommendation for the *shape of the prototype*, not a claim that the complete Brotato feature set is the best implementation target. Keep the run short, use original names/art/rules, and leave character unlocks, co-op, extensive catalogs, and meta-progression out of the first slice.

If the goal is maximum horde density, extend the existing *Vampire Survivors*-style arena. If the goal is maximum breadth of abilities, traits, and boss phases after the first game is delivered, *Halls of Torment* is a strong follow-up reference.

## What the first-party sources say

- **Vampire Survivors:** poncle describes a time-survival run against hundreds of monsters, with gold earned in a run funding upgrades for a later survivor. Its Steam page advises picking up gems/items, starting with several offensive weapons, and focusing their upgrades. A poncle update walkthrough also shows a weapon evolution gated by a max-level passive item. Those facts support a loop of moving through swarms, collecting drops, building a set of weapons, and surviving to the run's end. ([poncle's Steam page](https://store.steampowered.com/app/1794680/Vampire_Survivors/), [official update post](https://store.steampowered.com/news/app/1794680/view/4104540932629694732))
- **Brotato:** Blobfish describes a top-down arena run with up to six weapons, auto-fire by default, and player choice of traits/items. It explicitly divides play into waves lasting 20–90 seconds, collecting materials for experience, then buying from a shop between waves. This loop supplies the most varied *short prototype* boundary: real-time entity simulation followed by a transactional build change and another simulation phase. ([Blobfish's Steam page](https://store.steampowered.com/app/1942280/Brotato/), [Blobfish press factsheet](https://blobfishgames.com/press/brotato/))
- **Halls of Torment:** Chasing Carrots describes choosing a hero, surviving waves until a boss, and building during a run from traits, abilities, and items. The page also advertises quest-based meta-progression, bosses with distinct attack patterns, multiple stages, and items carried back to later runs. This is the broadest progression/content reference of these three, but most of that breadth can become catalogs, unlock UI, and save-state work before it exercises the core arena ECS. ([Chasing Carrots' Steam page](https://store.steampowered.com/app/2218750/Halls_of_Torment/))

These descriptions support observable gameplay only. They do not establish how any of the commercial games are internally implemented.

## ECS comparison (inference)

| Reference | ECS-shaped workload | Fit for a first Bendvy game |
| --- | --- | --- |
| *Vampire Survivors* | Large enemy groups, weapon effects, pickups, projectiles/areas, deaths and cleanup; weapon/passive combinations add build variation. | Strong for repeated updates and entity lifetimes. It overlaps most with the current Bendvy arena, so a new example risks repeating its single-arena swarm lesson. |
| *Brotato* | The swarm workload plus independently timed weapon instances, several enemy roles, material drops, wave boundaries, purchases, and newly equipped or upgraded weapons. | Best balance. Different queries and explicit schedule phases can be exercised without implementing a full campaign. A shop/catalog can stay ordinary resource/UI data; it need not be forced into entities. |
| *Halls of Torment* | Hero and class combinations, many skills/traits/items, boss phases and attack entities, pickups, quests, stages, and persistent progression. | Highest advertised content breadth, but its quest and metagame scope can dominate the work. Static trait tables alone do not demonstrate ECS; each behavior would need to compose through components/systems to justify this target. |

The distinction is architectural, not a known speed advantage. *Brotato*'s six weapons could be a six-element array, and a competent array-oriented implementation could handle every proposed mechanic. ECS earns its place here only if the game actually uses component presence to select independent behavior, declared system access, deferred entity changes, scheduled phase boundaries, and independent event readers. A central `EntityKind` switch wrapped in one `Body` component would mostly recreate the existing arena pattern.

## Concrete ECS model to try

The following is a proposed model of a Brotato-style game, not a statement about Brotato's internals.

- **World entities:** player, enemy, weapon instance, projectile, material pickup, temporary area effect, and (only if useful) in-world chest. Use distinct component families such as `Position`, `Velocity`, `Health`, `ContactDamage`, `EnemySteering`, `WeaponCooldown`, `WeaponPattern`, `ProjectileDamage`, `Pierce`, `Lifetime`, `MaterialValue`, and `Magnetizable`. A melee enemy can have `EnemySteering + ContactDamage + Health`; a shooter can have `EnemySteering + RangedAttack + Health`; a projectile does not need actor health or enemy AI.
- **Relations:** each weapon instance has an `EquippedBy` link to its player. This makes ownership, removal on run end, and queries for all weapons owned by one player observable. Avoid encoding owner links as unchecked host indexes if the public relation path is in use.
- **Systems and order:** host input writes player intent; movement advances entities with position/velocity; enemy steering updates enemy queries; each weapon ticks its own cooldown and emits a projectile or direct attack; projectiles move and check contact; damage updates health; death publishes one event and queues cleanup/drop work; pickup systems award materials/experience; the wave director changes phase when its own condition is met. Structural commands become visible at explicit barriers between the relevant phases.
- **Events:** publish `EnemyDied` once. Independent readers can update score/quest counters, create loot, and request a visual effect without one reader consuming another reader's notification. A compact first slice only needs a death event and one or two consumers; the model exposes the ownership/cursor benefit without requiring a broad event taxonomy.
- **Non-entity state:** keep wave number, phase, seed/RNG, currency, and shop offers in resources or host UI state. Only persistent gameplay objects need entity identity. Treating every offer/catalog row as an entity would add ECS machinery without a gameplay need.

A useful counterfactual design test is an original passive item called a **Gravity Well**. Its effect applies a time/slow field using shared `Position` and `Velocity` data, so the same system can slow the player, enemies, and projectiles in range without checking `kind`. Projectiles can still have a separate collision system because they carry `ProjectileDamage` and `Lifetime`. This is an invented example effect, not a Brotato feature. An array implementation can also share those fields; the ECS case is stronger if declared queries make that shared behavior composable and access-checked rather than another branch in the central game loop. If this item still needs a player/enemy/projectile case ladder, the proposed composition has failed its own test.

## Realistic vertical slice

Make one arena and one deterministic run with:

1. One controllable survivor, two enemy roles (a chaser and a slower high-health enemy), and a wave timer/resource.
2. Three weapon behaviors represented as separate weapon entities with their own cooldowns and ownership link. Start with two equipped; let a shop purchase add or replace one.
3. Projectile, health, death, material pickup, and player collection flows. Use circle overlap or another small custom collision rule; no general-purpose physics engine is required for the demonstration.
4. One between-wave shop screen with a few deterministic offers, one purchase, and a next-wave transition. The UI can be host-rendered while the purchase updates ECS-owned weapon/item state through the public commands and schedule.
5. A final survive/defeat result and restart. Feed input and a fixed seed from the host; retain a deterministic simulation route for backend checks.

The key review scenarios are structural and semantic: a purchased weapon joins the right query after the barrier; a killed enemy publishes one death observation and produces at most one drop; multiple death readers independently observe the same event; the Gravity Well applies to all shared-movement entities; and the run phase prevents combat systems from firing during the shop. These are scenario ideas, not tests run by this research task.

## Bendvy fit and boundaries

Bendvy already has a browser arena with enemies, pickups, bolts, pulses, chains, and ECS-driven movement/damage/cleanup. That example stores gameplay state in one compound `Body` component with a numeric `kind`, and it uses direct query orchestration; its README points to the separate scheduled-health example for registered systems and schedules. ([arena README](../../../bendvy/examples/arena/README.md), [arena game source](../../../bendvy/examples/arena/game.bend))

The scheduled-health example demonstrates separate `Health` and `HealthDecay` components, declared read/write access, a registered App entry, and a schedule with a structural barrier. The parity map also records delivered relation and typed Data-event slices. Those are useful foundations for the proposed weapon-owner link and independent death readers, but the examples do not amount to a finished game framework or prove game-scale performance. ([scheduled-health README](../../../bendvy/examples/scheduled-health/README.md), [current parity map](../../../bendvy/docs/parity/README.md))

Keep simulation rules in Bend and browser controls/rendering in the host, as the existing arena does. Use JS Canvas for the first playable presentation and deterministic JS/Native observations for the same simulation rules where practical. The renderer, keyboard handling, shop widgets, asset loading, and frame clock are host concerns; the game rules, world components, schedules, commands, and event readers are the ECS demonstration. The repository is CPU-oriented; don't add a GPU/parallel-compute premise to this project.

## Adversarial review against the other candidates

The existing arena already demonstrates enemies, moving attacks, pickups, damage, and cleanup. Brotato adds a shop phase and explicit build choices, but currency, offers, and weapon definitions can all remain ordinary arrays or resource data. If buying an item only changes a row in a player-stat table, that is little new ECS evidence. Brotato's incremental ECS value must come from *runtime composition*: individually addressable weapon entities with their own cooldown/attack components and an `EquippedBy` relation; purchases adding, replacing, or removing those entities at a phase boundary; and gameplay systems querying shared components across distinct families. A weapon catalog alone does not meet that bar.

The proposed **Gravity Well** makes the counterfactual concrete: represent the field by `Position + Radius + SlowFactor + Lifetime`; a single system applies its effect to any entity with `Position + Velocity` in range, including the player, enemies, and moving projectiles, with no `kind` branch. This is a design proposal, not a Brotato mechanic. A short array loop could also implement it, so it earns ECS value only if the checked query and independently composed behaviors make the system clearer than a central dispatcher. `EnemyDied` should likewise have real independent readers—for example, reward accounting and wave completion—not two wrappers around one score update.

| Alternative | It beats Brotato when… | What would make it a worse first slice |
| --- | --- | --- |
| **Magicka-inspired spell challenge** | The primary goal is independent, overlapping gameplay rules: the same `Health`/`Faction` target can receive different spell deliveries and optional statuses, and a state such as `Wet` changes later effects without actor-kind branches. The publisher explicitly describes combining elements, single-player play, and a wave-based challenge, so a solo slice can retain a recognizable loop without co-op. ([Paradox](https://www.paradoxinteractive.com/games/magicka/about); see also the [official manual](https://cdn.akamai.steamstatic.com/steam/apps/42910/manuals/Magicka%20manual%20body%20--%20English.pdf)) | If spells collapse to a static profile table plus one resolver switch, it has no more ECS substance than a weapon catalog; it also needs enough distinct status interactions to stay recognizably spell-composition gameplay. |
| **Noita-inspired hybrid** | The goal is explicitly to study the boundary between ECS actors/effects and a dense material-grid simulation. | Its defining material simulation becomes a separate grid/solver problem, reducing the share of the project that exercises ECS. |
| **Teardown-inspired heist** | The goal is object ownership/manipulation, mission phases, and a later integration with destructible geometry. | Voxel changes, physics, lighting, and rendering can dominate the first consumer. |
| **FTL-inspired tactics** | Crew assignment, ship/room ownership, targeting, power allocation, and pause/order phases are the desired ECS proof. Subset's own Steam page confirms player orders for crew, system power, and weapon targets, plus pausing combat to issue orders. ([Subset Games on Steam](https://store.steampowered.com/app/212680/FTL_Faster_Than_Light/)) | A crew navigation graph, room UI, and authored encounter content would exceed Brotato's simpler host unless the ship layout and campaign are tightly fixed. |
| **Cosmoteer-inspired combat** | Maximum relation and composition breadth is worth paying for module construction, crew tasks, hazards, damage, and topology changes. | Editor, ship geometry, pathfinding, spatial combat, and rendering make it a poor first playable under the current host. |
| **PvZ-inspired lane defense** | The priority is a small deterministic strategy game with a clear placement/resource choice and explicit win/lose conditions. The official manual describes row-and-column placement, sun as the purchase resource, and advancing enemy waves. ([EA/PopCap manual](https://akamai.cdn.ea.com/eadownloads/u/f/manuals/GAME-PVZ/en_US_readme.html)) | Fixed lanes and a tiny board may be clearer as arrays, and tower-defense work overlaps the separate planned #64 product; its ECS case depends on live upgrades/statuses changing component composition. |
| **Bloons-inspired defense** | Upgrade branches and active abilities are the intended focus, and a content-driven tower progression is valuable. | The upgrade catalog, balancing, and broad content surface can dominate; static branch data is not runtime ECS composition. |
| **Dungeon Defenders-inspired action defense** | The project specifically needs hero/tower/enemy interactions, equipment, loot, and co-op breadth, and the host can support action movement and 3D combat. | Its action, collision, navigation, renderer, and networking costs are far beyond Brotato's bounded arena loop. |

This comparison **withdraws Brotato as the default winner for “maximum ECS exposure.”** The strongest defensible first ECS recommendation is a small **Magicka-inspired solo spell challenge**, provided the slice uses real optional state components (for example, `Wet` and `Burning`) that change generic damage/status queries, multiple delivery forms, a shared target model for player/allies/enemies, and independent hit/death readers. Keep spell recipes and the shop-like catalog as data; they do not count as ECS evidence. Pick Brotato instead if finishing a short wave/shop game matters more than demonstrating richer cross-cutting composition. Pick FTL for a relation-and-phase-first target, or Cosmoteer only if “maximum breadth” outranks first-slice cost. These are design judgments, not claims about the commercial games' internal architecture.

## Risks, counterarguments, and falsifiers

- **Arrays may be the simpler answer.** With one player, six weapons, and a bounded arena, plain records/lists can be clear. If the implementation still has one traversal and a central kind dispatch, ECS has not made the system structure better. The decision should be judged on query separation, composition, schedule clarity, and ownership/lifecycle contracts, not on a presumption that ECS is faster.
- **Targeting and collision can dominate.** Naive all-pairs collision or each-weapon scanning every enemy can grow quickly. ECS does not supply a spatial broadphase by itself. Keep the first slice bounded and do not promise large-swarm performance without a later matched workload and measurements.
- **Shop logic can become the product.** Rerolls, item tiers, prices, inventory merging, multiple characters, unlocks, and saved progress can overwhelm the core demonstration. Keep shop offers deterministic and simple, and keep catalog data out of the entity world unless it needs runtime identity/lifecycle.
- **Relations/events can become decoration.** If the weapon owner relation is never queried or lifecycle-relevant, or if only one system reads death data, those features do not add much to the sample. Retain them only when the scenario demonstrates a concrete contract.
- **The hypothesis is falsified** if separating queries into component families makes the short game harder to read than a small array model; if every update still depends on one kind switch; if weapon ownership and event readers are not useful in the selected behaviors; or if a compelling prototype requires the full class/quest/meta-progression breadth of *Halls of Torment*. In that case, prefer a smaller *Vampire Survivors*-style arena extension or reassess the candidate set rather than claim ECS value from entity count alone.

No feature count, entity count, FPS, allocation, or speedup is inferred from these games. Quantitative performance is a separate question and this subtask did not benchmark anything.
