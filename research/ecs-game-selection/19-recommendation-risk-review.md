# 19 — риск рекомендации SS14 при текущем Ordinary App API

**Дата проверки:** 2026-10-20. Проверены отчёты 12 и 17 и первичные исходники Bendvy; код, сборки и тесты не запускались.

## Вывод

Рейтинг [17](17-independent-ranking.md) отвечает на вопрос «какая игра лучше всего вскроет ширину ECS?» и по этой оси SS14 остаётся сильнейшим кандидатом. Но он недостаточно отделяет эту цель от «какую игру удобнее прямо сейчас собрать поверх обычного Bendvy App». Для второй цели SS14 — плохой эталон текущего ergonomic пути: частая связка actor → held tool → target object как раз пересекает сущности, а стандартный компонентный callback получает только объявленные grants для текущей строки.

Это основание разделить рекомендации, а не автоматически понизить SS14 в рейтинге максимального ECS-потенциала. Если цель — использовать игру как стресс-тест и при необходимости развить API, SS14 остаётся первым. Если цель — показать игровую систему на обычном API без работы над библиотекой, ограниченный Magicka-подобный AoE срез выглядит лучше; Baba Is You — хороший второй выбор для проверки динамического состава, но его правило-сканнер и grid/push resolver дают более узкую ECS-поверхность. См. также независимый аудит API в [12](12-cross-entity-access-audit.md).

## Два подтверждённых ограничения обычного пути

1. **Query-композиция штатно соединяет доступы на одном owner, не делает join по handle.** Ordinary component body параметризован непрозрачным `H`, получает `Ops(H)` и `Args`; руководство прямо указывает, что body должен пользоваться объявленными capabilities, а registration не предоставляет доступ к другому компоненту или конкретному World ([App body contract](../../../bendvy/docs/reference/ordinary-app.md#L66-L72), [factory signature](../../../bendvy/src/ecs/ordinary-app-component.bend#L66-L75)). `ordinary-query-declaration.pair` принимает обе декларации с одним `H`; `compose.get/set` используют `Frame.handle`, то есть handle текущей строки ([pair](../../../bendvy/src/ecs/ordinary-query-declaration.bend#L121-L130), [current-row get/set](../../../bendvy/src/ecs/compose.bend#L49-L77)). Отдельный relation query может вернуть target handle в detached row, но callback получает только `ValueRead<Row>`; runtime relation provider выдаёт inverse lookup и queued relate/unrelate, а не target-компонентный writer ([relation row](../../../bendvy/src/ecs/relation-query.bend#L23-L38), [read-only callback](../../../bendvy/src/ecs/relation-query.bend#L92-L95), [provider grants](../../../bendvy/src/ecs/relation-providers.bend#L11-L18)). Поэтому обычный путь не позволяет в одном callback пройти от actor к произвольному target, прочитать его компоненты и сразу журналируемо изменить их.

2. **Успешная transaction и structural barrier — разные границы.** `transaction.finish` при успехе коммитит записанные изменения и ставит команды в очередь; он явно не исполняет barrier ([finish](../../../bendvy/src/ecs/transaction.bend#L71-L95)). Команды становятся видимыми на барьере. Ordinary App выполняет системы по порядку регистрации ([attach/run contract](../../../bendvy/docs/reference/ordinary-app.md#L121-L144)); scheduler отдельно подтверждает, что failure останавливает schedule на этой системе, а предыдущие успешные systems не откатываются как общая schedule-транзакция ([schedule result](../../../bendvy/src/ecs/schedule.bend#L30-L33)). Явная вставка также перепроверяется при barrier application, уже после постановки ([insert contract](../../../bendvy/src/ecs/compose.bend#L269-L291)).

Эти факты говорят об эргономике и границах commit, но не о невозможности собрать игровой срез. Один query traversal транзакционно обрабатывает выбранные строки, а `Args:Data` позволяет передать заранее построенный план целей; например, один тип компонента можно обновить у множества сущностей в одной операции ([query transaction](../../../bendvy/src/ecs/compose.bend#L257-L267), [App args](../../../bendvy/src/ecs/ordinary-app-component.bend#L66-L75)).

## Развести две рекомендации

| Цель | Выбор | Почему |
|---|---|---|
| Максимум естественных ECS-пересечений и обнаружение недостающих возможностей | **SS14** | Разные системы повторно пересекают actor, tool, target, контейнер, состояние станции и round outcome. Это делает target join, межсемейную координацию и политику barrier видимой частью настоящей игровой задачи, а не искусственным тестом API. Утверждение о максимальном охвате — архитектурный вывод из игрового цикла, как и отмечено в [17](17-independent-ranking.md); факт существования таких механик не доказывает, что они удобно выражаются именно текущим Bendvy API. |
| Лучший потребитель текущего Ordinary App без изменения ядра | **Magicka-подобный AoE срез**, затем **Baba Is You** | Для AoE отдельная hit-фаза может выдать список целей, а один `Health` query применить damage текущим строкам. Для Baba отдельная rule/push-фаза может подготовить карту новых позиций, а один `GridPosition` query применить её. Оба варианта обходят произвольную межсущностную запись через typed plan, но не демонстрируют полноценную relation/многофамильную композицию SS14. Описание планов и ограничений уже есть в [12](12-cross-entity-access-audit.md). |

Между двумя узкими кандидатами **Magicka ближе к гладкому пути текущего API**, если срез ограничен ударом/уроном по заранее разрешённому списку целей: это один однотипный writer и понятный query. Полное заклинание, меняющее Wet/Burning, projectile ownership, окружение и геометрию, быстро возвращает deferred structural и relation сложности; такой полный sandbox уже не следует выдавать за простой API demo. **Baba лучше показывает динамическое изменение поведения через состав компонентов**, но правила, занятость клеток и push-chain должны быть заранее разрешены, а добавление/снятие `Push/Stop/Win/You` остаётся отдельной structural фазой. Это полезный фокусный showcase, но не широта SS14.

## Adapter или изменение библиотеки?

- **Достаточно typed adapter и фаз**, если цель принимает предварительный hit/push/interaction plan, immediate writes одного семейства, затем structural barrier и видимые промежуточные стадии. Adapter может хранить detached handles/эффекты в `Args`, провести проверку отдельным read pass и применить данные текущим row query. Это не даёт общую атомарность, но такая atomicity не обязательна для этих специально выбранных срезов.
- **Нужна новая first-class возможность или тяжёлый доверенный adapter**, если обещание игры требует единого all-or-nothing действия через relation target, компоненты разных сущностей/семейств, ресурс и structural changes. Сейчас стандартные grants не предоставляют этот join/write unit, а несколько registrations имеют отдельные commit границы. Adapter может взять на себя более широкие access metadata, планирование, проверки и rollback policy; он способен снять продуктовый блокер для одного проекта, но это будет локальная реализация недостающей эргономики, а не evidence, что обычный API уже её поддерживает.

**Риск для исходного вывода:** в [17](17-independent-ranking.md) сказано, что текущие затраты не меняют рейтинг ECS-потенциала. Это корректно лишь для абстрактной цели «выявить максимум». Для практического выбора игры, реализуемой именно на сегодняшнем Ordinary App, ограничения меняют рекомендацию: SS14 остаётся диагностическим лидером, но Magicka-подобный ограниченный slice — более надёжный образец того, что можно выражать обычным API сейчас. Если приоритет пользователя — именно максимум ECS, а готовность менять Bendvy допустима, SS14 остаётся рекомендуемым выбором с явным признанием, что межсущностная композиция станет одним из предметов разработки.
