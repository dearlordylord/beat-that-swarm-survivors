# 19 - risk of SS14 recommendation with current Ordinary App API

**Date of review:** 2026-10-20. Reviewed reports 12 and 17 and Bendvy primary sources; no code, builds or tests were run.

## Conclusion

The [17](17-independent-ranking.md) rating answers the question “which game will best open up the ECS width?” and along this axis SS14 remains the strongest candidate. But he does not sufficiently separate this goal from “what game is more convenient to build on top of the regular Bendvy App right now.” For the second goal, SS14 is a poor standard for the current ergonomic path: the frequent connection actor → held tool → target object just intersects entities, and the standard component callback only receives declared grants for the current line.

This is the basis for splitting the recommendations rather than automatically downgrading SS14 in the maximum ECS potential ranking. If the goal is to use the game as a stress test and develop the API if necessary, SS14 remains the first. If the goal is to show a game system on a regular API without working on a library, a limited Magicka-like AoE slice looks better; Baba Is You is a good second choice for testing dynamic composition, but its scanner rule and grid/push resolver give a narrower ECS surface. See also independent API audit at [12](12-cross-entity-access-audit.md).

## Two Confirmed Limitations of the Conventional Path

1. **Query composition normally connects accesses on one owner, does not join by handle.** Ordinary component body is parameterized by opaque `H`, receives `Ops(H)` and `Args`; The manual explicitly states that the body must use the declared capabilities, and registration does not provide access to another component or a specific World ([App body contract](../../../bendvy/docs/reference/ordinary-app.md#L66-L72), [factory signature](../../../bendvy/src/ecs/ordinary-app-component.bend#L66-L75)). `ordinary-query-declaration.pair` accepts both declarations with one `H`; `compose.get/set` use `Frame.handle`, that is, handle the current row ([pair](../../../bendvy/src/ecs/ordinary-query-declaration.bend#L121-L130), [current-row get/set](../../../bendvy/src/ecs/compose.bend#L49-L77)). A separate relation query can return target handle in detached row, but the callback receives only `ValueRead<Row>`; The runtime relation provider issues an inverse lookup and queued relate/unrelate, rather than a target component writer ([relation row](../../../bendvy/src/ecs/relation-query.bend#L23-L38), [read-only callback](../../../bendvy/src/ecs/relation-query.bend#L92-L95), [provider grants](../../../bendvy/src/ecs/relation-providers.bend#L11-L18)). Therefore, the usual path does not allow you to go from actor to an arbitrary target in one callback, read its components and immediately change them in a logged way.

2. **Successful transaction and structural barrier are different boundaries.** If successful, `transaction.finish` commits the recorded changes and queues the commands; it clearly doesn't execute barrier ([finish](../../../bendvy/src/ecs/transaction.bend#L71-L95)). Commands become visible at the barrier. Ordinary App executes systems in order of registration ([attach/run contract](../../../bendvy/docs/reference/ordinary-app.md#L121-L144)); scheduler separately confirms that failure stops the schedule on this system, and previous successful systems are not rolled back as a general schedule transaction ([schedule result](../../../bendvy/src/ecs/schedule.bend#L30-L33)). Explicit insertion is also rechecked during barrier application, after installation ([insert contract](../../../bendvy/src/ecs/compose.bend#L269-L291)).

These facts speak about the ergonomics and limits of commit, but not about the impossibility of assembling a gaming slice. One query traversal processes selected rows transactionally, and `Args:Data` allows you to transfer a pre-built plan of goals; for example, one component type can be updated across multiple entities in one operation ([query transaction](../../../bendvy/src/ecs/compose.bend#L257-L267), [App args](../../../bendvy/src/ecs/ordinary-app-component.bend#L66-L75)).

## Separate two recommendations

| Goal | Choice | Why |
|---|---|---|
| Maximize natural ECS intersections and discover missing opportunities | **SS14** | Different systems re-intersect actor, tool, target, container, station state and round outcome. This makes target join, interfamily coordination, and barrier policy a visible part of the real game problem, rather than an artificial API test. The statement about maximum coverage is an architectural conclusion from the game loop, as noted in [17](17-independent-ranking.md); the fact that such mechanics exist does not prove that they are conveniently expressed by the current Bendvy API. |
| Best consumer of the current Ordinary App without changing the core | **Magicka-like AoE slice** then **Baba Is You** | For AoE, a separate hit phase can produce a list of targets, and one `Health` query can apply damage to the current lines. For Baba, a separate rule/push phase can prepare a map of new positions, and one `GridPosition` query can apply it. Both options bypass arbitrary inter-entity recording via typed plan, but do not demonstrate a full-fledged SS14 relation/multi-family composition. A description of plans and restrictions is already in [12](12-cross-entity-access-audit.md). |

Between two narrow candidates **Magicka is closer to the smooth path of the current API**, if the cut is limited to impact/damage on a pre-resolved list of targets: this is one single type writer and clear query. A full spell that changes Wet/Burning, projectile ownership, environment and geometry quickly returns deferred structural and relational complexity; such a complete sandbox should no longer be passed off as a simple API demo. **Baba better demonstrates dynamic behavior changes through component composition**, but rules, cell occupancy and push chains must be resolved beforehand, and adding/removing `Push/Stop/Win/You` remains a separate structural phase. It's a useful focal showcase, but not the breadth of SS14.

## Adapter or library change?

- **A typed adapter and phases suffice** if the goal accepts a preliminary hit/push/interaction plan, immediate writes within one family, then a structural barrier and visible intermediate stages. Adapter can store detached handles/effects in `Args`, check with a separate read pass and apply the data with the current row query. This does not give overall atomicity, but such atomicity is not necessary for these specially selected slices.
- **A new first-class capability or a substantial trusted adapter is needed** if the gameplay promise requires one all-or-nothing action spanning a relation target, components of different entities/families, a resource and structural changes. Currently standard grants do not provide this join/write unit, and several registrations have separate commit boundaries. The Adapter can take on broader access metadata, planning, checks and rollback policy; it is capable of removing a product blocker for one project, but this will be a local implementation of the missing ergonomics, and not evidence that the regular API already supports it.

**Risk to original conclusion:** [17](17-independent-ranking.md) states that ongoing costs do not change the ECS potential rating. This is correct only for the abstract purpose of “revealing the maximum.” For practical selection of a game implemented specifically on today's Ordinary App, the restrictions change the recommendation: SS14 remains the diagnostic leader, but the Magicka-like limited slice is a more reliable example of what can be expressed by the regular API now. If the user's priority is maximizing ECS, and a willingness to change Bendvy is acceptable, SS14 remains the recommended choice, with the explicit recognition that inter-entity composition will be a development item.
