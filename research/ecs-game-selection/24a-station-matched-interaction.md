# Matched interaction: station repair vs. colony repair

**Purpose.** This note answers the skeptical review's request for a matched gameplay trace, rather than comparing the whole station's atmosphere and power surface with a colony job scheduler in the abstract. It reads [the solver-weighting review](20-synthesis-skeptical-review.md), [the corrected cross-entity API audit](12-cross-entity-access-audit.md), and the primary [station](07-space-station.md) and [colony](03-colony.md) studies. No implementation, game run, or benchmark was performed.

## Matched trace and result

Both traces begin with one living actor already adjacent to a damaged barrier, carrying the only available repair input. The actor repairs the barrier, changing a local hazard boundary; the actor then crosses to a goal in the newly safe area. The scenario fixes the actor and target before the action so neither trace gets extra credit for counting an unrelated global scheduler or pathfinder. A wider colony game can add those systems back as separate work.

* **Station reference:** an engineer uses a held, partly fueled welder to repair a damaged barrier. A proposed content composition makes the repaired barrier airtight again; after the air solver updates, the engineer crosses the corridor to the evacuation control.
* **Colony reference:** a colonist carries the last repair material to a damaged firebreak/door. The proposed content composition makes it block the hazard again; after the local environment step, the colonist crosses to shelter.

The station repair path is source-backed: SS14 has a `RepairableComponent` with a required tool quality and fuel cost, a `RepairableSystem` that uses the shared tool interaction, and an integration test that repairs a damaged reinforced window with a welder. Its atmosphere system separately queries airtight/grid state and applies exposure to entities. The evidence **does not** prove that the tested window prototype combines all those components or that repair automatically restores airtightness. Combining repair, barrier state and the hazard boundary is the explicit clone scenario being evaluated here. See the source limits below.

The colony side is likewise a proposed matched microtrace, not a claim that vanilla RimWorld consumes steel to repair a wall. Ludeon's sources support physical stockpiles, priorities, hauling, pawn jobs and environmental danger. A last carried material as a repair prerequisite is imposed here to equalize the resource decision with the station welder's limited fuel. The adaptation is intentionally visible because otherwise the two player actions would not be comparable.

**Result:** the matched action gives SS14 much stronger *evidence confidence* because its repair/tool/exposure seams are in source. It does not show that the atmosphere internals are independent ECS queries. Count one atmosphere integration/solver boundary, then count only separately queried entity families that act on the resulting state. The colony trace can be decomposed into similar actor, material, target and outcome consumers, but the source record does not reveal its implementation boundaries. A full colony scenario introduces a real additional job-assignment decision; it is not needed to make this single-worker repair fair.

## The query ledger: what is actually independent

An ECS “query” below means a separately registered consumer that selects an entity family by component presence and owns a distinct read/write set. A tool attempt callback, a call into a solver, each gas node inspected inside a solver, a relation lookup, or a second subscriber to the same synchronous event is **not** counted as a separate ECS query.

| Consumer | Read set | Write set | Independent ECS query? | Why it is separate |
|---|---|---|---|---|
| `Q_tool_inventory` | `ToolQualities`, `Fuel`, tool liveness; plan contains `HeldBy` result | `Fuel` on the selected tool after approved completion | **Yes**, if it is a registered query over tool/fuel entities. This is a separate component family from the barrier target. It cannot itself query arbitrary relation target components. | Tool eligibility/resource changes are useful in other interactions too. In the original source, `SharedToolSystem` instead resolves the selected tool and calls the user, tool and target synchronously. |
| `Q_repair_target` | Current target's `Repairable + Damageable + BarrierState` and its handle | `Damageable` repair amount and the existing `BarrierState` value | **Yes.** It selects repairable targets and writes the target row; it does not inspect unrelated actor or tool rows through its row capability. | Repair progression/damage belongs to the target family. If seal state changes optional component membership, see the structural note. |
| `Q_actor_exposure` | `AtmosExposed + Position/Transform + Health` and the latest containing mixture result | Actor `Health`/exposure status | **Yes.** This is a distinct actor-family consumer after the environment update. | It changes character consequences based on environment, independently of repair and objective logic. The source SS14 analog is its exposure entity query. |
| `Q_actor_motion` | Actor `Position`, collision/movement capabilities, current barrier passability | Actor `Position` | **Yes**, if registered independently. | A safe route changes actor movement eligibility. The fixed scenario needs only a one-step move; it does not imply navmesh/pathfinding. |
| `Q_goal` | Actor alive/at-exit state and `BarrierState` or committed `RepairCompleted` | Objective completion state | **Yes** as a separate objective evaluator, but **not another interaction query** if it only consumes the event. | It demonstrates a post-commit consumer that can be reused for other mission outcomes. |
| `RepairIntent` validation | Actor status and location; selected held-item relation; tool quality/fuel; target liveness, damage and repairability | None; returns accept/refuse and a plan | **No** under current Bendvy ordinary row-query semantics. It is a cross-entity action resolver/plan builder. | The current API audit says a relation view yields detached handles and ordinary writers target the current row; actor → tool → target joins need a plan, typed passes or a custom adapter. Do not count each read in this resolver as an independent query. |
| `Q_hazard_field` | Grid/map/gas or local fire/smoke field, plus barrier connectivity | Field mixture/intensity and derived zone state | **No**, for this comparison. It is one specialized field/topology solver call. | ECS entity consumers integrate with its result, but the solver's internal loops/nodes are not added to the ECS-query count. |
| `Q_repair_complete readers` | Committed `RepairCompleted` event | Independent objective, incident/log and presentation reader state | **Independent readers, not entity queries.** | Reader independence can justify an event stream without pretending each subscriber selects a component archetype. |

The shared set is `Q_tool_inventory`, `Q_repair_target`, `Q_actor_exposure`, `Q_actor_motion`, `Q_goal`, plus one environment solver and one multi-entity action resolver. SS14 has direct source evidence for the repair/tool/event and exposure sides. The colony fixture proposes the same actor/material/target/outcome surface plus job semantics; its source materials do not show equivalent ECS queries. Do **not** turn “AtmosphereSystem has several dependencies” into several more rows in this ledger. They are integrations and inputs to the one hazard solver boundary.

## Colony trace and the solver fairness rule

The colony data map is deliberately scoped to one pawn with the repair job already selected and the material already carried. This matches the station actor's user-issued repair intent and avoids smuggling a many-pawn allocator into one side only.

| Colony consumer | Read set | Write set | Independent? |
|---|---|---|---|
| `Q_pawn_work` | `WorkPolicy`, skill/capability, `Health`, assigned-job state | Job progress / pawn work state | Yes, pawn/job consumer; it may stop work on injury or invalid assignment. |
| `Q_carried_material` | `CarriedBy`, stack kind and `Quantity` | Decrement `Quantity`; possibly queue despawn at zero | Yes, separate item/stack family. Carried relation is observed through an immutable plan, not foreign-row access. |
| `Q_repair_target` | `Damageable + Repairable + BarrierState` | Target integrity and barrier state | Yes, target family. This is analogous to station target repair as a *proposed* component mapping, not an assertion about RimWorld internals. |
| `Q_pawn_environment` | Pawn `Position + Health/Needs` and field output | Health/Needs exposure state | Yes, actor consumer after the hazard field pass. |
| `Q_pawn_motion` | Pawn position and the now-passable route | Pawn position | Yes. For the matched adjacent case it is a local collision/movement check, not a path search. |
| `Q_job_assignment` | Pawn candidates, repair jobs, priorities/skills, material availability/reservations and reachability | Chosen job and reservations | It is a distinct registered system, but its **global choice** is one specialized scheduling/reservation pass, not several independent per-component queries. With one eligible pawn and one job, it degenerates to a simple validity check. A full colony slice with competing priorities should include one such scheduler pass. |
| `Q_goal` / event readers | Pawn alive/at-shelter and committed job/barrier result | Outcome state; separate log/UI readers | Goal is one distinct evaluator. Readers are event consumers, not additional ECS queries. |

### Solver calls (one per domain boundary)

| Trace | Specialized work invoked in the matched interaction | Explicitly not counted as query breadth |
|---|---|---|
| Station | 1 local atmosphere/grid update after airtight state changes; 1 exposure selection/effect pass over `AtmosExposed + Transform` entities; local tool-fuel solution lookup/consumption and one timed do-after; 1 adjacency/interaction-range check. | Gas mixtures, nodes, tiles, pressure propagation and network traversal are internal to the atmosphere solver and count once. Welder fuel solution bookkeeping and the do-after clock are services, not independent ECS query families. No power-network solver is invoked. No route pathfinder is needed for the one-step goal. |
| Colony | 1 local fire/smoke/temperature field update after the barrier state changes; 1 pawn exposure pass; 1 local adjacency/movement check. If the colony slice permits competing jobs, add exactly 1 global scheduler/reservation pass. | Field cells/connectivity count once inside the environment solver. The fixed adjacent actor needs no pathfinding. With only one pawn and one selected job, do not charge a non-existent global optimization call; with the real multi-worker colony slice, do not hide the scheduler either. |

The matched scenario therefore does **not** justify saying “SS14 has N extra ECS queries because atmosphere has N internal stages.” Nor does it justify demoting RimWorld solely because a full run could include a work scheduler. In a full-game comparison, count one pressure solver against one fire/temperature solver and one colony assignment solver against any station job/round scheduler actually retained; audit each candidate's ECS integration separately. For this microtrace, both have a handful of genuinely separate component consumers and one hazard solver. SS14's lead is confidence in actual boundaries and a richer source-backed integration surface, not a multiplied solver count.

## Relations, barriers and transaction/failure semantics in Bendvy

### Relations and structural visibility

* `HeldBy(actor, welder)` / `CarriedBy(pawn, stack)` is a real relation because the item's owner/location changes and needs inverse lookup/cleanup. `AssignedTo(job, pawn)` and `Targets(job, barrier)` are also useful for the colony job model; add them only if work can be reassigned or cancelled. Keep the target entity handle in the validated immutable action plan.
* A relation observation returns detached handles, not a capability to read/write the target's row. The ordinary component writer addresses only the current row. The [cross-entity audit](12-cross-entity-access-audit.md) says arbitrary actor → tool/material → target updates need a prebuilt typed plan, multiple passes, or a checked custom adapter; they do not become one atomic row query because a relation exists.
* Keep `BarrierState` as a field in an already installed target component for the minimal trace. This lets the repaired/open/sealed fact be a same-target-row write and avoids creating a structural barrier solely to claim composition.
* If the implementation instead adds/removes `Broken`, `Airtight` or `Passable` capabilities, queue that structural command and apply it at an explicit barrier. Queries before the barrier still see the old membership. If a zero-quantity material stack is despawned, the actor↔stack/job relations also become stale until the removal/cleanup policy runs.

### Pre-commit refusals and stale targets

Validation must run before spending fuel/material or modifying damage:

1. **Invalid actor/tool/input:** actor is dead/disabled, the selected item is no longer held, tool lacks `Welding` quality, welder is off, fuel is short, material kind/quantity is wrong, or the target is already undamaged. Return an explicit refused result; stage no component change, relation change, structural command or `RepairCompleted` event.
2. **Dead/stale target:** if the target no longer exists or no longer matches `Repairable + Damageable`, reject before writes. If it disappears between plan creation and execution, revalidate when the target-family pass matches the handle; do not heal a substitute entity with a recycled/colliding local ID. Publish no success event.
3. **Cancelled do-after:** moving, damage, tool/target veto or other cancellation produces no repair result. The game decides whether a cancelled/abandoned attempt consumes any fuel; the SS14 welder implementation has its own do-after fuel timing, so a clone must not assume fuel rollback from a later target failure.

These are proposed application rules informed by SS14's explicit tool quality/user/tool/target gates. In the original source, `UseTool` returns false for a missing/wrong-quality tool or cancelled attempt; the separate target event completes only after the timed action. The exact target-deleted-between-phases outcome must be tested for any implementation; this note does not infer a general atomic guarantee from those callbacks.

### Transaction and late barrier failure

The safe Bendvy intent is: validate first; apply target damage, consumed resource, stable barrier-state field and staged event within a deliberate action boundary; only publish `RepairCompleted` after the game state needed for the route is visible. This matched action crosses distinct actor/tool/target families, so the current ordinary App route does not provide an out-of-the-box atomic three-entity join. Do not promise it as an ordinary query. Use a verified custom composite action declaration or make the phase boundary explicit and maintain a pending/reconciliation state.

If a structural version is chosen, a failure before the action system commits rolls back that system's journaled writes and staged publications. Once it commits, the later barrier is a separate operation: if revalidation/relation/component application fails there, earlier committed damage/fuel writes and already-published events do **not** automatically roll back. Thus:

* never emit final `RepairCompleted`, `HazardStabilized` or `GoalReached` before the structural barrier is confirmed;
* either keep the effect as a stable `BarrierState` field for this tiny scenario, or represent an explicit `RepairPending`/recovery state and retry/compensate after a late barrier refusal;
* report the barrier failure separately and keep the objective incomplete. The action's visible `RepairStarted` may be committed earlier, but it must not be confused with completion.

In the colony trace, a stack depleted to zero or a relation removal can hit the same late-barrier boundary. A later failure in the job/goal system also does not undo a previously committed repair system. If multi-entity all-or-none is essential for a scarce resource, keep reservation and consumption within the verified composite transaction path; do not spread them across independent scheduled systems and then call them one transaction.

For successful completion, `RepairCompleted` is an informational `Data` event after committed writes. Independent objective and incident/log readers may observe it; the hazard system still runs its own scheduled field update. Robust's directed `RepairedEvent` is synchronous and target-local, so this is a semantic translation rather than event API parity. The current [ordinary App contract](../../../bendvy/docs/reference/ordinary-app.md) executes registrations in order, and Bendvy's [`Data` event contract](../../../bendvy/docs/parity/typed-data-events.md) retains independent readers and transaction-governed publication.

## Strongest objection: the global resolver may be clearer

For this deliberately tiny trace, a single `repair(actor, item, barrier)` function can be the clearer product design. It reads three records, validates one action, consumes one scarce input, updates one target and returns `repaired/refused`; a fixed field map handles the local hazard and the goal check is one condition. A small array-of-structs update or one interaction resolver can implement that without an ECS runtime. The colony fixture's one-pawn/one-job case especially has no meaningful scheduler optimization.

The ECS case survives only if the consumer grows just enough that independent reuse is real: the same `Repairable + Damageable` target path is used by windows, machines and crew; the same held-item/tool systems participate in repair, construction and other interactions; the actor exposure query serves all exposed actors; goal/log readers independently observe committed results; and optional barrier/health/control capabilities change which queries match. If these are not distinct consumers in the actual small application, a global resolver is the honest choice. The one trace alone cannot prove ECS is better.
