## Problem Statement

The existing bots are built for testing mechanics. They choose upgrades immediately, run either at realtime pace or without a speed limit, and finish when their run ends. Their behaviour is hard to follow as a viewer, their strategy is compiled into the native program, and they do not provide a continuous audiovisual show.

The operator wants a separate bot for a 24/7 stream or recorded video. Viewers should have time to see decisions, and the operator should be able to edit and replace strategy code during a live run. This must preserve the native headless bots used for mechanics testing, including their independent-world CPU parallelism and their freedom from Node.js or Python controllers.

## Solution

Add an opt-in native stream session with an externally editable JS/TypeScript strategy, readable decision presentation, game audio, and automatic transitions between runs. The game continues to execute in Bend. A separately supervised strategy process returns bounded intentions through a language-neutral interface. The native policy remains available as the fallback.

Changing strategy code prepares and validates a new generation before switching at a decision boundary. A failed edit leaves the working strategy active. A disconnected or stalled strategy cannot freeze the game window or hold combat waiting for advice.

Keep normal visible bots, the parallel grid and fast headless batches as separate existing launch modes. The stream session is for observation, not a new speed benchmark or a replacement for mechanics-test controllers.

## User Stories

1. As a viewer, I want upgrades to remain visible before confirmation, so that I can understand the choices offered to the bot.
2. As a viewer, I want to see which offer the bot is considering, so that the final choice is understandable.
3. As a viewer, I want a short explanation of the current intention, so that I can follow the strategy without reading a debug log.
4. As a viewer, I want the bot to pursue stable travel goals, so that its movement does not look like unexplained direction changes every frame.
5. As a viewer, I want the bot to react to imminent danger, so that presentation delays do not prevent necessary evasive movement.
6. As a viewer, I want the bot to collect XP physically, so that it follows the same game mechanics as a person.
7. As a viewer, I want normal game music and sound effects, so that the native stream is suitable for watching or recording.
8. As a viewer, I want death or victory followed by a readable transition into another run, so that the stream continues without an operator.
9. As an operator, I want a dedicated stream launch mode, so that presentation behaviour does not affect mechanics tests.
10. As an operator, I want to choose the initial profile, seed and run setup, so that I can reproduce a run or arrange a sequence of runs.
11. As an operator, I want to edit strategy code while the game runs, so that changing priorities does not require rebuilding or restarting the native game.
12. As an operator, I want strategies written in JS or supported TypeScript, so that normal editor and debugging tools remain available.
13. As an operator, I want a language-neutral decision interface, so that another language can be connected later without rewriting the game.
14. As an operator, I want strategy loading to report syntax and initialization errors visibly, so that a broken edit is diagnosable.
15. As an operator, I want the previous strategy to remain active when a replacement fails validation, so that editing does not interrupt the show.
16. As an operator, I want the active strategy revision to be visible, so that I know which code the bot is using.
17. As an operator, I want compatible policy memory to survive a successful reload, so that the bot does not forget its current goal unnecessarily.
18. As an operator, I want incompatible memory to reset explicitly, so that a new strategy does not silently misinterpret old state.
19. As an operator, I want a faulty or nonresponsive strategy to fall back to the native policy, so that the native session stays playable.
20. As an operator, I want fallback and restart reasons to remain visible, so that recovery does not hide errors.
21. As an operator, I want configurable decision cadence and presentation delays, so that the stream's pace can be adjusted without changing mechanics.
22. As an operator, I want to reload, pause and resume the stream session, so that I can manage a recording or a live demonstration.
23. As an operator, I want bounded strategy queues, logs and retained generations, so that repeated edits do not accumulate indefinitely.
24. As an operator, I want automatic strategy-process recovery with backoff, so that temporary failures do not create a restart storm.
25. As an operator, I want one launch command to supervise the optional strategy service, so that normal operation does not require starting several terminals manually.
26. As a strategy author, I want current legal upgrades and relevant goal candidates from the game, so that I do not duplicate progression rules or invent invalid actions.
27. As a strategy author, I want visible threats and remembered XP or discoveries, so that decisions can use player-like knowledge rather than hidden whole-world information.
28. As a strategy author, I want movement and goal preferences to be adjustable in code, so that risk tolerance, build priorities and collection strategy can differ between personalities.
29. As a strategy author, I want explicit time and size limits for requests and memory, so that I can write a strategy that fits the stream service's contract.
30. As a maintainer, I want Bend to remain authoritative for physics, combat, RNG, XP and legal choices, so that scripting does not create a second game implementation.
31. As a maintainer, I want replies from old runs, phases or strategy generations rejected, so that delayed advice cannot corrupt the current decision.
32. As a maintainer, I want presentation time separate from simulation time, so that an upgrade pause cannot prevent its own confirmation deadline from expiring.
33. As a mechanics-test user, I want existing headless commands to run without Node.js and without presentation waits, so that the streaming feature does not slow or replace my test bots.
34. As a mechanics-test user, I want the existing native grid and CPU parallelism preserved, so that observing multiple ordinary bots remains available.
35. As a maintainer, I want decision records tied to run, strategy and source identity, so that behaviour seen in a video can be traced back to the code that produced it.
36. As a maintainer, I want real native-session recovery and long-running evidence, so that a passing unit test is not mistaken for a reliable 24/7 stream.

## Implementation Decisions

- Implement in a separate worktree from current canonical `master`. Recheck current source before implementation. This specification authorizes the stream feature, not an engine rewrite, deployment or a measured 100× optimization campaign.
- Keep the authoritative simulation and ordinary native policy in Bend. Strategy code may decide intentions and build preferences; it cannot create entities, award XP, change damage, bypass collisions or choose unavailable upgrades. Keep published BendHub dependency pins authoritative.
- Add an explicit stream session alongside existing headless, normal visible and parallel-grid modes. Existing commands retain their defaults and do not acquire a Node dependency, strategy IPC, delays or stream-session lifecycle.
- Use one optional supervised Node.js strategy service, with replaceable Workers for JS/TypeScript strategy generations. Pin a supported Node version. Support erasable TypeScript syntax with a separate type-check step; do not promise arbitrary TypeScript execution without a toolchain. Other languages are future adapters to the same protocol.
- Maintain a shared typed decision boundary between observation, policy choice and application. Today the native driver calls the compiled policy directly; the external interface does not already exist. Refactor only the necessary seams, reuse native planning/steering and game decisions, and preserve ordinary controller semantics. Do not copy the native bot into a second scripted implementation.
- Define one authoritative typed observation and intention model. Expose current legal offered upgrades and bounded relevant goals, player/build status, visible threats and remembered discoveries. External strategy may rank or choose goals, return a legal upgrade and provide an intention label. Existing native steering executes goals and can react to urgent danger without waiting for a script. Any low-level movement override must use the same bounded input contract as player movement.
- Establish a real supported native transport/codec boundary in the first vertical slice. Use asynchronous local IPC and a single authoritative or type-derived wire schema. In-process Bend code passes typed values. Do not rebuild the removed full-state file-command controller, hand-build JSON in game logic, add a second manual schema generator, or assume a stable native FFI that has not been demonstrated. Coordinate this boundary with the typed-output work rather than restoring its obsolete encoders. This is an explicit feasibility gate before widening implementation: demonstrate the supported native asynchronous transport and compliant codec. If either is unavailable under these constraints, record the exact missing capability and dependency, retain the working native modes, and stop that integration path. Do not bypass the gate with legacy exporters or expand into compiler/runtime work.
- Publish bounded observations only at decision cadence or relevant events, not the full ECS world every tick or render. Bound messages, collections, policy memory and queued work; report truncation or aggregation explicitly. Keep one pending strategy decision per session and coalesce superseded observations. Select concrete bounds during the vertical slice and record them as configuration defaults.
- Keep strategy IO asynchronous. The native event/render loop continues while advice is pending. Use native local fallback or a still-valid prior intention during combat. Never pause active combat solely to wait for strategy code.
- Give each request a session/run identity, request identity, strategy generation, phase and decision/offer identity. Simulation ticks describe game causality. Native monotonic presentation time controls deadlines. Admit a reply only while its decision is current and unexpired; reject stale, malformed, non-finite or unavailable actions. Failure recovery must not admit replies from an earlier generation or run.
- Implement readable presentation as an explicit stream state machine, separate from strategy and game phase. During an existing upgrade pause, show offers for an advice window, then freeze one current legal recommendation or a native fallback at the advice cutoff. Display that frozen recommendation for a separate minimum dwell and commit exactly once afterward. Initial defaults are a 500 ms advice window and a 1500 ms recommendation dwell, both configurable. A reply after the cutoff cannot replace the displayed recommendation or shorten its dwell. Revalidate the decision identity before commit; a changed offer set starts a new decision instead of applying stale advice. Deadline handling must work while simulation ticks are stopped. Do not insert sleeps into the render loop or add artificial simulation ticks.
- Persist stream UI state across frames. The current bot renderer reconstructs initial UI state and native offer rendering has no recommendation index. Add explicit offer highlighting and intention display rather than assuming the existing menu-selection field already handles upgrade offers.
- Operator pause stops simulation advancement, upgrade confirmation and next-run startup while keeping window events and rendering active. Accumulated presentation dwell and run-transition delays stop during operator pause and continue from their remaining duration on resume. Invalidate outstanding advice on pause; resume requests fresh advice for the current phase and decision. Preserve the frozen legal recommendation where its identity remains current. Hot-reload candidates may prepare while paused, but activation waits for a valid resumed decision boundary. Pause and resume audio through the persistent native audio session without creating a second session.
- Retain meaningful goals across movement decisions. Replan on relevant danger, damage, invalid goals or being stuck. Scripted style may vary risk and XP/build priorities. Random input jitter and arbitrary delays before every action are not the definition of realism. Emergency steering can interrupt an outdated travel intention.
- Prepare each changed strategy in a fresh Worker, load its dependencies, validate its exported contract and run a bounded smoke decision before activation. Switch generations atomically at a decision boundary. A syntax error or invalid candidate keeps the last known good generation. Avoid accumulating cache-busted ESM imports in a permanent Worker.
- Carry only explicit, bounded, versioned plain-data strategy memory between generations. Preserve compatible memory; reset incompatible memory visibly. Keep native navigation/observation memory with its correct native owner. New-run decision identity and temporary goals reset; operator configuration may persist. Do not attempt to transfer arbitrary closures or runtime heaps.
- Bound candidate preparation, strategy execution and upgrade waits. Distinguish candidate preparation from active strategy execution. A candidate syntax error, initialization failure, invalid smoke reply or smoke timeout retires only that candidate and leaves a healthy active generation running. Failure of the active decision or active process visibly activates native fallback and recovery with backoff. Cancel or retire obsolete work, terminate retired Workers, and supervise the entire sidecar process when Worker recovery is insufficient. Node Worker limits are not a total process-memory guarantee.
- Support both change detection and explicit reload. Debounce file writes, validate a complete candidate and use content identity to avoid redundant reloads. Replacing the strategy must not require rebuilding Bend or restarting the game world.
- Reuse native game audio and its persistent audio-session lifecycle for music and effects. Existing bot windows bypass that lifecycle; audio is new integration work. Avoid per-frame audio-session recreation, duplicate sounds on reload and orphaned audio devices between runs. Provide mute control for recording setups.
- The stream session owns a bounded end-of-run display, automatic next-run startup, seed progression and optional configured run rotation. Death or victory is expected, not a strategy-service crash. Show genuine game failures and recover by resetting session/run state deliberately; do not silently report success or continue corrupted state.
- Expose current run and strategy identity, active/native-fallback/reloading state, current intention, actual FPS/TPS and actionable errors in a compact stream overlay. Keep developer stack traces in accessible diagnostics rather than filling the recording view. Record accepted decisions, reload outcomes and failures with bounded logs; do not invent explanations for a strategy that supplied none.
- Provide one documented launch flow for macOS Apple Silicon and the supported Linux native environment. The launcher starts and supervises the optional strategy service. Closing the window or terminating the launcher cleans up owned Workers, sockets, processes and audio resources without affecting another running game. Use an isolated stream profile initialized from the chosen setup. Do not write to the operator's normal player profile; persistence or reset of stream-only progress is explicit configuration.

## Testing Decisions

- Use one main acceptance seam: the launched native stream session driven through its public launch/control interface, with strategy edits and external strategy faults as inputs. Observe rendered frames, actual game progression, audio output, accepted-decision records, reload status and process exit. Exercise production code rather than a parallel test-only session model.
- Preserve existing seams for native headless launch and the ordinary visible/grid runners. Use these for compatibility and no-Node checks rather than inventing another bot test framework. Tests assert visible behaviour and authoritative results, not internal function names or Worker counts.
- State Bend laws for the production stream-session decisions before implementation. Cover current-decision admission, old-generation/run rejection, expiry, legal-offer membership, exactly-once confirmation, minimum recommendation dwell, late advice after cutoff, stopped simulation clocks, operator pause/resume and bounded recovery transitions. Falsify and mutate the actual implementation, including late replies, duplicate confirmations and a wrong clock. Keep proof claims limited to the properties actually stated.
- Reuse prior native window checks, bounded driver probes, scheduler-law checks, mixed-completion probes and launcher fixtures. A JS test may help diagnose protocol or reload behaviour but is not the final authority for native game behaviour or 24/7 reliability.
- In the first native vertical slice, demonstrate one real upgrade: the live game supplies legal offers, the external strategy receives the bounded typed observation, the recommendation appears, frames continue during dwell, and one legal choice is applied after the configured wait. Demonstrate the actual native IPC/codec in that slice; a Node-only mock is insufficient.
- Edit strategy priorities during a live run and observe a new validated revision affect the next eligible decision without resetting the world. Test initial syntax errors, broken replacements, dependency edits, incompatible memory, rapid repeated saves, disconnection, a deliberate infinite loop and a reply arriving after reload or new-run startup. In particular, a candidate whose smoke decision loops must leave a healthy active strategy making decisions. Each fault must leave the native window responsive and disclose its recovery outcome.
- Verify physical XP collection and goal continuity, and verify that emergency steering continues during delayed strategy replies. Check that observations do not grant hidden whole-world knowledge merely because a native snapshot contains it.
- Verify operator pause during advice collection, recommendation dwell and the between-run transition. No confirmation or new run occurs while paused; resume honours the remaining dwell and rejects pre-pause advice. Verify game audio, mute, death/victory transitions, automatic next runs and shutdown on actual native execution. Check that reloads and run rotation do not duplicate effects, leak audio resources or write to the operator's normal player profile.
- Run the existing deterministic native bot fixtures before and after any shared-driver refactor. Compare observations, actions/memory where existing probes expose them, and gameplay results at the same seeds and tick bounds. Verify existing headless commands with Node and Python unavailable, and rerun the native parallel-grid checks. Do not claim complete physical-state equality from a summary-only comparison.
- Treat the first working native vertical slice and 24/7-readiness qualification as separate milestones. Run a real 24-hour stream-session soak before claiming 24/7 readiness. Include repeated successful and failed reloads, strategy-service restarts and multiple automatic new runs. Record source/runtime identities, run/reload counts, frame/tick progress, memory, queue/log growth and visible failures. Set and record resource-growth and responsiveness limits before the soak. Capture evidence that no stale generation acts and that owned resources are reclaimed. A shorter development run is useful but does not replace this qualification. A successful soak qualifies only the recorded configuration and limits; it is not a universal uptime guarantee.
- Do not start a new headless speed campaign under this specification. Stream timing includes deliberate presentation behaviour and is not an estimator of the separate 100× headless goal.

## Out of Scope

- Replacing ordinary headless bot controllers with JS, Python or another external runtime.
- Achieving or declaring completion of the separate single-world 100× performance goal.
- Changing combat, XP rules, spawn pressure, difficulty or multiplayer balance to make the stream look better.
- Multiplayer streaming, host migration, chat integration, Twitch/YouTube broadcast configuration or deploying a public streaming service.
- Training a bot, automatic post-run learning, paid classifier integration or claiming a validated model of human behaviour. A future strategy may use a classifier through the same interface.
- Shipping Lisp, Elixir or other adapters, embedding QuickJS/Lua, or building a general-purpose mod runtime in this first implementation.
- Moving game logic outside Bend, adding a local/vendored ECS dependency, compiler/runtime changes or a Bend-to-WASM port.
- Restoring removed full-world JSON exporters or file-command controllers, selecting a project-wide build-system migration, or solving every typed-output issue as part of the stream feature.
- Treating native fallback as a reason to suppress errors, claiming deterministic script behaviour without recorded decisions, or claiming proven whole-game correctness from session laws.
